**Access — внутренний компонент RAG API.** Он определяет допуск сотрудника и административные действия. Runtime реализует ORM, чтение и атомарные переходы PostgreSQL. Отдельный модуль верхнего уровня не создаём.

## Приём сотрудника

1. Из достоверного Telegram update получаем отправителя и тип чата. Вопросы допускаются только из личного чата с ботом.
2. Проверяем User ID в списке разрешённых сотрудников. Chat ID используется для доставки, но не заменяет идентичность сотрудника.
3. Неавторизованному пользователю не запускаем Core, модели, поиск и создание тикета. Решение о пропуске/отказе подтверждает update; потерянный ответ не должен превращаться в повторное принятие вопроса.
4. Для допущенного сотрудника RAG API различает вопрос и действие Support. Только самостоятельный вопрос занимает активный слот.

Проверка активного слота выполняется атомарно при регистрации, чтобы два одновременно пришедших вопроса не были оба приняты. Повтор уже принятого update возвращает прежний исход. Другой вопрос занятого сотрудника получает уведомление без постановки в очередь.

## Администрирование

Администратор через web-панель тикет-системы управляет разрешёнными Telegram User ID. Первого администратора назначает оператор развёртывания; публичной bootstrap-ручки нет. Способ web-входа остаётся открытым, до его подключения защищённые ручки закрыты. Сам Telegram User ID в теле внешнего web-запроса не является подтверждённой личностью.

Отключение сотрудника запрещает регистрацию новых вопросов. Ранее принятый вопрос завершается обычным путём: Core не отменяется из-за enabled=False, текст и оставшиеся изображения досылаются с обычными ограниченными повторами. Если итог — автоматическая эскалация, создание тикета и доставка ссылки также завершаются. Принятым считается вопрос с подтверждённым коммитом register_question; повтор того же update возвращает его прежний исход.

## Границы прав

- В MVP опубликованная документация общая для допущенных сотрудников; фильтрации по отделам нет.
- Документная ролевая модель — возможное расширение.
- Механизм web-входа ещё не выбран; права уже заданы: сотрудник видит свои тикеты, operator/admin — все. Авторизация новых web/Support-действий проверяется по текущим правам.
- Сбой чтения допуска не превращается в разрешение; разрешающая заглушка допустима только для изолированного теста.

Изменение enabled и register_question согласуются по одному user_id в PostgreSQL. Коммит приёма до отключения сохраняет право завершить этот вопрос; если отключение зафиксировано первым, новый вопрос получает denied. Отдельного поля-снимка enabled в DTO вопроса не нужно: разрешение подтверждает уже сохранённый принятый request.
