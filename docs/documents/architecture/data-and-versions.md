## Кто владеет данными

| Данные | Кто отвечает за изменение | Где хранится |
| --- | --- | --- |
| Входящий вопрос, место в порядке чата и исход доставки | RAG API | PostgreSQL. |
| Ход обработки, выбранные редакции и готовый результат | RAG Core | PostgreSQL. Готовый результат доступен для повторной доставки. |
| Входной файл до завершения индексации и запись о принятой загрузке | Ingestion Gateway принимает, Ingestion Worker удаляет файл после завершения | Рабочий том worker и PostgreSQL. |
| Задание после приёма, активная редакция и поколение корпуса | Ingestion Worker | PostgreSQL. |
| Фрагменты, векторы и локаторы источников | Ingestion Worker пишет, Searcher читает | Qdrant. |
| Копия готового ответа для повторного использования | Exact Cache | Redis. |
| Записи о передаче следующего сообщения | Каждый владелец этапа создаёт свою запись, Queue Relay отмечает отправку | Outbox в PostgreSQL. |

RabbitMQ доставляет уведомления со ссылками на работу. Вопрос, результат и состояние попыток получатель читает из PostgreSQL. [Очереди и доставка](./message-flow.md)

Рабочие таблицы, форматы записей и порядок запуска описаны в Runtime. [Компоненты Runtime](../infrastructure/index.md)

## Как меняется версия корпуса

**Корпус** — все документы, доступные боту для поиска. У каждого документа в этом наборе одна опубликованная редакция. **Редакция** — версия одного документа, а **поколение корпуса** — номер версии всего набора.

Например, в поколении 41 бот ищет по документам A и B. После публикации нового документа C поколение 42 включает A, B и C. Редакции A и B те же, но C может изменить ответ на тот же вопрос, поэтому ответ из кеша для поколения 41 уже не подходит для поколения 42. Запрос, который начал обработку на поколении 41, заканчивает по A и B.

Публикация новой редакции или нового документа увеличивает поколение. Если состав меняется при удалении или откате, это тоже новое поколение. Подготовка индекса сама по себе поколение не меняет. [Где хранится номер поколения](../infrastructure/postgresql/index.md#corpus_state)

1. Ingestion Worker записывает новую редакцию в Qdrant рядом со старой и проверяет, что фрагменты доступны. Затем одной транзакцией переключает активную редакцию, увеличивает поколение и фиксирует публикацию в PostgreSQL.
2. В начале обработки RAG Core согласованно с публикацией и очисткой сохраняет поколение запроса. Этот номер удерживает все видимые в нём редакции. Их ID читаем перед поиском при промахе кеша. Это исключает гонку, в которой запрос выбрал старую редакцию, а worker уже разрешил её удалить.
3. Searcher читает фрагменты по закреплённому составу. При рестарте Core восстанавливает этот состав из сохранённого состояния. Пока запрос может возобновиться, редакции остаются закреплёнными.
4. RAG Core освобождает редакции в той же транзакции, в которой сохраняет итог и задачу доставки. RAG API берёт готовый результат для отправки. Ingestion Worker может очистить старые фрагменты, когда редакция выведена из активного состава и ни один запрос её не удерживает. Зависший запрос сначала возобновляем или явно завершаем. Для ссылки на источник используем сохранённый адрес или локатор по условиям кейса.

Вариант для MVP — одна короткая точка синхронизации в PostgreSQL для закрепления состава, публикации и разрешения очистки. Запрос сохраняет закрепление до вызова поиска, а worker отмечает редакцию готовой к удалению до обращения к Qdrant. Если по кейсу появится откат, повторную активацию и очистку одной редакции нужно взаимоисключить. [Блокировки в PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html)

~~~mermaid
sequenceDiagram
  participant C as RAG Core
  participant P as PostgreSQL
  participant W as Ingestion Worker
  C->>P: Начать запрос A и закрепить поколение 41
  W->>P: Опубликовать новую редакцию и поколение 42
  Note over C: Core перезапустился
  C->>P: Возобновить A с поколением 41
  C->>P: Начать запрос B из другого чата с поколением 42
  C->>P: Сохранить итог A и освободить редакции
  P-->>W: Старую редакцию можно очистить, если других запросов нет
~~~

## Когда Exact Cache устаревает

RAG Core передаёт Exact Cache вопрос, нормализованный Guardrails, и поколение, которое взял из PostgreSQL в начале обработки. Совпадение проверяется с этим поколением запроса, в том числе когда новый документ меняет ответ, а прежние источники ещё существуют.

| Что нашли в Redis | Что делаем |
| --- | --- |
| Совпадают вопрос и поколение | Используем готовый ответ с источниками. |
| Запись старше поколения запроса | Условно удаляем прочитанную запись и идём полным путём. Удаление выполняется атомарно и только если запись с тех пор не заменили. |
| Запись новее поколения запроса | Пропускаем запись без удаления и идём полным путём по закреплённому составу. |
| Записи нет или кеш недоступен | Идём полным путём по закреплённому составу. |

При записи более старый запрос не перезаписывает результат нового поколения. Если PostgreSQL недоступен до выбора поколения, Core повторяет этот этап по правилам восстановления. Кеш остаётся копией готовых ответов. [Условные транзакции Redis](https://redis.io/docs/latest/develop/interact/transactions/)
