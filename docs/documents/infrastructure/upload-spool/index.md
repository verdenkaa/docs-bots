## Запуск

Именованный том `worker_spool` подключён к `worker`. Здесь хранятся **результат конвертации**, манифест и подготовленные поисковые наборы. Исходные документы и файлы изображений в этот том не записываются.

## Запись временного файла

Внутренний ключ `uploads/<revision_id>` определяет каталог:

| Файл | Содержимое |
| --- | --- |
| `converted.md` | UTF-8 Markdown с описаниями и плейсхолдерами изображений. |
| `manifest.json` | Название исходника и список ImageRef, без байтов/секретов. |
| `chunks.json` | Полная DocumentBatch: source с именем/доступом/необязательным source_url и непустой упорядоченный массив PreparedChunk. Сохраняется Gateway до регистрации. |
| `prepared.json` | Неизменяемый PreparedRevision: чанки, примеры, векторы и профили. Появляется до первой записи Qdrant. |

~~~json
{
  "source": {"filename": "Руководство.docx", "access_level": "employees"},
  "images": [
    {"image_id": "e1246aa5-3bba-4a74-8445-60b6271c0551", "description": "Схема согласования"}
  ]
}
~~~

Адаптер сначала пишет во внутренние временные файлы, обеспечивает устойчивость и атомарную видимость полного Markdown/манифеста, затем возвращает ключ. После аналогичной записи prepared.json разрешается начинать запись индексов. Повреждённый существующий подготовленный набор — ошибка, не основание незаметно сгенерировать другой.

## Приём и восстановление

1. Gateway сохраняет изображения S3, результат конвертации и полную DocumentBatch через store_document_batch, затем транзакцией PostgreSQL регистрирует редакцию/outbox. Только после коммита возвращает accepted.
2. Worker читает chunks.json через load_document_batch, без повторного разбиения Markdown. Если prepared.json уже есть, использует его **вместо** повторной генерации примеров и embedding. Если prepared.json ещё нет, embedding и генерация примеров по той же партии могут выполняться заново: запись Qdrant ещё не разрешалась.
3. После публикации/окончательного сбоя без незавершённой записи Worker удаляет весь каталог и очищает staging_ref. Для qdrant_write_pending=true каталог сохраняется до сверки.
4. HTTP Gateway до возобновления приёма и затем периодически выбирает старые остатки, включая неполные записи. Recovery/Worker также запускает сверку. Возраст задаёт RAG_RECOVERY_WINDOW_S. Обход идёт страницами по staging_ref, поэтому зарегистрированные каталоги не закрывают доступ к следующим кандидатам. Gateway держит отдельную OS-блокировку `<revision_id>.upload.lock` от начала вызова до завершения регистрации/отмены. Очистка пробует ту же блокировку без ожидания, пропускает активную загрузку и держит её до окончания удаления. Удаляет только после is_staging_referenced=False, дождавшись возможного коммита регистрации. При недоступном PostgreSQL ничего не удаляет. После падения процесса ОС освобождает блокировку. Все процессы, работающие с одним spool, используют общий том и каталог блокировок.
5. Отказ до начала регистрации удаляет собственный staging сразу; ошибка удаления оставляет его для фоновой сверки. При неизвестном коммите или отмене регистрации материалы сохраняются до сверки с БД. Файлы блокировок не удаляются при обходе, чтобы исключить замену inode активной блокировки.
6. Потеря тома до публикации — технический сбой задания, нужна новая загрузка оригинала. После штатной публикации том больше не нужен для поиска.

Долговременные данные: чанки/примеры в Qdrant, включая source_url чанков, изображения S3, состояние и source_name/image_ids в PostgreSQL. URL также сохраняется внутри готовых ответов и кеша. Уборка каталога не затрагивает S3 и метаданные источника. [PostgreSQL](../postgresql/index.md)
