:::warning Проектное решение
Определены границы подтверждения приёма и доставки. Число параллельных отправок, интервалы, срок хранения и пределы нагрузки уточним по условиям запуска.
:::

## Приём и постановка вопроса

1. Проверяем источник и передаём Telegram Update в `handle_telegram_update`. Корректное обновление вне поддерживаемых типов пропускаем.
2. Для текстового вопроса вызываем `register_question(update_id, chat_id, question_text)`. Повтор по `update_id` получает прежний ID, новый запрос и outbox для `rag.questions` сохраняются вместе. [Контракт приёма](./entrypoints.md#handle-telegram-update)
3. Подтверждаем приём Telegram после коммита. Queue Relay публикует уведомление независимо от входного адаптера. Core получает идентификатор работы и читает текст из PostgreSQL.

Порядок внутри чата задаёт `request_id`, выданный при регистрации. Очередь может доставить уведомления в другом порядке, поэтому очередность проверяем в PostgreSQL. [Маршруты RabbitMQ](../../architecture/message-flow.md)

Временный сбой RabbitMQ допускает приём, пока PostgreSQL принимает записи и число незавершённых запросов ниже лимита. В лимит входят принятые вопросы до окончательного исхода доставки, даже если Relay уже отправил уведомление. При достижении предела новые вопросы ждут повторной доставки Telegram. Уже принятые повторы можно подтвердить после проверки сохранённого состояния.

| Режим | Когда подтверждаем обновление |
| --- | --- |
| Webhook | Возвращаем `200` после коммита, при распознанном повторе или корректном пропуске. Если новый вопрос не удалось надёжно зарегистрировать, возвращаем ошибку. [Ручка webhook](../endpoints/telegram-webhook.md) |
| Long polling | Обрабатываем пачку по порядку, двигая `offset` до `update_id + 1` за непрерывной последовательностью завершённых обновлений. При `retry_later` останавливаемся на этом обновлении и повторяем с задержкой. Некорректный Update с валидным ID фиксируем в диагностике и пропускаем. Если ID отсутствует, текущий ответ считаем некорректным и повторяем чтение с последним надёжным `offset`. После рестарта первый вызов без `offset` берёт неподтверждённые обновления. [Telegram Bot API](https://core.telegram.org/bots/api#getupdates) |

## Отправка результата

В MVP в контейнере `core` планируем одного потребителя `rag.results` с общим лимитом отправки для бота. Он может отправлять в разные чаты параллельно. Приём обновлений и отправка результатов работают независимо.

1. Ограничиваем приём уведомлений слотами отправки. `handle_rag_result` вызывает `claim_delivery(request_id)`, чтобы получить сохранённый итог и зафиксировать попытку. На один чат допускается одна активная доставка.
2. Если результат пришёл раньше своей очереди, `claim_delivery` возвращает `None`, а уведомление подтверждаем. Завершение предыдущей доставки создаёт запись outbox для следующего готового ответа под той же блокировкой чата.
3. Если номер попытки выше лимита, вызываем `complete_delivery(attempt, delivered=False, uncertain=False)` без новой отправки. PostgreSQL учитывает уже сохранённую неоднозначность. Иначе отправляем через `send_answer(chat_id, result)` в пределах оставшегося срока попытки. По исходу сохраняем окончательное состояние в `complete_delivery` или планируем повтор в `schedule_delivery_retry`. Подтверждаем RabbitMQ после коммита или подтверждённой потери права на переход. [Состояния и сбои](../../architecture/lifecycle.md#кто-продолжает-работу-после-рестарта)

## Сбои и повторы

| Событие | Действие RAG API |
| --- | --- |
| Хранилище временно недоступно | Откладываем обработку уведомления до восстановления. Подтверждение RabbitMQ следует за сохранением результата или ожидания. |
| Некорректное уведомление или запрос отсутствует после успешного чтения | Фиксируем сбой маршрутизации и подтверждаем уведомление после фиксации. |
| Telegram ограничил частоту | Планируем повтор с учётом `retry_after`, если он пришёл. Сохраняем время повтора. |
| Временный сбой Telegram или сети | Повторяем с экспоненциальной задержкой до предела попыток. После таймаута Telegram мог уже принять сообщение, поэтому возможен дубликат. |
| Ответ превышает лимит длины | `send_answer` отправляет короткое пояснение в рамках текущей доставки. Если Telegram подтвердил его, отмечаем доставку и освобождаем следующий ответ чата. [Правила форматирования](./entrypoints.md#send-answer) |
| Окончательный отказ Telegram или предел попыток | Фиксируем итог доставки и освобождаем следующий результат чата. Если хотя бы одна попытка могла дойти и подтверждения нет, итог остаётся неизвестным. |

Готовый результат для каждой попытки берём из сохранённой записи. Число отправок ограничиваем отдельно от скорости обработки вопросов в Core. [Telegram Bot API](https://core.telegram.org/bots/api#responseparameters) · [Подтверждения и prefetch RabbitMQ](https://www.rabbitmq.com/docs/confirms)

Порядок определяет, когда RAG API может начать отправку следующего ответа. После неизвестного исхода сообщение от прежней попытки всё ещё может появиться в чате.
