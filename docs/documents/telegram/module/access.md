**Access — внутренний компонент RAG API.** Runtime хранит список допуска и атомарно проверяет его при приёме.

## Приём сотрудника

1. Из Telegram Update получить from.id, from.username и личный chat. User ID остаётся владельцем вопроса, активного слота и callback; Chat ID задаёт доставку.
2. Нормализовать username в нижний регистр без @. Админ-форма также удаляет один начальный @; DTO принимает только каноническую запись из ASCII-букв, цифр и подчёркивания, длиной 1–32. Отсутствующий username не даёт допуск новому вопросу или действию Support.
3. Проверить username в PostgreSQL employees: запись существует и enabled=True. Username берём только из Telegram from, не из текста вопроса или callback_data.
4. При регистрации сначала проверить ledger update; новый вопрос повторно проверяет допуск атомарно, затем единственный активный слот по user_id. Повтор принятого update возвращает прежний исход, даже после отзыва доступа.

Username — изменяемое имя: список разрешает текущего носителя имени, а не навсегда привязывает разрешение к первому User ID. После смены имени новое имя должно быть разрешено администратором. Старые вопросы/тикеты сохраняют исходный user_id, доступ к ним через callback проверяется по нему. Уже принятый вопрос, его доставка и автоматическая эскалация не отменяются после смены имени или enabled=False.

## Администрирование

Админ-панель защищена HTTP Basic по HTTPS. Runtime читает ADMIN_LOGIN и ADMIN_PASSWORD из окружения (локально из неотслеживаемого .env). Пустые/отсутствующие настройки закрывают только административные ручки с 503 auth_not_configured. Нет или неверны credentials — 401 с WWW-Authenticate. Сравнение секретов выполняется без утечек через логи; реальные значения не входят в DTO и репозиторий.

После успешной проверки каждого административного запроса HTTP-адаптер создаёт Principal(login=ADMIN_LOGIN). У единственной статичной учётной записи есть права управления списком username, просмотра списка тикетов/метрик, ответа от имени «Оператор» и закрытия тикета. Telegram-учётная запись администратора не требуется. Principal не принимается из JSON, query или публичной формы. Для изменяющих административных запросов проверяется Origin на адрес панели (защита от CSRF при credentials браузера); отдельной cookie-сессии в первом срезе нет.

Изменение enabled и регистрация синхронизируются по нормализованному username, включая отсутствующую строку (общая блокировка ключа); слот отдельно сериализуется по user_id. Общий порядок блокировок: username, затем user_id. Если отзыв закоммичен первым, новый вопрос получает denied; иначе принятый вопрос завершается.

## Тикеты по ссылке

`GET /tickets/{case_id}` и `POST /tickets/{case_id}/messages` публичны: любой посетитель ссылки читает созданный тикет и пишет без входа. Реплика имеет author_role=visitor, без подтверждённого имени и без привязки к Telegram User ID. Только open принимает новые сообщения; closed доступен для чтения. case_id генерируется случайным UUIDv4, общего публичного списка тикетов нет.

Оператор пишет через отдельный административный маршрут после проверки env-credentials. Админ-панель может закрывать тикеты; публичный посетитель не может закрывать их или управлять допусками. Публичная ссылка и история намеренно не ограничены владельцем Telegram-вопроса. Бот всё равно проверяет список разрешённых username для новых входящих вопросов и действий Support.
