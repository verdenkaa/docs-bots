## Запуск

Поднимаем один брокер с отдельным томом. Runtime объявляет три долговечные очереди. Для первого среза Queue Relay может публиковать в стандартный exchange с именем очереди как ключом маршрутизации. Сообщения публикуем с сохранением на диске. [Очереди RabbitMQ](https://www.rabbitmq.com/docs/queues) · [Стандартный exchange](https://www.rabbitmq.com/docs/exchanges#default-exchange)

| Очередь | Кто ставит работу | Кто читает | Ссылка в сообщении |
| --- | --- | --- | --- |
| `rag.questions` | RAG API | RAG Core | `request_id` сохранённого вопроса. |
| `rag.results` | RAG Core | RAG API | `request_id` сохранённого результата. |
| `ingestion.jobs` | Ingestion Gateway | Ingestion Worker | `job_id` равен `revision_id` строки с заданием. |

## Структура сообщения

Свойство AMQP `message_id` равно идентификатору записи outbox. Тело с типом `application/json` содержит номер запроса или UUID задания. По нему получатель читает запись в PostgreSQL. Очередь определяет назначение уведомления.

Для `rag.questions` и `rag.results` используем [DTO `RequestRef`](../../rag-core/contracts.md#очередь-и-готовый-результат).

```json
{ "request_id": 1042 }
```

Для `ingestion.jobs`:

```json
{ "job_id": "bb32ecbf-082b-4497-a41f-4b61aa56a139" }
```

## Подтверждения и восстановление

1. Владелец этапа сохраняет работу и outbox в PostgreSQL. [Queue Relay](../queue-relay.md) читает записи, для которых наступило время публикации.
2. Relay публикует с publisher confirms и флагом `mandatory`. Отмечает отправку после подтверждения, если брокер не вернул сообщение как немаршрутизированное. Если подтверждение потерялось, он может опубликовать ту же запись с тем же `message_id`.
3. Получатель проверяет состояние запроса или задания по ссылке. Подтверждает сообщение вручную после сохранения итога либо ожидания или повтора. Если уведомление пришло повторно, состояние этапа определяет, нужна ли работа.
4. При новом запланированном повторе появляется новая запись outbox с тем же идентификатором работы. Время повтора хранится в PostgreSQL. При потере содержимого очередей владельцы этапов восстанавливают из базы только нужные уведомления.

Prefetch ограничивает число сообщений, которые каждый потребитель держит до подтверждения. Порядок внутри чата контролируем по состоянию PostgreSQL. Для `ingestion.jobs` запускаем одного потребителя с `prefetch=1`.
