RAG API — модуль в контейнере `core`. Он владеет Telegram-транспортом, приёмом, доставкой, допуском и поддержкой. Внутренние компоненты **Access** и **Support** не требуют отдельных модулей верхнего уровня или собственных контейнеров. ORM и атомарные операции PostgreSQL находятся в Runtime.

| Часть | Что делает | Граница |
| --- | --- | --- |
| Приём Telegram | Проверяет источник webhook, разбирает сообщения и управляющие действия, распознаёт повторы. | Только личные чаты; группы/каналы не создают вопросы. |
| Access | Проверяет Telegram User ID и управляет допуском; согласует один активный вопрос сотрудника через Runtime. | Не равен документной ролевой модели. [Подробнее](./access.md) |
| Связь с Core | Сохраняет вход и outbox для `rag.questions`, получает готовые доставки из `rag.results`. | Не выполняет поиск и генерацию в webhook. |
| Доставка | Оформляет готовый Markdown, получает изображения по ID, отправляет статусы и ссылки на тикеты. | Общие ограничения отправки и сохранённый прогресс частей. |
| Support | Обрабатывает недовольство, просьбы о человеке, ожидание, подтверждение и тикеты. | Диалог с оператором — в web-системе. [Подробнее](./support.md) |
| HTTP-интерфейс | Служебные проверки, HTML-заглушка источника, будущие страницы тикетов/админ-панели. | Способ входа в web-систему ещё не выбран. |

## Какие входы обрабатываем

| Вход | Действие |
| --- | --- |
| Текст допущенного сотрудника | Зарегистрировать самостоятельный вопрос, если активного нет. |
| Изображение пользователя и подпись | Сохранить устойчивую ссылку на файл и подпись. Core получает байты через Runtime и выполняет только OCR через Model Gateway. |
| Новый вопрос при занятом слоте | Не ставить в очередь; сообщить об обработке предыдущего и подтвердить update. |
| Недовольство ответом / просьба о человеке после ответа | Передать в Support с привязкой к конкретному вопросу/ответу; показать кнопку вызова. |
| Нажатие кнопки / подтверждение помощи | Обработать как управляющее действие Support, без нового RAG-вопроса. |
| Группа, канал или неподдерживаемое сообщение | Корректно пропустить без регистрации вопроса и вызова моделей. |

Каждое управляющее действие проверяет пользователя и принадлежность обращения. Повтор update или нажатия не создаёт новое ожидание/тикет. Формат callback и привязка к ответу закреплены в [DTO](./contracts.md).

## Способ приёма {#два-способа-приёма}

Для MVP выбран **webhook**. Telegram получает подтверждение после надёжной регистрации либо окончательного бизнес-решения о пропуске/отказе. Бот использует `TELEGRAM_BOT_TOKEN` из окружения `core`; секрет входящего webhook задаётся отдельно.

Long polling остаётся возможным адаптером для другого профиля запуска; одновременно с webhook не используется. Он не меняет бизнес-логику приёма и доставки. [Текущий HTTP-контракт webhook](../endpoints/telegram-webhook.md)

## Источники и изображения

И новый, и кешированный ответ содержит готовый Markdown, источники, описания и ID изображений. RAG API получает файлы из S3 через Runtime, не обращаясь к исходному документу. Формат Markdown ответа преобразуется в поддерживаемое Telegram представление; исходная разметка не отправляется вслепую. Неизвестные ID не превращаются в произвольные загрузки по URL.

Ссылка на источник ведёт на простую HTML-заглушку RAG API с текстом «Тут должен быть хостинг документа „Название документа“». Метаданные названия и идентичности сохранены после Ingestion и присутствуют в чанках. Оригинал и раздел документа страница не показывает; отдельный сайт исходников не нужен. [HTTP-контракт страницы](../endpoints/source-page.md) оформлен по общему шаблону.

## Карта контрактов {#contract-alignment}

- Приём: User ID, личный чат, текст/изображение/подпись, время приёма, исход занятости и управляющие действия.
- Core: происхождение входа OCR, устойчивое различение ответа, отсутствия подтверждений, отказа и технического сбоя; намерение Support.
- Доставка: самостоятельное уведомление, ответ с изображениями, порядок и прогресс частей; rag.questions несёт RequestRef, rag.results — DeliveryRef.
- Runtime: допуски, активный слот, метаданные входящего файла, история, ожидания, тикеты и исходы доставок.
- HTTP: страница источника и web-система тикетов/администрирования с Principal из будущего web-входа; до подключения входа ручки закрыты.
