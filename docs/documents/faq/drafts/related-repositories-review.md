# Что взять из смежных репозиториев для корпоративного Telegram-бота

В [описании кейса](./case.md) бот отвечает по актуальной документации проекта. [Candidate Architecture v1](./candidate_architecture_v1_rag_bot.md) уже описывает версии корпуса, проверяемые ссылки, отказ при нехватке данных, шлюз Telegram и кеш. Ниже — способы реализовать и проверить отдельные части этой схемы по коду смежных проектов. Решения по стеку и требованиям остаются предметом согласования после получения полного задания.

Проверены 16 репозиториев через GitHub по снимкам основных веток. Ссылки закреплены за коммитами. Это статический разбор исходников и документации. Приложения не запускались, авторские метрики не перепроверялись.

Первый рабочий срез стоит собрать вокруг цепочки «публикация ревизии → поиск → проверяемая ссылка → Telegram». Из найденного к нему напрямую подходят локаторы источников из `RAG_for_study`, этапы индексации из `YamAISdelali` и диагностика полноты поиска из `avito-nlp`. Singleflight стоит проверить отдельно после появления сквозного сценария. Согласованность публикации, прав доступа и отправки ответа остаётся собственной задачей Candidate v1.

## Что взять в первую очередь

### 1. Измерять полноту пула до ранжирования

В `avito-nlp` BM25 отдельно индексирует поля объявления. Выдачи объединяются по рангам через RRF, а косинусное сходство эмбеддингов используется как признак второго этапа. README отдельно показывает, какой результат дал бы идеальный ранкер на фиксированном пуле. Если нужного кандидата нет в пуле, усложнять ранкер бесполезно. [src/bm25.py](https://github.com/b3ss0n/avito-nlp/blob/d3c987cd066ae83778ca84e2f9c7f150b4b6fdab/src/bm25.py#L59-L96) · [src/candidates.py](https://github.com/b3ss0n/avito-nlp/blob/d3c987cd066ae83778ca84e2f9c7f150b4b6fdab/src/candidates.py#L89-L116) · [src/ranker.py](https://github.com/b3ss0n/avito-nlp/blob/d3c987cd066ae83778ca84e2f9c7f150b4b6fdab/src/ranker.py#L35-L46) · [разбор качества](https://github.com/b3ss0n/avito-nlp/blob/d3c987cd066ae83778ca84e2f9c7f150b4b6fdab/README.md#L30-L47)

**Для нашего Retrieval.** Индексировать коды ошибок, имена параметров, версии и номера пунктов отдельно от обычного текста. Сравнить на одних вопросах dense, lexical и dense + lexical с RRF. Для каждого пути применить одинаковые ограничения по проекту, правам и релизу до отбора кандидатов. Для легитимной области доступа можно использовать приоритет конкретного продукта или раздела, если он известен из вопроса. Отдельно измерить `Evidence Recall@K` до ранкера и `Evidence Recall@k` после него. Для вопросов из нескольких документов считать долю запросов, где найдены **все** нужные фрагменты. Отчёт разбить по точным идентификаторам, перефразировкам и конфликтам версий. Ранкер имеет смысл добавлять, когда доказательства уже регулярно попадают в пул, но выпадают при обрезке контекста. [разбиение и Recall@k](https://github.com/b3ss0n/avito-nlp/blob/d3c987cd066ae83778ca84e2f9c7f150b4b6fdab/src/validation.py#L37-L93)

`simple-open-webui` показывает вторую вариацию. Заголовок и путь секции участвуют в BM25, а исходный текст остаётся доступным для ответа. Векторная и лексическая выдачи объединяются с дедупликацией, затем вызывается reranker. Для нашего корпуса стоит проверить отдельные поля «название документа», «заголовки» и «текст». Дедупликацию при объединении выдач лучше привязать к `chunk_id` в зафиксированной ревизии. Одинаковый текст может иметь разное происхождение, права и срок действия. В примере BM25 строится внутри запроса, а параметр `filter` в `QdrantClient.search()` не передаётся в `query_points()`. Наш поисковый путь должен использовать готовый индекс и явно передавать ограничения в Qdrant. [гибридный поиск](https://github.com/KroJIak/simple-open-webui/blob/02dc3e689ceac915a870b373318b99c029ddf603/backend/open_webui/retrieval/utils.py#L307-L425) · [адаптер Qdrant](https://github.com/KroJIak/simple-open-webui/blob/02dc3e689ceac915a870b373318b99c029ddf603/backend/open_webui/retrieval/vector/dbs/qdrant.py#L144-L166)

### 2. Сохранить адрес доказательства от загрузки до Telegram

`RAG_for_study` добавляет к чанку имя файла и метаданные страницы или листа. Генератор передаёт модели ID чанков. В ответе чата источниками становятся все результаты retrieval, а токен чата проверяется для истории уже после поиска. Это полезный шаблон для отображения контекста, который надо усилить для корпоративной выдачи. [метаданные чанка](https://github.com/warnerry/RAG_for_study/blob/1e6c4719770b544afb1b76403e94febed1f606bc/backend/app/services/documents/chunker.py#L22-L45) · [формат контекста](https://github.com/warnerry/RAG_for_study/blob/1e6c4719770b544afb1b76403e94febed1f606bc/backend/app/services/rag/prompts.py#L26-L36) · [ответ чата](https://github.com/warnerry/RAG_for_study/blob/1e6c4719770b544afb1b76403e94febed1f606bc/backend/app/api/chat.py#L20-L61)

**Для нашего Answer Core.** На ingest хранить `doc_id`, `revision_id`, `chunk_id` и локатор (страница, раздел или лист). В ответе модели передавать ID доказательств по тезисам. Приложение проверяет, что ID принадлежат выданному разрешённому контексту, и само строит ссылки. Принадлежность ID подтверждает происхождение ссылки, поэтому поддержку тезиса нужно оценивать отдельно на эталонных вопросах. `hackathon-vtb-more` даёт компактный пример вызова `AsyncOpenAI.responses.parse` с Pydantic-схемой. Для нашего контракта полезны отдельные исходы «ответ с источниками», «недостаточно данных» и «зависимость недоступна». [структурированный вывод](https://github.com/one-zero-eight/hackathon-vtb-more/blob/5b794cc8bf529449743d1978d7f00478682922f8/backend/src/services/ai/assessor.py#L50-L64)

**Проверка.** Загрузить fixture с двумя похожими разделами, задать вопрос и убедиться, что ссылка ведёт к нужной странице и тезис подтверждается именно ей. Повторить после публикации исправленного документа. Сценарий `health → upload → process → chat` из учебного проекта пригоден как основа, если дополнить его проверками кода ответа, цитаты и версии. [smoke-сценарий](https://github.com/warnerry/RAG_for_study/blob/1e6c4719770b544afb1b76403e94febed1f606bc/scripts/smoke_test.sh#L13-L31)

### 3. Показать этапы индексации и отдельно подтвердить публикацию

`YamAISdelali` разделяет загрузку, парсинг, индексацию и завершение и отдаёт прогресс по идентификатору задачи. Состояния хранятся в памяти. В этой цепочке OCR-фолбэк вызывает заглушку, возвращающую пустую строку, а парсинг передаёт в RAG плоский текст. Шаблон полезен для статусов и диагностики, реализацию извлечения нужно проверять отдельно на нашем корпусе. [этапы ingestion](https://github.com/ssoberin/YamAISdelali/blob/f57ec348a3854cd9aed10c4abae16c4e0582a76e/src/ingestion/pipeline.py#L93-L152) · [статусы](https://github.com/ssoberin/YamAISdelali/blob/f57ec348a3854cd9aed10c4abae16c4e0582a76e/src/ingestion/status_tracker.py#L37-L95) · [OCR в цепочке](https://github.com/ssoberin/YamAISdelali/blob/f57ec348a3854cd9aed10c4abae16c4e0582a76e/src/ingestion/pipeline.py#L231-L276)

**Для нашего Ingestion Worker.** Разделить `indexed` и `published`. Парсер сохраняет блоки с локаторами. Воркер готовит новую ревизию, проверяет, что у неё есть пригодные чанки, и только затем публикует её через авторитетный указатель из Candidate v1. Ошибка до публикации оставляет читателям последнюю успешно опубликованную ревизию согласно согласованной политике актуальности. Долговременные статусы и ключ идемпотентности позволяют повторить задачу после перезапуска. Сценарий защиты должен показывать момент переключения версии и поведение при сбое посередине.

В том же `YamAISdelali` полезна отдельная модель статуса нормативного документа с заменой и датами действия. Для нас это применимо, если заказчик даст реестр со статусами. Код использует локальный справочник и после точного поиска допускает частичное совпадение по номеру. Для версии документа с явно указанным годом это способ выдать сведения о другом издании. Явное несовпадение версии или конфликт источников стоит показывать пользователю, а подбор замены опирать на метаданные реестра. [поиск статуса и замены](https://github.com/ssoberin/YamAISdelali/blob/f57ec348a3854cd9aed10c4abae16c4e0582a76e/src/mcp_tools/gost_validator_tool/gost_database.py#L138-L195)

### 4. Объединять одинаковые запросы, пока выполняется первый

`one-zero-eight/monorepo` содержит `SingleFlight`. Одновременные вызовы с одинаковым ключом ждут один `asyncio.Task`. Тесты покрывают одинаковые и разные ключи и новый запуск после ошибки. В реализации ожидание идёт через прямой `await task`, поэтому при переносе отдельно проверить, что отмена одного ожидающего клиента не отменяет общий вызов и не удаляет его запись преждевременно. Эта реализация работает в пределах одного процесса. [singleflight](https://github.com/one-zero-eight/monorepo/blob/742abde2aae19a0b7c1c02404f45e8deeb287b3b/src/room_booking/modules/bookings/single_flight.py#L30-L54) · [конкурентные запросы](https://github.com/one-zero-eight/monorepo/blob/742abde2aae19a0b7c1c02404f45e8deeb287b3b/tests/room_booking/test_single_flight.py#L29-L66) · [ошибка и повтор](https://github.com/one-zero-eight/monorepo/blob/742abde2aae19a0b7c1c02404f45e8deeb287b3b/tests/room_booking/test_single_flight.py#L107-L133)

**Для нашего RAG API.** Начать с exact singleflight в одном процессе. Ключ включает вопрос, эффективную область доступа, поколение корпуса и влияющий на ответ контекст. Результат можно разделять между ожидающими только при совпадении всех составляющих. Доставку в Telegram и финальную проверку права выполнять для каждого запроса отдельно. Проверить, что N одновременных эквивалентных запросов вызывают один LLM-вызов, а смена релиза, прав или истории создаёт отдельную работу. Отдельно измерить p95 для уникальных вопросов, одновременных повторов и попаданий в готовый кеш. Межпроцессная координация имеет смысл после проверки сценария с несколькими репликами.

## План проверки на первом рабочем срезе

1. **Пройти путь от документа до ответа.** Загрузить один документ, опубликовать ревизию, задать вопрос в Telegram, открыть точную страницу или раздел. Повторить с вопросом, которого нет в корпусе, и с недоступной зависимостью. Каждый исход должен быть различим.
2. **Обновить один факт при работающем боте.** В новой ревизии поменять значение в инструкции, повторить вопрос после публикации, проверить текст и ссылку. Отдельно прервать подготовку ревизии и убедиться, что читателю не видна частично загруженная версия. Политику запроса, начатого до публикации, проверить отдельным сценарием по согласованному контракту.
3. **Прогнать одинаковые запросы через три поисковых режима.** Взять точные коды, перефразировки, вопросы с несколькими источниками и вопросы без ответа. Сравнить полноту пула, качество финальных цитат, долю ложных ответов и p95. Использовать одни и те же версии корпуса, модели и промпта.
4. **Проверить повторы и доставку.** Одновременно отправить одинаковые вопросы в одном scope, затем в разных scope. Зафиксировать число вызовов модели, p95 и исходы доставки. Повторить с таймаутом одного клиента и повторным `update_id`.
