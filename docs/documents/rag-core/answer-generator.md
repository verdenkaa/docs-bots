## Как собирается ответ

1. Адаптер формирует контекст в пределах бюджета модели. Вопрос и тексты фрагментов передаёт отдельно от системных инструкций. Если бюджет не позволяет включить ни одного фрагмента, сообщает о технической ошибке. В MVP Runtime выбирает провайдера, допущенного для общего корпуса. Если кейс задаст правила передачи на уровне отдельных документов, добавляем проверку до отправки контекста.
2. Адаптер назначает вошедшим в контекст чанкам метки `S1`, `S2` и хранит соответствие меток и `chunk_id` на время вызова. Для ответа модель заполняет `kind: "answered"`, `answer_text` и список меток `citations`. Для нехватки данных возвращает `kind: "insufficient_evidence"`.
3. Адаптер проверяет структуру результата и переводит метки в `cited_chunk_ids`. Ответ без текста, без ссылочных меток или с неизвестной меткой считается ошибкой формата. Core собирает источники по ID, убирая повторы в порядке первого упоминания. Ссылки и локаторы берёт из метаданных чанков.

Для MVP предлагаем отдавать цельный текст и отдельный список источников. RAG API отвечает за оформление списка в Telegram. Проверка меток подтверждает, что источник входил в контекст. Фактическая опора ответа на источники остаётся задачей промпта. [Итоги синка, D-05 и Q-10](../faq/drafts/architecture-team-sync.md)
