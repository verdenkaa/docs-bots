# Архитектура RAG: два независимых исследования

> **Статус: черновик для обсуждения, не решение команды.** Обновлено: 1 ноября 2026 года. Полное ТЗ, корпус БАРС Груп, доступные модели, аппаратные ресурсы и критерии жюри пока неизвестны. Численные ориентиры из отчётов не являются измеренными характеристиками системы.

## За две минуты

**Вывод:** обе работы рекомендуют модульный Python-бэкенд, управляемую публикацию документов, retrieval по разрешённым источникам, проверяемые цитаты, отказ при недостатке доказательств, ограничение очередей и **exact-кеш**, а не безусловный semantic answer cache. **Расходятся** они по выбору поискового хранилища и строгости актуальности на момент отправки.

| | Исследование №1 (27.10) | Независимое №2 (01.11) |
| --- | --- | --- |
| Основной вариант | PostgreSQL + Qdrant; Redis как необязательный ускоритель | PostgreSQL + pgvector + FTS; exact-кеш без обязательного Redis |
| Поиск | Dense + lexical/sparse, RRF; Qdrant-native hybrid | Dense + PostgreSQL FTS/identifier path; fusion в приложении |
| Публикация | Immutable физическая коллекция Qdrant, SQL pointer и монотонный epoch | Ревизии, chunks, индексы и pointer транзакционно в PostgreSQL |
| Актуальность | Snapshot закрепляется после очереди; начатый ранее ответ может завершиться по старой версии **с маркировкой** | Строгая финальная проверка поколения/известных pending changes; повтор или контролируемый отказ |
| Повторные вопросы | Redis exact answer cache после P0 | Exact response cache + singleflight |
| Уникальные вопросы | Короткий путь: компактный evidence, один основной LLM call, ограниченные стадии | То же; отдельное внимание общим префиксам и long-context, когда подходит корпус |
| Главный аргумент | Специализированные retrieval-примитивы и разделение зон разработки | Одна транзакционная граница и меньший интеграционный риск |

**Не надо голосовать за названия БД.** Сначала уточнить требования и провести короткую одинаковую проверку качества, частоты обновлений и уникальных запросов.

## Что предлагаем обсудить

### 1. Минимальный продукт, который должен работать независимо от архитектуры

1. Загрузка документов и извлечение текста со структурой, страницами/разделами и provenance.
2. Вопрос Telegram → разрешённый retrieval → короткий ответ с источниками или обоснованный отказ.
3. Контролируемое обновление факта; новый запрос не должен смешивать версии.
4. Проверка источников и прав **до контекста модели**, а также на выдаче.
5. Измерение повторного и уникального запроса отдельно: качество, p50/p95, tokens, failures.
6. Один воспроизводимый запуск и понятный план деградации при API/DB ошибках.

### 2. Пять решений, которые пока открыты

| Решение | Основные вопросы | Как закрыть |
| --- | --- | --- |
| pgvector/FTS или Qdrant | Обязателен ли Qdrant по ТЗ? Реальный объём и язык корпуса? | Одинаковые retrieval fixtures, Recall@k, p95, нагрузка и обновление |
| Freshness contract | Допускается ли помеченный старый in-flight ответ после commit? Нужно ли блокировать источник после обнаруженной правки? | Согласовать SLA с организатором и проиграть гонку publish vs send |
| Exact cache | Нужен ли внешний Redis при одной инстанции? Что за фактическая доля повторов? | Повторный workload, проверка ключей scope/revision/history |
| Выбор LLM | Разрешён ли внешний API и передача корпоративного текста, какие квоты? | Live connectivity/quota smoke; gold set correctness + latency/cost |
| Long-context режим | Умещается ли разрешённый корпус в бюджет контекста? | Cold unique eval и проверки потерянных/конфликтных фактов |

### 3. Отдельно: четыре цели, четыре независимые проверки

| Цель | Что измеряем | Ошибка интерпретации |
| --- | --- | --- |
| Качество | Evidence Recall@k, correctness, citation support, refusal | «Есть ссылка» не означает «ссылка подтверждает тезис» |
| Актуальность | Source-detection lag, publish lag, stale dispatch, ревизии | Атомарный pointer не означает мгновенное знание о правке в источнике |
| Повторные вопросы | p50/p95 exact hits, actual hit ratio, права и версия | Backend cache RPS не равно Telegram goodput |
| Новые вопросы | p50/p95 fully unique misses, токены, LLM quota, useful goodput | Прогретый exact answer cache не ускоряет новый запрос |

## Архитектурный скелет без выбора поискового движка

~~~mermaid
flowchart TB
  T[Telegram] --> G[Gateway: identity and bounded admission]
  G --> V[Pin knowledge version and scope]
  V --> C{Exact answer reuse}
  C -->|hit| S[Validate and send]
  C -->|miss| R[Retriever: candidate search]
  R --> E[Evidence selection and citation ids]
  E --> M[One grounded model call]
  M --> S
  I[Ingestion worker] --> P[Prepare and validate new revision]
  P --> A[Publish via authoritative control state]
  A --> V
~~~

Это **контракт компонентов**, а не утверждённое физическое размещение. В №1 retrieval использует Qdrant и pointer в PostgreSQL; в №2 вариант A хранит оба слоя в PostgreSQL.

## Решения по итогам обсуждения

Пока **ничего не принято**. Предлагаемый формат командного решения:

- **Решение:** что выбираем и для какой задачи.
- **Основание:** требование, эксперимент или инженерный компромисс.
- **Контрпример:** где подход проиграет.
- **Fallback:** что делаем, если API/корпус/сроки изменятся.
- **Статус:** proposed / accepted / rejected / superseded.
