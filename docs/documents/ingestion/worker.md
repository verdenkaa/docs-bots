Вход из RabbitMQ — [`handle_ingestion_job(event) -> ConsumeDecision`](./entrypoints.md#handle-ingestion-job). Адаптер читает `ingestion.jobs`, проверяет сообщение и передаёт UUID задания. В MVP один потребитель выполняет по одному заданию за раз с `prefetch=1`.

## От задания до публикации

1. **Взять задание.** [`claim_ingestion_job`](../infrastructure/postgresql/ingestion.md#claim-ingestion-job) возвращает ID документа, ключ временной загрузки, номер и срок попытки. В пределах одного документа редакции берём в порядке регистрации. Пока редакция ждёт повтора, можно выполнять задания других документов. Если номер попытки уже превысил лимит, фиксируем сбой до чтения файла.

2. **Прочитать готовый Markdown и снимок.** open_staged_upload даёт converted.md, название и ImageRef. load_prepared_revision возвращает ранее сохранённый набор либо None. При существующем наборе не запускаем повторную конвертацию/разбиение/генерацию.
3. **Подготовить набор, если его ещё нет.** prepare_chunks делит Markdown по разделам, сохраняя неделимые плейсхолдеры. embed_texts(texts, "document", timeout_s=...) даёт по вектору на чанк. Worker собирает ChunkPoint; профили и размерности сверяет с индексом.
4. **Сформировать примеры темы.** Worker задаёт системный промпт и структурированный JSON со списком самостоятельных вопросов только по содержимому редакции. Через Model Gateway.generate обрабатывает документ порциями в пределах контекста, не обрезая его молча; проверяет completed, формат, непустые вопросы, убирает повторы в устойчивом порядке. Если подтверждённых примеров не получилось — ошибка подготовки, не публикация редакции без темы. Вопросы кодируются embed_texts(..., "query", timeout_s=...). Список TopicPoint имеет детерминированные ID.
5. **Закрепить подготовку.** store_prepared_revision сохраняет полные ChunkPoint/TopicPoint и версии подготовки/embedding до первой записи Qdrant. Повтор читает те же тексты, ID, векторы и примеры. При неизвестном исходе сохранения сначала перечитываем снимок.
6. **Записать и опубликовать.** begin_revision_write(attempt, len(points), len(topic_points)) сохраняет оба ожидаемых числа и общий qdrant_write_pending. Только после True выполняем write_revision_points, затем write_topic_points, verify_revision_points и verify_topic_points. При полном подтверждении publish_revision снимает признак и атомарно переключает поколение. Любой неизвестный исход записи прекращает дальнейшие записи/публикацию до сверки.

## Срок попытки и остановка процесса

- PostgreSQL задаёт `deadline_at` при взятии задания и сверяет срок при каждом переходе. Runtime запускает процесс потребителя под отдельным супервизором. Потребитель включает у него короткий таймер перед взятием задания. После успешного взятия заменяет этот таймер оставшимся бюджетом попытки до начала обработки. Супервизор отсчитывает бюджет монотонными часами.
- Каждый вызов парсера, модели, PostgreSQL и Qdrant получает свой лимит в пределах остатка общего бюджета. Перед блокирующим шагом потребитель передаёт супервизору и срок этого шага. Сетевые адаптеры ограничивают соединение и ожидание ответа. Для пакетной записи ограничиваем и весь вызов, и каждый пакет. Лимит RabbitMQ на ожидание подтверждения настраиваем с запасом относительно бюджета попытки и времени остановки процесса.
- Потребитель и дочерние процессы парсера работают в одной отдельной группе Linux. При зависании супервизор посылает группе `SIGTERM`, а после короткого срока на остановку — `SIGKILL` оставшимся процессам. Он пишет причину, `job_id` и `attempt_no`, если задание уже взято, и запускает нового потребителя после подтверждённого выхода старой группы. При падении супервизора Runtime перезапускает контейнер `worker`, дождавшись остановки прежнего контейнера. RabbitMQ возвращает неподтверждённое сообщение после закрытия соединения. Прерывание задачи Python само по себе не останавливает блокирующий код или уже отправленный запрос. [Отмена задач Python](https://docs.python.org/3/library/asyncio-task.html#asyncio.wait_for)

### Запись в Qdrant с неизвестным исходом

Если после `begin_revision_write` процесс оборвался или Qdrant не подтвердил применение пакета, признак остаётся в PostgreSQL. При неизвестном коммите публикации повторное уведомление сначала проверяет сохранённое состояние через `claim_ingestion_job`. При состоявшейся публикации признак уже снят и задание завершено. Пока признак установлен, редакция остаётся невидимой и заблокирована для повтора и удаления. Её рабочий файл сохраняется. Очередь продолжает обрабатывать другие документы. По `job_id` и `attempt_no` пишем событие для оператора.

В MVP оператор разбирает такие записи в окно обслуживания по [процедуре сверки Qdrant](../infrastructure/qdrant/index.md#сверка-незавершённых-записей). Она исключает старые операции записи, подтверждает отсутствие частичных точек и снимает блокировку в PostgreSQL. После этого Runtime повторно ставит задание в очередь. Если лимит попыток исчерпан, Worker фиксирует сбой без новой записи точек.


## Подготовка текста

- Worker читает только готовый Markdown; извлечение DOCX/PDF/изображений и OCR/VLM принадлежат Gateway/Converter.
- Первично режем по разделам и абзацам; крупные части — с настраиваемым перекрытием. Порядок, заголовки, URL и операторы сохраняются. Плейсхолдер с ID/описанием не дробим. Блок сверх бюджета даёт chunk_too_large, а не молчаливое обрезание.
- Для каждого чанка images содержит только использованные плейсхолдеры из манифеста. Имя источника берём из UploadSource.filename; source_url=None. Внутренний локатор необязателен: пользовательская ссылка ведёт на документ целиком.
- Нет пригодного содержимого — ошибка задания. Окончательно неудачная редакция не подменяет опубликованную.
- Версия правил разбиения/генерации и embedding-профиль закреплены в PreparedRevision. Смена конфигурации выполняется после завершения/разбора старых заданий, а не в середине повтора.

## Повторы и подтверждение очереди

| Ситуация | Действие Worker | Решение для RabbitMQ |
| --- | --- | --- |
| `claim_ingestion_job` вернул `None` | Задание отсутствует, уже взято, завершено или ещё ждёт своего времени или предыдущей редакции. Готовую работу повторно поставит PostgreSQL через outbox. | `ack` |
| Временный сбой до начала записи, например сбой доступа к тому или `StepError` с `retryable=True` | Если остались попытки, `schedule_ingestion_retry` фиксирует срок и новую запись outbox. Повтор читает тот же Markdown и сохранённый PreparedRevision; пишет те же точки обоих наборов. | `ack` после сохранения |
| До начала записи обнаружен окончательный сбой или попытки исчерпаны | `fail_ingestion_job` фиксирует сбой. Например, нет файла или текста, либо шаг вернул `StepError` с `retryable=False`. Причину пишем в диагностику с `job_id` и номером попытки. Предыдущая опубликованная редакция сохраняется. | `ack` после сохранения |
| Публикация завершилась | Новое поколение зафиксировано. Уборка идёт отдельно. | `ack` |
| Истёк срок попытки | Супервизор останавливает зависший процесс. Новый потребитель может взять истёкшую попытку без признака незавершённой записи. | Брокер возвращает неподтверждённое сообщение после остановки. Если обработчик успел завершиться и PostgreSQL подтвердил потерю права на переход, допустим `ack`. |
| После начала записи PostgreSQL подтвердил, что признак ещё установлен | Записываем событие для оператора и ждём сверки. Новое уведомление создаётся после снятия блокировки. | `ack`, если обработчик ещё работает |
| Состояние или итог коммита PostgreSQL неизвестен | Следующее уведомление повторно проверит запись. Если публикация состоялась, повтор её не выполнит. | `retry_broker` |

После рестарта Runtime вызывает [`recover_pending_work("ingestion.jobs", limit)`](../infrastructure/postgresql/outbox.md#recover-pending-work). Он также запускает эту проверку периодически, в том числе когда RabbitMQ повторно доставил уведомление до истечения предыдущей попытки и получил `ack`. Восстановление создаёт уведомления для готовых заданий и истёкших попыток без признака незавершённой записи. Перед новой записью Worker заново берёт задание по UUID.

## Очистка после обработки

| Что очищаем | Когда | Порядок |
| --- | --- | --- |
| Временный Markdown, манифест и PreparedRevision | Задание опубликовано либо окончательно завершилось и qdrant_write_pending=false. | `list_finished_staging` → `remove_staged_upload` → `clear_staging_ref`. |
| Чанки и примеры неудачной редакции | Сбой зафиксирован и признак незавершённой записи снят. | `claim_revision_cleanup` → `delete_revision_points` → `finish_revision_cleanup`. |
| Чанки и примеры прежней опубликованной редакции | Её интервал видимости закрыт и ни один запрос её не удерживает. | Та же последовательность очистки точек по `revision_id`. |

При рестарте Worker подбирает незавершённую очистку. Удаление уже отсутствующего файла или точек считается успешным. Если файл удалён, а ссылка осталась, следующий проход очищает ссылку после повторной проверки. [Контракты очистки](../infrastructure/postgresql/cleanup.md)

## Проверка первого сквозного сценария

1. Загрузить небольшой документ с таблицей и изображением. Сверить `job_id` в outbox, в сообщении RabbitMQ и в строке редакции. До подтверждения проверить S3 и converted.md; после публикации — оба набора точек, source_name, image_id и HTML-заглушку. Оригинала в томе/S3 быть не должно.
2. Загрузить замену с тем же `document_id`. До коммита новой редакции Searcher видит старую. После коммита новый запрос получает новую, а запрос с закреплённым поколением может закончить по старой.
3. Заблокировать разбиение/локальный исполнитель Worker (конвертер отдельно проверяется до accepted). Проверить завершение старого процесса по сроку, возврат неподтверждённого сообщения и обработку следующего задания.
4. Прервать Worker после отправки пакета Qdrant и до подтверждения. Проверить, что после рестарта повтор и очистка заблокированы для этой редакции, а остальные документы обрабатываются. После сверки повтор использует тот же набор ID. Отдельно прервать Worker после коммита публикации до `ack` и проверить, что повтор видит завершённую публикацию.
5. Загрузить документ без пригодного Markdown/описаний либо проверить пустой результат prepare_chunks. Задание завершается ошибкой, поколение корпуса и ответы по прежней редакции сохраняются.

6. Оборвать Worker после store_prepared_revision: повтор не запускает генерацию вопросов заново. Оборвать между двумя индексами: новое поколение не публикуется, очистка ждёт сверки обоих наборов.
