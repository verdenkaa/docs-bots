Корпоративный Telegram-бот отвечает сотрудникам по общей документации: кратко, с источниками и нужными изображениями прямо в чате. Вопросы самостоятельные, без контекста предыдущих ответов и уточняющего диалога бота. Если подтверждений недостаточно, создаётся обращение в собственную простую тикет-систему; разговор с оператором идёт там. Пользовательского Mini App нет.

Основа — [итоги синка](../faq/drafts/architecture-team-sync.md), затем [решения кейса](../faq/case-checklist.md) и более поздние уточнения команды. При расхождении приоритет у последнего решения. Этот раздел задаёт поведение и владельцев, а не формат функций.

## Контейнеры и очереди

**Вопросы и поддержка.** Внутренние шаги Core перечислены в таблице модулей ниже.

~~~mermaid

  TG["Telegram"]
  subgraph CORE["Контейнер core"]
    subgraph APIMODULE["Модуль RAG API"]
      API["Telegram / HTTP / доставка"]

      S["Support · тикеты<br/>и админ-панель"]
      API --> AC
    end

    C -->|"намерение эскалации"| S
  end
  subgraph MQ["RabbitMQ · через outbox и Queue Relay"]

  end
  EMP["Сотрудник / оператор / администратор"]
  TG <-->|"вопрос / текст / изображения"| API
  API --> Q1 --> C
  C --> Q2 --> API
  S -->|"уведомления"| Q2
  EMP <-->|"web-интерфейс"| S
~~~

**Загрузка и индексация.** Подготовка Markdown и изображений принадлежит Ingestion Gateway.

~~~mermaid
flowchart TB
  SRC["Источник документов"]
  IMG[("S3 · изображения")]
  subgraph WORKER["Контейнер worker"]
    IG["Ingestion Gateway"]
    CV["Document Converter<br/>подмодуль Gateway"]
    MD["Готовый Markdown<br/>описания и плейсхолдеры"]
    IW["Ingestion Worker"]
    IG --> CV --> MD
  end
  Q3[("RabbitMQ · ingestion.jobs")]
  IDX[("Qdrant · чанки и примеры")]
  PG[("PostgreSQL · публикация")]
  SRC -->|"документ"| IG
  CV -->|"изображения через Runtime"| IMG
  MD -->|"задание через outbox"| Q3 --> IW
  IW -->|"подготовить и проверить"| IDX
  IW -->|"переключить поколение"| PG
~~~

`core` и `worker` собираются из общей Python-кодовой базы. В `core` работают RAG API с компонентами Access/Support и отдельный оркестратор RAG Core; в `worker` — шлюз загрузки и последовательная индексация. Web-интерфейс Support может обслуживаться из `core`, отдельный контейнер для каждого модуля не требуется. Отдельный сайт исходных документов не поднимаем: HTML-заглушку источника отдаёт RAG API. S3 — внешнее либо собственное объектное хранилище. Развёртывание допустимо локально или в облаке.

Схемы показывают бизнес-маршруты. PostgreSQL хранит состояние и outbox, Qdrant — поисковые данные, Redis — Exact Cache; RAG API получает изображения из S3 по ID через [S3-адаптер Runtime](../infrastructure/s3.md). Владение вынесено в [данные и версии](./data-and-versions.md). Runtime собирает адаптеры и фоновые процессы, включая общий Queue Relay в `core` для всех трёх маршрутов. Model Gateway предоставляет вызовы локальных моделей/API; самостоятельный сервер моделей необязателен. [Очереди и доставка](./message-flow.md)

## Имена модулей

| Модуль или внутренний компонент | Ответственность |
| --- | --- |
| [RAG API](../telegram/index.md) | Приём Telegram webhook, допуск через Access, регистрация одного активного вопроса сотрудника, статусы ожидания, доставка текста/изображений и HTML-заглушка источника на уровне документа. |
| [RAG Core](../rag-core/index.md) | Оркестрация вопроса: OCR при необходимости, проверки, кеш, поиск, генерация; сохранение ответа либо намерения эскалации. Внутри — **Exact Cache** и **Answer Generator**. |
| [Guardrails](../guardrails/index.md) | Prompt injection, явная бессмыслица, соответствие теме документации; нормализация текста. Решения о допуске принадлежат модулю. |
| [Searcher](../retrieval/index.md) | Поиск фрагментов по закреплённым редакциям; гибридный поиск с приоритетом частотной ветки для вопросов со ссылками. Веса и модели выбираем тестами. |
| [Ingestion](../ingestion/index.md) | **Gateway** принимает документ, вызывает свой **Document Converter**, сохраняет изображения в S3 и готовый Markdown во временном томе. **Worker** индексирует Markdown, публикует редакцию и очищает поисковые данные. Оригиналы не сохраняются. |
| **RAG API · Access** | Допуск сотрудников по Telegram User ID; управление списком разрешённых пользователей администратором. Роли на документы — возможное расширение. |
| **RAG API · Support** | История обращения, автоматическая/ручная эскалация, тикеты, разговор с оператором, админ-панель и представление бизнес-метрик. Вход в web-систему ещё проектируется. |
| [Model Gateway](../model-gateway/index.md) | Техническое исполнение моделей: OCR пользовательского изображения, OCR/VLM для Document Converter, embedding, reranker, детекторы и генерация, включая примеры вопросов для индекса. Не принимает бизнес-решения. |
| [Runtime](../infrastructure/index.md) | Адаптеры PostgreSQL, RabbitMQ, Redis, Qdrant, временных загрузок и получения изображений; сборка процессов. **Queue Relay** передаёт сохранённые уведомления брокеру. |

## Основные сценарии {#два-основных-сценария}

1. **Вопрос → ответ.** Access допускает сотрудника; RAG API сохраняет вход. Core получает текст напрямую или через OCR, выполняет проверки и возвращает готовый Markdown с источниками и ID изображений. RAG API одинаково доставляет новый и кешированный ответ. [Сборка сценария](./module-composition.md)
2. **Документ → поисковая редакция.** Gateway конвертирует вход в Markdown, сохраняет изображения и связывает их ID с плейсхолдерами. После надёжного сохранения Markdown ставит задание в очередь; Worker публикует чанки и примеры вопросов. Core видит редакцию через новое поколение, документ напрямую в Core не отправляется. Ссылка источника ведёт на HTML-заглушку с названием документа.
3. **Вопрос → поддержка.** Отсутствие подтверждений или низкое сходство с примерами ведёт к автоматической эскалации. Ручная просьба — к десятиминутному ожиданию и подтверждению. Support создаёт тикет, RAG API доставляет ссылку. Если ответа нет, тикет создаётся сразу и кнопка вызова не нужна. Для недовольства ответом или явной просьбы после ответа показываем кнопку ручного сценария. [Состояния поддержки](./lifecycle.md#support)

## Границы доступа

MVP работает только в личных чатах. Проверяем именно отправителя Telegram по User ID, а не только чат доставки. Неавторизованный пользователь не запускает модели и поиск. Документация в MVP общая для допущенных сотрудников; фильтрация по отделам/должностям не обязательна. Администратор управляет допуском через Support, используя Access. Механизм входа в тикет-систему ещё открыт; права employee/operator/admin уже определены в контрактах RAG API; наличие URL не считается доказательством авторизации. [Таблица доступа](../faq/case-checklist.md#авторизация-и-уровни-доступа)

Доступ отправителя документа к Ingestion проверяет входной адаптер до регистрации загрузки. Внешние провайдеры моделей выбираются конфигурацией Runtime. Обязательный доступ нельзя заменять разрешающей заглушкой в рабочем профиле. Отключение сотрудника запрещает новые вопросы; принятый до отключения вопрос и доставка его итога завершаются обычным путём.

## Ограничения и открытые решения {#что-уточним-по-кейсу}

- Один активный вопрос на сотрудника; новые вопросы не накапливаем за ним. Статус после 10 секунд без готового итога; 20 секунд — целевая метрика, поздний ответ допустим. Технические сроки попыток задаются отдельно.
- Модели, квоты, ресурсы и численные параметры поиска/фильтров выбираем тестами. OCR пользовательского изображения извлекает только текст. Document Converter анализирует изображения документов через OCR/VLM и сохраняет их описания; конкретные модели выбираем тестами.
- Плейсхолдер, разрешение image_id, callback-действия и минимальная история зафиксированы в контрактах. Остаются параметры моделей/испытаний, сроки хранения, механизм web-входа в Support и формула бизнес-успеха. Эти вопросы не меняют принятые границы модулей.

## Согласование со смежными разделами {#contract-alignment}

| Раздел | Где закреплён согласованный стык |
| --- | --- |
| [RAG API](../telegram/module/entrypoints.md) / [PostgreSQL](../infrastructure/postgresql/rag-api.md) | User ID, атомарный допуск одного вопроса, входящее изображение, самостоятельные доставки статусов/изображений/поддержки и HTML-заглушка источника. |
| [RAG Core и DTO](../rag-core/contracts.md) | Различение бизнес-исходов, намерение эскалации, QuestionInput, QuestionOutcome, сохранённый prepared_text и ImageRef в готовом ответе. |
| [Guardrails](../guardrails/entrypoints.md) / [Searcher](../retrieval/entrypoints.md) | Единый набор revision_ids для темы и поиска; out_of_scope до кеша. Guardrails и Searcher пока кодируют вопрос независимо; переиспользование вектора — будущая оптимизация. |
| [Ingestion](../ingestion/entrypoints.md) / [Qdrant](../infrastructure/qdrant/contracts.md) | Конвертация в Gateway; том содержит Markdown/манифест/PreparedRevision. Изображения S3, отдельные примеры вопросов и совместная проверка полноты двух индексов. |
| [Model Gateway](../model-gateway/entrypoints.md) / [Runtime](../infrastructure/index.md) | OCR/VLM и исполнение конвертера, запись/чтение S3, метаданные заглушки источника, таймеры и состояния Access/Support. |

Новых модулей верхнего уровня для допуска и тикетов не создаём: их функции, управляющие HTTP-ручки и фоновые проверки находятся внутри RAG API. ORM, запросы и атомарные переходы PostgreSQL остаются в Runtime; бизнес-правила не прячем в таблицах. Core сохраняет причину передачи в поддержку и не управляет тикетами.

Контракты, DTO и сигнатуры ведём в разделах владельцев по [правилам Pydantic](../faq/dto.md). Таблица выше — карта стыков. Эта документация задаёт целевой MVP. DTO, сигнатуры и контрактные тесты каркаса синхронизированы с этой спецификацией; бизнес-операции и инфраструктурные адаптеры пока являются заглушками. Снятие warning означает согласованность спецификации, а не работающий RAG.
