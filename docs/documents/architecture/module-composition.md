## Как RAG Core ведёт вопрос

Runtime при запуске связывает реализации шагов с RAG Core. Core задаёт порядок и выбирает следующий шаг по результату. Поиск, проверка и генерация возвращают результат в Core. [Порядок вызовов и DTO](../rag-core/index.md)

| Шаг | Кому и что передаёт RAG Core | Что получает и делает дальше |
| --- | --- | --- |
| 1. Начать обработку | Читает ссылку на запрос из `rag.questions` и загружает сохранённый вопрос RAG API из PostgreSQL. | Закрепляет опубликованное поколение корпуса за запросом. При повторе использует то же поколение. |
| 2. Проверить и подготовить вопрос | Передаёт исходный вопрос в Guardrails. | При допуске передаёт нормализованный вопрос дальше. При блокировке или некорректном вводе просит уточнить вопрос. При сбое проверки планирует повтор или фиксирует технический исход. [Guardrails](../guardrails/index.md) |
| 3. Проверить кеш | Передаёт Exact Cache нормализованный вопрос и закреплённое поколение корпуса. | Готовый ответ с источниками идёт к завершению. При промахе или сбое кеша Core вызывает Searcher. [Правила актуальности кеша](./data-and-versions.md#когда-exact-cache-устаревает) |
| 4. Найти подтверждение | Читает набор редакций закреплённого поколения и передаёт его Searcher вместе с нормализованным вопросом. | Получает фрагменты с источниками. Пустая выдача ведёт к ответу о недостатке данных. Сбой поиска ведёт к повтору или техническому исходу. |
| 5. Сформировать ответ | Передаёт Answer Generator нормализованный вопрос и найденные фрагменты. | Получает текст и ID использованных чанков либо признак нехватки подтверждения. Core берёт источники из найденных фрагментов по этим ID. |
| 6. Завершить обработку | Сохраняет итог в PostgreSQL и ставит через outbox уведомление для `rag.results`. | RAG API получает уведомление и загружает готовый итог для доставки. Успешный ответ можно записать в Exact Cache с поколением запроса. |

## Как документ становится доступен поиску

Ingestion Gateway сохраняет файл во временном рабочем томе и регистрирует задание. Queue Relay публикует уведомление в `ingestion.jobs`. Ingestion Worker последовательно готовит фрагменты, проверяет индекс в Qdrant и публикует редакцию через PostgreSQL. После завершения задания worker удаляет временный файл. RAG Core берёт новое поколение для следующих запросов, Searcher читает выбранные редакции. [Состояния загрузки и публикации](./lifecycle.md#загрузка-и-публикация)

## Как убрать или заменить модуль

| Модуль или компонент | Вариант отключения или замены |
| --- | --- |
| RAG API | Подставить CLI или тестовый адаптер, который принимает вопрос и получает готовый результат. |
| RAG Core | Подставить обработчик с теми же входом и результатом. Для стенда он может возвращать фиксированный результат из тестовых данных. |
| Exact Cache | Убрать шаг или подставить реализацию с постоянным промахом. Запрос сразу идёт в Searcher. |
| Searcher | Подставить другой поисковый адаптер или тестовый набор фрагментов. При пустой выдаче сценарий завершится исходом «недостаточно данных». |
| Answer Generator | Подставить другой генератор ответов по фрагментам. Заглушка для отключённой генерации возвращает технический исход, если вопрос дошёл до неё. |
| Guardrails | Подставить другой способ принять решение о допуске, сохранив смысл нормализации. В рабочем профиле проверка обязательна. Для изолированных тестов задаём решение явно. |
| Ingestion | Подставить другой источник загрузки или обработчик публикации. При отключении Ingestion вопросы обслуживаются по уже опубликованному корпусу. |
| Model Gateway | Заменить backend отдельной роли, сохранив DTO. Для тестов — явная детерминированная заглушка. Смена embedding-профиля требует переиндексации; отключать обязательные проверки при сбое нельзя. |
| Runtime | Для локального теста можно использовать хранилища в памяти. Рабочая сборка сохраняет состояние и поддерживает восстановление. |

## Обращения к моделям

Model Gateway — зависимость Guardrails, Searcher, Ingestion Worker и Answer Generator, а не дополнительный последовательный шаг Core. Runtime выбирает и запускает провайдеров; бизнес-модули передают уже имеющиеся тексты и настройки своих шагов, получают модельные DTO и переводят их в прежние результаты для Core. [Трассировка вызовов](../rag-core/flow.md#model-calls).

## Как вставить новый шаг

Например, дополнительный отбор контекста можно поставить между Searcher и Answer Generator. Он получает вопрос и список фрагментов, сокращает список и сохраняет идентификаторы, редакции и локаторы оставшихся фрагментов. Runtime может подключить этот шаг как обёртку Searcher, сохранив вход и результат вызова для Core.

На любом стыке сначала сверяем выход предыдущего шага, вход нового и вход следующего. Шаг с совместимым входом и выходом можно добавить в цепочку сразу. Если ему нужны новые данные, явно добавляем их поставщика или адаптер. Если шаг должен выполняться и на коротких путях, например при попадании в кеш, подключаем его на общем участке либо в нужных ветках.

При сборке проверяем, что у каждого шага есть нужные данные на всех путях. Сохраняем порядок проверок, версии источников и обязательные точки записи состояния. Например, изменение текста вопроса, влияющее на допуск, должно предшествовать Guardrails или запускать проверку повторно. Для нового получателя из RabbitMQ применяем те же правила подтверждения и повтора. [Очереди и доставка](./message-flow.md)

Для MVP точки восстановления — сохранённый вопрос с поколением и готовый результат перед доставкой. Вызовы между Guardrails и генерацией можно повторить целиком. Если новый шаг сам меняет внешнее состояние, при подключении отдельно определяем его границу сохранения и правило повтора. [Повторы в RAG Core](../rag-core/flow.md#транзакции-и-повторы)
