## Кто владеет данными

| Данные | Кто изменяет | Где хранится |
| --- | --- | --- |
| Допуск сотрудников и администраторов | RAG API · Access; админ-панель Support вызывает его операции | PostgreSQL. Telegram User ID не подменяется chat_id. |
| Вход, время приёма, активный слот и доставка | RAG API | PostgreSQL; для изображения сохраняется устойчивая ссылка на вход и доступные метаданные. |
| OCR-текст, ход обработки, закрепление и готовый ответ | RAG Core | PostgreSQL. Ответ — Markdown, источники и ID изображений, не бинарные файлы. |
| История обращения, ожидание и подтверждение помощи, тикет | RAG API · Support | PostgreSQL; история отделена от контекста LLM. |
| Исходный документ во время конвертации | Ingestion Gateway / Document Converter | Только входной поток/буфер текущего вызова; архив и постоянная копия оригинала отсутствуют. |
| Изображения и связь с плейсхолдерами | Ingestion Gateway через Runtime | S3 и метаданные подготовленной редакции; ID стабилен для конкретного содержимого. |
| Название и идентичность источника для HTML-заглушки | Ingestion сохраняет, RAG API читает | Метаданные PostgreSQL и копия в чанках/готовом ответе. Страница не содержит исходного документа. |
| Результат конвертации Markdown и подготовленный набор до завершения задания | Gateway сохраняет, Worker готовит и очищает | Временный рабочий том и метаданные PostgreSQL. |
| Редакция, поколение, ожидаемые наборы точек | Ingestion Worker | PostgreSQL. |
| Чанки, векторы, локаторы и ссылки/ID изображений | Ingestion Worker пишет, Searcher читает | Qdrant; вектор строится по тексту и описаниям. |
| Примеры допустимых вопросов и их векторы | Ingestion Worker пишет, Guardrails читает | Qdrant, отдельно от чанков, с привязкой к редакции и профилю. |
| Копия готового ответа | Exact Cache | Redis: готовый Markdown, источники, ID изображений и версия. |
| Намерения доставки / публикации уведомлений | Владелец этапа; Queue Relay отмечает публикацию | PostgreSQL и outbox; RabbitMQ содержит ссылки, не оригиналы данных. |
| Бизнес-метрики и состояние тикетов | Владельцы фиксируют исходы, Support представляет аналитику | Сохранённые события/состояния PostgreSQL; Grafana дополняет технические замеры. |

Access и Support — компоненты RAG API, не новые модули верхнего уровня. Новые таблицы дополняют существующую БД, а бизнес-правила реализуются функциями RAG API.

Runtime предоставляет технические адаптеры, но не решает, кого допускать, когда создавать тикет и что считать успешным ответом. Успешная генерация и превышение 20 секунд — технические исходы, не доказательство решения/нерешения проблемы пользователя. Формулу бизнес-успеха ещё согласовать.

## Как меняется версия корпуса

**Корпус** — опубликованный набор документов. **Редакция** — версия одного документа; **поколение корпуса** — версия всего набора. В каждом поколении у документа не более одной видимой редакции. Состав по поколениям определяем в PostgreSQL.

Например, в поколении 41 есть A и B. Добавление C создаёт поколение 42, хотя A и B не изменились: C может изменить ответ на прежний вопрос. Поэтому кеш проверяет поколение всего корпуса, а не версии только прежних источников.

1. Gateway конвертирует документ, сохраняет изображения в S3, готовый Markdown и метаданные источника. Оригинал не сохраняется. Для обновления нужна стабильная идентичность документа; совпадение имён файлов не определяет её.
2. Worker готовит новую редакцию рядом со старой: чанки, примеры вопросов, embedding и метаданные. Для конкретной редакции фиксируется подготовленный набор; повтор не меняет ID, тексты и описания незаметно.
3. До публикации проверяются полные наборы чанков **и** примеров по сохранённым ожиданиям. Наличие одной точки с revision_id не доказывает полноту. PostgreSQL хранит expected_chunk_count и expected_topic_count; сверяются точные детерминированные ID обоих наборов.
4. После успешной проверки Worker одной короткой транзакцией переключает редакцию и увеличивает поколение. Подготовка индекса или неудачная загрузка поколение не меняет.
5. Core закрепляет поколение до Guardrails и кеша. Guardrails фильтрует примеры, Searcher фильтрует чанки по одному набору редакций; готовящаяся редакция ни в один путь не попадает. Повтор вопроса использует прежнее закрепление.
6. При сохранении ответа либо намерения Support Core освобождает закрепление поиска. Для доставки и истории все нужные данные сохраняются отдельно; старые точки больше не нужны только ради отправки готового текста.

Публикация, закрепление и разрешение очистки синхронизируются в PostgreSQL. При обычном обновлении начатый вопрос заканчивает по старому составу. Удаление/откат меняют поколение; экстренное изъятие самого документа остаётся отдельной открытой политикой. Отключение сотрудника не прерывает ранее принятый вопрос и его доставку, но запрещает новые вопросы.

~~~mermaid
sequenceDiagram
  participant C as RAG Core
  participant P as PostgreSQL
  participant W as Ingestion Worker
  participant Q as Qdrant
  C->>P: Закрепить поколение 41 для вопроса A
  W->>Q: Подготовить чанки и примеры новой редакции
  W->>Q: Проверить оба полных набора
  W->>P: Опубликовать редакцию и поколение 42
  Note over C: После рестарта A продолжает с 41
  C->>Q: Guardrails и Searcher читают редакции 41
  C->>P: Сохранить итог A, освободить поиск
  P-->>W: Разрешить очистку старых поисковых точек
~~~

## Когда Exact Cache устаревает

Кеш хранит **готовый ответ бота в Markdown**, а не исходные Markdown документов. В ответе могут быть описания и ID изображений; сами изображения в Redis не помещаются. После попадания в кеш RAG API разрешает ID тем же способом, что при новом ответе.

| Что нашли в Redis | Действие |
| --- | --- |
| Вопрос и поколение совпали | Используем готовый ответ с источниками и ID изображений. |
| Запись старше поколения вопроса | Атомарно удаляем только прочитанную устаревшую запись, если её ещё не заменили; идём полным путём. |
| Запись новее закреплённого поколения | Пропускаем без удаления; ищем по своему составу. |
| Кеша нет или Redis недоступен | Продолжаем основной поиск. |

Более старый вопрос не перезаписывает результат нового поколения. Кеш не отменяет Access и Guardrails: проверка темы выполняется до него, поэтому попадание всё равно может потребовать embedding и обращения к индексу примеров Qdrant.

TTL ограничивает срок хранения, но не заменяет проверку поколения. Смена правил генерации, нормализации, плейсхолдеров или профиля моделей требует отдельной инвалидации кеша/смены пространства ключей: она не всегда меняет документы. Политику реализуем в Exact Cache и Runtime.

## Изображения и источники {#media}

Document Converter извлекает изображения, Gateway сохраняет их в S3 и связывает ID с плейсхолдерами и описаниями в Markdown. Оригинальный документ не архивируется. ID нельзя переиспользовать для другого содержимого. Доставка получает свежий доступ к файлу по стабильному ID, а не полагается на сохранённую в кеше временную подписанную ссылку.

ID и описание проходят путь «Markdown → чанк → найденный контекст → готовый ответ → кеш/доставка». Генератор использует только ID из переданного контекста. Плейсхолдер `![Описание](image://<uuid>)` определён в общих DTO; Runtime разрешает UUID в объект настроенного S3-bucket без URL от модели.

Ссылка источника ведёт на HTML-заглушку RAG API: «Тут должен быть хостинг документа „Название документа“». Источник определяется документом; подпись берётся из сохранённых метаданных, совпадающих с названием в чанках. Старый ответ сохраняет своё название источника. Метаданные страницы не удаляем вместе с поисковыми точками, а выводимое название экранируем как текст. Якоря разделов, выделение цитаты в браузере и отдельный Docusaurus для исходников не требуются.

## Очистка и восстановление {#cleanup}

| Материал | Когда разрешена очистка |
| --- | --- |
| Временный входной Markdown и результаты подготовки | Задание опубликовано или окончательно завершилось, нет неизвестной записи, требующей восстановления. |
| Старые чанки и примеры | Редакция не видима в текущем составе и не нужна закреплённым вопросам; разрешение фиксируется до удаления Qdrant. |
| Ответы Redis | По TTL, лимиту памяти или правилам версии; это не разрешение удалить изображение из S3. |
| Изображения и метаданные HTML-заглушки | По политике Ingestion с учётом доставок, кеша, истории и выданных ссылок. Освобождение поиска не удаляет эти материалы. Непривязанные объекты S3 проверяем отдельно. |
| История, тикеты, допуски и исходы доставки | По отдельным срокам хранения и правилам дедупликации; незавершённая работа не исчезает из-за очистки. |

Неизвестная запись Qdrant сначала проходит [сверку](../infrastructure/qdrant/index.md#сверка-незавершённых-записей). Восстановление сверяет ожидаемые наборы обоих индексов, профиль embedding и ссылочные материалы. При потере индекса примеров корпус не объявляется полностью готовым.

Бэкап/восстановление учитывают PostgreSQL, оба набора Qdrant, незавершённые Markdown-задания и S3. Отдельного репозитория источников и архива оригиналов нет. При утрате готовых данных после очистки временного Markdown повторная конвертация возможна только после новой загрузки отправителем. S3 и PostgreSQL не имеют общей транзакции: до коммита проверяем сохранность материалов, а при неизвестном коммите не удаляем возможные ссылки принятого задания.
