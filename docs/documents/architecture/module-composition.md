Access и Support — внутренние компоненты RAG API. Их таблицы и атомарные операции реализуются через Runtime; отдельные модули верхнего уровня не требуются.

Runtime при запуске связывает реализации модулей. RAG Core задаёт порядок обработки вопроса; модули возвращают ему результаты, а не вызывают следующий бизнес-шаг сами. Обращения к моделям идут через Model Gateway, к хранилищам и файлам — через адаптеры Runtime.

## Как RAG Core ведёт вопрос

До Core RAG API проверяет сотрудника через Access и атомарно регистрирует единственный активный вопрос. Сохраняются Telegram User ID, назначение доставки, время приёма и текст либо устойчивая ссылка на входящее изображение. Ссылка должна позволять получить байты после рестарта; хранения только в памяти недостаточно.

| Шаг | Что уже есть и кому передаётся | Результат и следующий путь |
| --- | --- | --- |
| 1. Взять вопрос | Ссылка из `rag.questions` → чтение входа и попытки через Runtime. | Core закрепляет поколение корпуса. Повтор использует то же поколение. |
| 2. Получить текст | Текстовый вход используется напрямую. Для изображения Runtime получает байты по сохранённой ссылке, Model Gateway выполняет OCR. | Core получает текст; изображение не сравнивается с интерфейсами документации. Если текста нет, просим прислать текстовый вопрос. Подпись и OCR-текст объединяются без потери исходных значений. |
| 3. Проверить вопрос | Текст и ID редакций закреплённого поколения → Guardrails: prompt injection, явная бессмыслица, нормализация, сравнение с примерами темы. | Допуск даёт единый нормализованный текст. Инъекция → отказ; бессмыслица → просьба переформулировать; низкое сходство → автоматическая эскалация без основного поиска. Спорная осмысленная формулировка проходит дальше, если не сработал настроенный порог темы. |
| 4. Проверить кеш | Нормализованный текст и поколение → Exact Cache. | Попадание даёт готовый Markdown с источниками и ID изображений. Промах/сбой Redis → поиск. Все обязательные проверки уже выполнены. |
| 5. Найти подтверждение | Core повторно использует набор редакций, уже полученный до Guardrails, и передаёт его Searcher вместе с текстом. | Фрагменты содержат источники и плейсхолдеры изображений. Пустая выдача → эскалация. Ссылка в вопросе повышает приоритет частотной ветки, вес подбирается тестами. |
| 6. Подготовить ответ | Нормализованный вопрос и найденные фрагменты → Answer Generator. | Готовый Markdown, использованные источники и ID изображений только из контекста. Нехватка подтверждений → эскалация; выдуманный ID — ошибка результата, а не произвольная загрузка файла. |
| 7. Зафиксировать решение | Попытка и бизнес-исход → PostgreSQL через Runtime. | Сохраняем ответ и доставку либо намерение Support. Снимаем закрепление поиска. В кеш попадает только успешный готовый ответ; эскалации и технические сообщения не кешируем. |
| 8. Доставить | RAG API читает итог, разрешает ID изображений через Runtime и оформляет сообщение. | Новый и кешированный ответ доставляются одинаково. Прогресс текста/изображений сохраняется отдельно от исполнения Core. |

~~~mermaid
flowchart TD
  I["Принятый вопрос + поколение"] --> T["Текст / OCR"]
  T --> G["Guardrails"]
  G -->|"допуск"| K["Exact Cache"]
  G -->|"отказ / бессмыслица"| R["Сохранить пояснение"]
  G -->|"вне темы"| H["Сохранить намерение Support"]
  K -->|"попадание"| A["Готовый Markdown + ID изображений"]
  K -->|"промах"| S["Searcher"]
  S -->|"фрагменты"| L["Answer Generator"]
  S -->|"пусто"| H
  L -->|"ответ"| A
  L -->|"не хватает подтверждений"| H
  A --> D["RAG API: текст + изображения"]
  R --> D
  H --> SUP["Support: создать тикет"]
  SUP --> D
~~~

Непустой корпус не обязан иметь пример на каждую формулировку; порог темы делаем щадящим и проверяем тестами. Но отсутствие/недоступность самого индекса примеров — технический сбой, не доказательство, что вопрос вне темы. После базовых проверок пустой опубликованный корпус даёт исход о недостатке данных, без поиска по примерам.

## Как документ становится доступен поиску

1. **Ingestion Gateway** проверяет отправителя, метаданные, размер и поддерживаемый формат документа, назначает идентичность документа/редакции. Конвертация выполняется до подтверждения приёма. «Разные форматы» не означает молчаливую поддержку неизвестного: неподдерживаемый файл завершается явным отказом.
2. **Document Converter**, подмодуль Gateway, приводит содержимое к Markdown, извлекает изображения, получает их текстовые описания через OCR/VLM в Model Gateway. Конвертер возвращает изображения в памяти; Gateway через Runtime сохраняет их в S3 и связывает уникальные ID с неделимыми плейсхолдерами в Markdown. Готовый Markdown проходит тот же путь; картинки обрабатываются, если они присутствуют.
3. Gateway сохраняет **только полученный Markdown** с метаданными и соответствием изображений во временном рабочем томе. После успешной записи S3 и Markdown одной транзакцией регистрирует задание и outbox для `ingestion.jobs`. Лишь после коммита загрузка считается принятой. Оригинал используется как входной поток/буфер текущей конвертации, в БД, рабочем томе и архиве не сохраняется.
4. **Ingestion Worker** читает подготовленный Markdown, делит прежде всего по разделам; крупные части — с настраиваемым перекрытием. Плейсхолдер с ID и описанием не разрывается. Слишком большой неделимый блок не обрезается молча: нужна корректировка входа/настроек.
5. Worker через **Model Gateway** получает embedding чанков и генерирует примеры допустимых вопросов. Сохраняет PreparedRevision в рабочем томе до begin_revision_write, чтобы повтор не менял разбиение, векторы и результаты генерации. Чанки и примеры лежат в Qdrant раздельно, с привязкой к редакции.
6. После проверки обоих полных наборов Worker одной транзакцией PostgreSQL открывает редакцию и увеличивает поколение. Новые вопросы видят новые чанки и примеры; неудачная загрузка не меняет опубликованный состав. Gateway не вызывает поисковый пайплайн Core напрямую.
7. Завершённое задание освобождает временный Markdown. Изображения остаются в S3 по отдельной политике хранения. При повторе уже принятого задания оригинал и повторная конвертация не нужны.

Gateway ограничивает время конвертации и размер входа. CPU-парсер выполняется управляемым исполнителем вне event loop; модельные вызовы проходят через Model Gateway. Если процесс упал до надёжного приёма Markdown, отправитель повторяет загрузку оригинала. Если итог коммита неизвестен, сохраняем Markdown и изображения до выяснения состояния, а не удаляем материал потенциально принятого задания. Непривязанные объекты S3 убираются отдельно после проверки отсутствия ссылок.

### Ссылка на источник

RAG API отдаёт простую HTML-страницу с текстом «Тут должен быть хостинг документа „Название документа“». Название и идентичность берём из сохранённых метаданных источника, которые также присутствуют в чанках. Ссылка ведёт на документ целиком; якоря разделов, `#:~:text=…` и отдельный сайт исходников не требуются. Страница не содержит оригинал, цитаты для ответа по-прежнему берутся из найденных чанков. [HTTP-контракт](../telegram/endpoints/source-page.md) определён в RAG API.

## Как работает поддержка

Core сохраняет причину автоматической эскалации, ссылку на вопрос и намерение передать контекст. Support создаёт тикет один раз для этого обращения; затем RAG API доставляет URL. История Support служит передаче оператору и не подмешивается в контекст генерации.

После недовольства ответом или просьбы о человеке после ответа показываем кнопку. Её нажатие запускает 10 минут самостоятельного поиска; до первого ответа кнопки нет. Автоматическая эскалация при отсутствии ответа сразу даёт тикет, без этой кнопки. Пользователь может задавать новые самостоятельные вопросы. Затем Support через RAG API спрашивает, нужна ли ещё помощь; тикет создаётся после «Да». Отказ или отсутствие подтверждения сами по себе тикет не создают. После автоматического создания тикета устаревшее подтверждение по тому же обращению не создаёт второй. [Состояния](./lifecycle.md#support)

## Как убрать или заменить модуль

| Модуль или компонент | Замена и обязательное условие |
| --- | --- |
| RAG API | Другой транспорт или CLI с явной идентичностью пользователя и теми же исходами. Telegram-форматирование не проникает в Core. |
| RAG API · Access | Другой источник сотрудников. Разрешающая заглушка допустима только в изолированном тесте. |
| RAG Core | Другой обработчик вопроса, сохраняющий решения, попытки и намерения доставки/поддержки. |
| Guardrails | Другие детекторы с теми же исходами. Сбой обязательной проверки не превращается в допуск. |
| Exact Cache | Постоянный промах; путь идёт в Searcher. |
| Searcher / Answer Generator | Другой поиск / генератор с сохранением редакций, происхождения источников и ID изображений. Тестовые данные задаются явно. |
| Ingestion | Другой конвертер внутри Gateway или обработчик индексации; граница Gateway → Worker остаётся готовым Markdown. Без новых загрузок вопросы работают по опубликованному составу. |
| RAG API · Support | Адаптер внешней тикет-системы вместо собственной. Сбой/отключение не выдаёт пользователю фиктивный номер тикета. |
| Model Gateway | Замена backend роли; смена embedding-профиля требует переиндексации чанков и примеров. |
| Runtime | Хранилища/файлы в памяти только для изолированных проверок; рабочая сборка сохраняет состояние. |

## Обращения к моделям

Model Gateway — зависимость вызывающих модулей, не отдельный последовательный шаг. Core организует OCR; Guardrails использует детекторы и embedding для темы; Searcher — embedding и опциональный reranker; Answer Generator — генерацию; Document Converter в Gateway — OCR/VLM документов; Worker — embedding и генерацию примеров. Локальная модель/API выбираются в Runtime. Роли конвертации не загружаются в процесс индексации без необходимости.

Embedding нормализованного вопроса желательно использовать повторно между Guardrails и Searcher. Его поставщик, профиль и передача должны быть явно отражены в будущих контрактах; глобальная скрытая переменная не является способом связать модули.

## Как вставить новый шаг

Для каждого шага указываем вход, выход, исходы, источник данных и побочные эффекты. Совместимый отбор контекста можно оформить обёрткой Searcher: сохранить ID, редакции и локаторы оставшихся фрагментов. Шаг с новыми данными требует их поставщика и согласования контрактов.

Проверяем короткие пути: кеш не обходит Access/Guardrails; получение изображений работает без Searcher; отказ OCR не запускает генерацию; эскалация не зависит от наличия источников. Изменение смысла вопроса после проверки требует повторной проверки. Новые внешние записи получают границу сохранения, ключ идемпотентности и правило восстановления.
