:::warning План проверки
Это сценарии для будущей реализации. Корпус, пороги и нагрузку берём из кейса.
:::

| Проверка | Ожидаемое наблюдение |
| --- | --- |
| Документ → вопрос → источник | Бот отвечает по опубликованной редакции. Ссылка открывает HTML-заглушку с названием документа; нужные изображения доставлены в чат по ID. |
| Неизвестный вопрос и отказ зависимости | Недостаток данных, блокировка вопроса и технический сбой дают разные исходы. |
| Повтор и обновление корпуса | Повтор берёт ответ из Exact Cache для своего поколения. После публикации редакции или нового документа запрос пропускает старый ответ и пересчитывает его. Если во время очистки кеша другой запрос записал новый ответ, тот остаётся доступным. |
| Публикация во время запроса и рестарт Core | Начатый запрос восстанавливает прежние редакции, а новый запрос из другого чата берёт новое поколение. Старые фрагменты удаляются только после сохранения итогов запросов, которые их закрепили. |
| Зависшее локальное вычисление | Супервизор завершает процесс с потомками. RabbitMQ возвращает неподтверждённое сообщение, новый потребитель обрабатывает следующие задания. |
| Неизвестный исход записи в Qdrant | Частичная редакция не видна. Перезапуск Worker не разблокирует повтор или очистку. После остановки писателей, перезапуска Qdrant и подтверждённой сверки задание снова готово к запуску. При потерянном ответе на коммит публикации уже опубликованные точки сохраняются. |
| Падение после записи временного файла | После неизвестного коммита регистрации уборка дожидается исхода транзакции. Принятый файл сохраняется, осиротевший удаляется. |
| Неполный снимок индекса при сохранном PostgreSQL | Снимок с 40 из 100 точек отклоняется, даже если `revision_id` присутствует. Сверка обнаруживает также заменённый ID при том же числе точек. Поиск и кеш ждут восстановления нужных редакций. |
| Повтор обновления Telegram и рестарт | Один входящий update не создаёт второй запрос. Готовый результат можно дослать после сбоя без повторной генерации. Новый вопрос сотрудника с активным запросом получает busy и не создаёт вторую работу; доставки сохраняют порядок. |
| Брокер работает, потребитель отстаёт | Лимит учитывает запросы с опубликованным outbox. При общем лимите приём временно отклоняется, уже принятый дубликат подтверждается; busy-сообщение не создаёт второй вопрос. Периодическая проверка не публикует копию на каждом проходе. |
| Последняя отправка прервалась | После истечения последней попытки фиксируем неизвестный исход без ещё одной отправки. |
| Ответ слишком длинный | Сокращаем оформление источников. Если ответ всё ещё не помещается, Telegram получает короткую просьбу сузить вопрос. После подтверждения доставка завершена, в логе есть `length_fallback`. При таймауте исходной отправки второе сообщение в той же попытке не отправляется. |
| Ожидание в outbox | Для всех маршрутов Relay считает интервал по `available_at` из PostgreSQL и времени начала публикации. Тело и заголовки сообщения RabbitMQ сохраняют прежний формат. |
| Рестарт приложения или потеря очереди | Queue Relay допубликовывает незавершённый outbox. При потере очередей владельцы этапов восстанавливают только нужную работу из PostgreSQL. Если позднее уведомление пришло первым, оно не блокирует очередь и ждёт своего хода. |
| Проверка и нормализация вопроса | При блокировке бот просит переформулировать вопрос. У допущенного вопроса сохраняются отрицания, номера версий и значимые символы кода. |
| Замена и вставка шага | Запрос проходит без Exact Cache и с тестовым Searcher. Добавленный после Searcher шаг сохраняет идентификаторы и редакции источников. Сборка отклоняет сценарий, у которого отсутствует обязательный вход. |
| Скорость и качество | Отдельно замеряем новые и повторные вопросы, задержку до готового ответа и до доставки. Проверяем полноту найденных источников и обоснованность ответов. |

## Проверки новых условий

| Проверка | Ожидаемое наблюдение |
| --- | --- |
| Конвертация до accepted | Оригинала в томе/S3 нет; Markdown/манифест и изображения подтверждены до коммита job/outbox. |
| Повтор индексации | PreparedRevision читается, примеры/векторы не генерируются заново после закрепления. |
| Один из двух наборов индекса неполон | Публикации нет; при восстановлении проверяются expected_chunk_count и expected_topic_count. |
| OCR пользователя | Подпись + извлечённый текст сохранены; VLM-описание пользовательской картинки не вызывается. |
| Фильтры до кеша | Явная бессмыслица → переформулировать; out_of_scope → тикет; сломанный индекс → технический сбой. |
| 10 / 20 секунд | Статус после 10; после 20 запрос не отменяется и тикет только по времени не создаётся. |
| Автоматическая / ручная поддержка | Нет подтверждений → сразу тикет; просьба после ответа → 10 минут и подтверждение Да. |
| История / модели | Тикет содержит исходный вопрос/ответ; история обращения не подмешивается в следующую генерацию. |
| Web-доступ не настроен | Защищённые HTTP-ручки закрыты с auth_not_configured. |

| Проверка отзыва допуска | Принять вопрос, отключить сотрудника до claim/между частями доставки: принятый вопрос завершается, текст/картинки или ссылка тикета доставляются. Повтор его update сохраняет прежний исход; новый вопрос получает denied. При обратном порядке коммитов вопрос не регистрируется. |
