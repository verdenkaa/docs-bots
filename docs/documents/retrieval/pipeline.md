:::warning Кандидат для MVP
Схема основана на прототипе Ромы. Режим запуска, модели, лимиты и порог релевантности определим после сравнения на корпусе кейса.
:::

Гибридный профиль ищет по смыслу и по словам. Например, dense помогает сопоставить «не могу войти» с разделом «Восстановление доступа», а BM25 ищет по терминам из вопроса вроде кода ошибки `AUTH-17`. То, как код разбивается на токены, проверяем на реальных примерах. [Гибридный поиск Qdrant](https://qdrant.tech/documentation/search/text-search/hybrid-search/)

~~~mermaid
flowchart LR
    IN["Вопрос и выбранные редакции"] --> D["Эмбеддинг вопроса → dense"]
    IN --> T["Текст вопроса → BM25"]
    D --> F["Qdrant объединяет списки через RRF"]
    T --> F
    F --> R["Reranker переоценивает кандидатов<br/>если включён"]
    R --> OUT["Лучшие фрагменты с источниками"]
~~~

1. Для пустого набора редакций сразу возвращаем пустой список. Для остальных запросов применяем `Match Any` по `revision_id` к каждой ветке до выбора кандидатов. В гибридном запросе один фильтр передаём в оба `prefetch`. Так готовящаяся редакция не займёт места в выдаче, а начатый запрос продолжит поиск по своему набору. [Фильтры в гибридном запросе](https://qdrant.tech/course/beginners/module-3/filtering/)
2. **Dense.** Кодируем вопрос той же версией модели, которой Worker кодирует чанки. Стартовый кандидат — `BAAI/bge-m3`, плотный вектор из 1024 чисел и косинусная метрика в Qdrant. [Карточка BGE-M3](https://huggingface.co/BAAI/bge-m3) · [Конфигурация коллекции](../infrastructure/qdrant/index.md#запуск)
3. **BM25.** Qdrant оценивает совпадения по текстовому индексу payload-поля `text`. Для запроса используем `TextQuery`, а RRF объединяет списки по позициям фрагментов. Итоговый балл RRF отражает место в выдаче и сам по себе не показывает, достаточно ли данных для ответа. [Полнотекстовый поиск](https://qdrant.tech/documentation/search/text-search/full-text-search/) · [RRF](https://qdrant.tech/documentation/search/hybrid-queries/)
4. **Reranker.** Если включён, приложение одним пакетом передаёт модели пары «вопрос — текст чанка» для ограниченного пула кандидатов. В прототипе используется `BAAI/bge-reranker-v2-m3`. Модель меняет порядок внутри пула. При отключённом шаге сохраняем порядок поиска. [Карточка модели](https://huggingface.co/BAAI/bge-reranker-v2-m3)
5. **Выдача.** Если для выбранного профиля подобран порог релевантности, применяем его перед выдачей. Затем возвращаем до `top_k` фрагментов со ссылочными данными. Даже непустая выдача может не подтверждать ответ. Решение о достаточности контекста остаётся за RAG Core и Answer Generator.

Вызовы к Runtime идут в таком порядке: `embed_texts([query])` даёт вектор вопроса, `find_chunks(query, query_vector, revision_ids, candidate_limit)` даёт список `QdrantHit`. После отбора Searcher возвращает только их `fragment`. [Функции адаптеров](../infrastructure/qdrant/contracts.md)

В `day6` прототипа каждая ветка берёт до 10 кандидатов, RRF отдаёт до 10, reranker оставляет до 3. Эти числа подходят для первого сравнительного прогона. Для плотного поиска отдельно, гибрида и гибрида с reranker сохраняем общий контракт. Выбранный профиль задаём при запуске. Сбой обязательного для профиля компонента возвращаем как техническую ошибку.

Runtime загружает модель эмбеддингов один раз при запуске каждого процесса, которому она нужна. Core использует её для вопросов, Worker для чанков. Reranker загружается только в процессе поиска при включённом шаге. Число одновременных вычислений подбираем по памяти и задержке на сервере. [Порядок запуска](../infrastructure/startup.md)
