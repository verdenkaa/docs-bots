:::warning
Это небольшой профиль разработки для проверки интеграции. LLM-классификация инъекций, LLM-реранкер и OCR маленькой VLM требуют отдельной оценки качества на данных проекта. Успех пробного вызова не подтверждает готовность защиты или всего Telegram-бота.
:::

Адаптер app/rag/model_gateway/ollama.py подключает настоящий HTTP API Ollama ко всем шести [ролям Gateway](./entrypoints.md). Сервер может работать на том же компьютере. Binding использует execution="remote", поскольку inference выполняется сервером Ollama вне Python-процесса приложения. Загрузка модели происходит в Ollama; бизнес-модули по-прежнему вызывают Model Gateway.

## Профиль разработки

| Роль | Небольшая модель | Нормализация |
| --- | --- | --- |
| embedding | embeddinggemma:300m | 768 измерений, query/document с разными инструкциями. |
| generation | qwen3:0.6b | Полный ответ, явный done_reason, счётчики токенов; thinking выключен. |
| injection | qwen3:0.6b | Наблюдение benign/injection по JSON Schema; решение о допуске остаётся в Guardrails. |
| reranker | qwen3:0.6b | LLM-оценка каждого кандидата от 0 до 1, исходные индексы сохраняются. Это экспериментальный профиль, не специализированный cross-encoder. |
| ocr / vision (опционально) | Явно заданная через --vision-model VLM | Распознанный текст / описание, изображение передаётся в base64. |

Названия и размеры доступны в каталогах [Qwen3 0.6B](https://ollama.com/library/qwen3:0.6b) и [EmbeddingGemma](https://ollama.com/library/embeddinggemma). По умолчанию проверяется текстовый профиль из четырёх ролей; VLM подключается явно. Модели загружаются оператором явно. Облачные модели Ollama этот адаптер отклоняет; к облачному API не переключается.

## Подготовка и запуск

Для минимального запуска обработчика вопросов с этими двумя моделями задайте `RAG_TEXT_ONLY=true` в общем `.env`. В этом явном тестовом режиме Runtime не требует OCR binding; вопросы с фотографиями завершаются техническим уведомлением, без подмены распознавания. По умолчанию `false`: полноценный профиль вопросов по-прежнему требует OCR. Этот переключатель не отключает Guardrails и не меняет требования embedding/generation/injection или включённого reranker.

Запустите установленную Ollama. API по умолчанию слушает http://127.0.0.1:11434. Отдельно скачайте веса:

~~~sh
ollama pull qwen3:0.6b
ollama pull embeddinggemma:300m
~~~

Из app/ с установленными зависимостями проекта:

~~~sh
python -m rag.model_gateway.ollama_setup --smoke --report .env.ollama.report.json
~~~

Команда читает список уже установленных моделей, закрепляет полные SHA-256 manifest digest и создаёт .env.ollama.local. При --smoke сначала проверяет роли настоящими inference-вызовами. Она не поднимает сервер, не скачивает веса, не подключается к PostgreSQL и не меняет индекс. Существующие файлы не перезаписывает; для повторного запуска задайте новые --output/--report. Без --smoke команда только строит профиль; для проверки используйте check-models. --vision-model добавляет установленную VLM для ocr/vision; --skip-vision исключает её. Текстовый профиль не подходит для запуска роли questions, требующей OCR. --timeout-s ограничивает каждый smoke-вызов, по умолчанию 180 секунд.

.env.ollama.local и .env.ollama.report.json игнорируются Git. Основной .env не меняется и новый файл сам не подхватывается. Для явной проверки сохранённого профиля:

~~~sh
python -c "from dotenv import load_dotenv; load_dotenv('.env.ollama.local', override=True); from rag.runtime.__main__ import main; main()" check-models
~~~

Для приложения в Docker Desktop при Ollama на Windows укажите `--endpoint http://host.docker.internal:11434`. Внутри контейнера localhost относится к самому контейнеру. На Linux адрес и доступность хостового API настраиваются отдельно. Не публикуйте неавторизованный Ollama API в общедоступную сеть ради этой проверки.

Созданный dotenv-файл предназначен для загрузки через python-dotenv/Pydantic Settings: JSON-значения в нём экранированы. Это не прямой Docker --env-file. Передайте параметры штатной сборке окружения приложения или явно загрузите файл внутри Python. Для Runtime embedding-профиль и размерность обязаны совпадать с индексом; этот тест не переключает существующий корпус на новые векторы.

## Регистрация адаптера

### <span className="operation-badge operation-badge--call">CALL</span> `register_providers`

~~~python
def register_providers() -> None: ...
~~~

Технический синхронный hook регистрирует factory под именем ollama. Вызывается при явном start_models через MODEL_GATEWAY_PROVIDER_MODULES. Сам по себе не выполняет сетевых вызовов. Для ручной сборки укажите MODEL_GATEWAY_PROVIDER_MODULES как JSON-список `["rag.model_gateway.ollama"]`, а RAG_MODEL_BINDINGS возьмите из созданного файла. Модуль не выбирается автоматически по наличию установленной Ollama.

ModelBinding.model_revision должен содержать полный manifest SHA-256 (допустим префикс sha256:). Во время запуска проверяются digest и capabilities нужной роли. Перед каждым inference digest сверяется снова: изменение тега приводит к model_profile_mismatch, а не к вызову новой версии под прежним профилем. Не изменяйте теги во время работы: API Ollama маршрутизирует по имени и не предоставляет атомарного условия digest для самого POST. Профиль фиксирует также версию нормализации v1. Изменение промптов, purpose-инструкций, контекста или модели требует нового профиля и согласования кеша/индекса.

Для embedding v1 поддерживается именно EmbeddingGemma с её [инструкциями query/document](https://ai.google.dev/gemma/docs/embeddinggemma/model_card). Текст запроса получает префикс `task: search result | query: `, документ — `title: none | text: `. truncate=false запрещает молча отрезать вход. Gateway проверяет фактическую размерность и количество векторов.

## Ограничения и ошибки

HTTPX-клиент переиспользуется, не использует системный HTTP proxy для локальных вызовов, не следует redirect и не повторяет POST. Ответ ограничен MODEL_GATEWAY_MAX_MESSAGE_BYTES. Полный ответ [chat](https://docs.ollama.com/api/chat) принимается только при done=true и известном done_reason: stop переводится в completed, length сохраняется. Неизвестное завершение, повреждённый JSON, tool_calls вместо текста и несовпадающая модель дают model_invalid_response. Для OCR, описания и структурированного вывода length не считается полным результатом. Сырые ошибки сервера не попадают в логи Gateway.

Профиль v1 использует контекст 2048. Для chat применяется консервативный допуск по UTF-8-байтам с запасом на служебные/визуальные токены и бюджет вывода: слишком большой вход отклоняется до inference. Поэтому длинные документы, большие списки кандидатов и большие max_output_tokens этому профилю не подходят. Это сознательное ограничение небольшого локального стенда; production-профиль с другим контекстом требует отдельного согласования.

OLLAMA_GATEWAY_KEEP_ALIVE по умолчанию "0": сервер выгружает модель после ответа, снижая потребление RAM ценой повторной загрузки перед следующим вызовом. Можно явно задать, например, 5m для сохранения в памяти; учитывайте суммарную память моделей и параллелизм самого Ollama. close_models закрывает клиенты приложения и не останавливает общий сервер Ollama.

Числовые значения из env (`0`, `-1`, `3600`, `0.5`) передаются Ollama как JSON-числа секунд, а длительности с единицами (`5m`, `-1s`) остаются строками. Отрицательное значение удерживает модель в памяти при наличии ресурсов. Строка JSON `"-1"` без единицы времени не принимается Ollama и вызывает HTTP 400; адаптер нормализует её в число `-1` до пробных и рабочих запросов.

Все вызовы проходят обычную [защиту повторов Gateway](./providers.md#повторы). Smoke отправляет восемь одновременных одинаковых embedding-запросов и затем повторяет запрос; счётчик реальных inference HTTP-вызовов должен вырасти ровно на один. В приложении долговечность этой защиты обеспечивает координатор Runtime. После сетевого таймаута закрытие HTTP-соединения не доказывает остановку серверного inference; неизвестный исход не повторяется автоматически.

## Что проверяет smoke

Отдельный профиль генерации JSON для Ingestion/Answer Generator можно включить через `OLLAMA_GATEWAY_GENERATION_JSON=true`. Тогда только роль generation передаёт Ollama `format="json"`; при неуказанной температуре используется 0. Схему и смысл ответа по-прежнему проверяет вызывающий модуль, Markdown-обёртки не удаляются и неверные ответы не принимаются. По умолчанию режим выключен: для смены режима задавайте новый generation `profile_id`.

Для отдельного тестового текстового профиля можно явно задать `OLLAMA_GATEWAY_TEXT_CONTEXT_LENGTH` от 2048 до 32768. Адаптер использует это значение и для допуска входа, и для `num_ctx` Ollama; превышение по-прежнему отклоняется до inference. Для изменённого контекста задавайте новые `profile_id` текстовых ролей и проверяйте реальные вызовы. OCR/vision сохраняют контекст 2048 независимо от этой настройки. Значение по умолчанию и профиль v1 не меняются.

Проверяются readiness всех выбранных ролей, векторы документов и вопроса, генерация, ранжирование, классификация. При подключении VLM создаётся синтетическая картинка HELLO RAG 42; в отчёт входят фактические OCR-текст и описание. Оцениваются транспорт и контракты, а не точность ответов. Отчёт показывает реальные ответы и число inference HTTP-вызовов после readiness. Синтетические данные можно сохранять; пользовательские промпты и документы в репозиторий не добавляются.

При локальной проверке Moondream 1.8B Q2_K вернула пустую строку на пробную картинку: для OCR это допустимый OcrResult, для vision это model_invalid_response по контракту ImageDescription. Gateway корректно отклонил такой ответ и свернул частичный запуск. Чтобы менять/ослаблять валидацию ради слабой тестовой модели не пришлось, VLM не включена в профиль по умолчанию. Проверка с подходящей VLM использует тот же адаптер.

Слабое качество маленькой модели не исправляется фиктивным успешным ответом: в отчёте остаётся фактический результат. Подбор production-моделей, оценка Guardrails/retrieval/OCR и реализация остальных бизнес-модулей — отдельные задачи.
