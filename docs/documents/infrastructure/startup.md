Базовая среда приложения — Python 3.12.x; зависимости задаёт `app/pyproject.toml`. [Библиотеки и установка](../faq/python-environment.md).

## Что поднимаем

| Сервис | Что запускает | Постоянные данные |
| --- | --- | --- |
| `core` | RAG API, RAG Core, потребителя `rag.results` и один активный [Queue Relay](./queue-relay.md) для всех маршрутов. | В подключённых хранилищах. |
| `worker` | Ingestion Gateway и одного последовательного Ingestion Worker под отдельным [супервизором](../ingestion/worker.md#срок-попытки-и-остановка-процесса). | `worker_spool` для готового Markdown, манифеста и PreparedRevision; оригиналов нет. |
| `postgres` | Базу состояния и outbox. | `postgres_data` подключаем к каталогу данных выбранного образа PostgreSQL. |
| `rabbitmq` | Три долговечные очереди с сохраняемыми сообщениями. | `rabbitmq_data` для состояния брокера. |
| `qdrant` | Коллекции document_chunks и topic_questions. | `qdrant_data` подключаем к `/qdrant/storage`. |
| `s3` или внешний S3 | Изображения по неизменяемому UUID; доступ через Runtime. | Постоянный bucket; у собственного сервиса отдельный том. |
| `redis` | Exact Cache. | Для первого среза достаточно памяти. |

`core` и `worker` собираем из одной Python-кодовой базы с разными командами запуска. Для MVP выбран Telegram webhook; long polling остаётся сменным адаптером и одновременно с webhook не работает. Для HTTP в синке указаны Gunicorn и процессы Uvicorn. Фоновые роли запускаем отдельно от HTTP-процессов внутри контейнера, чтобы масштабирование HTTP не запускало повторно Relay, контроллеры статуса/Support или потребителя доставки. [Варианты приёма Telegram](../telegram/module/index.md#два-способа-приёма) · [Итоги синка, D-07](../faq/drafts/architecture-team-sync.md)

## Что переживает перезапуск

Данные PostgreSQL и Qdrant переживают рестарт контейнера, его пересоздание и перезагрузку сервера, если подключены те же именованные тома и диск сохранился. Для PostgreSQL путь монтирования берём из документации выбранной версии образа. [Тома Docker](https://docs.docker.com/engine/storage/volumes/) · [Образ PostgreSQL](https://hub.docker.com/_/postgres) · [Запуск Qdrant](https://qdrant.tech/documentation/quickstart/)

| Событие | Что происходит |
| --- | --- |
| `docker compose restart` или пересоздание контейнера с тем же томом | Базы снова читают сохранённые данные с тома. |
| Перезагрузка сервера | Тома остаются на диске. Автоматический запуск контейнеров задаётся отдельно, например политикой `restart: unless-stopped`. [Политики перезапуска Docker](https://docs.docker.com/engine/containers/start-containers-automatically/) |
| `docker compose down -v` | Compose удаляет именованные тома, объявленные проектом. [Docker Compose down](https://docs.docker.com/reference/cli/docker/compose/down/) |
| Утрата диска или тома Qdrant | Чанки и векторы восстанавливаем из снимка Qdrant либо повторной загрузкой документов. [Восстановление индекса](./qdrant/index.md#восстановление-индекса) |

## Порядок запуска

1. Поднять хранилища и брокер во внутренней сети. Проверить подключение с учётными данными приложения и доступность нужных томов.
2. Применить миграции PostgreSQL из образа приложения. Одним шагом проверить обе коллекции и индексы Qdrant для выбранного профиля. Автоматически создаём пустые коллекции только для нового корпуса. Если коллекция пропала, а в PostgreSQL есть редакции, нужные новым или начатым запросам, требуется восстановление. [Восстановление индекса](./qdrant/index.md#восстановление-индекса)
3. Запустить `core` и `worker`. Runtime объявляет очереди и вызывает `start_models(bindings)` в процессах, выполняющих модельные операции. Model Gateway инициализирует локальные исполнители либо API-клиенты; Runtime сверяет embedding-профиль Core, Worker и индекса до запуска потребителей. При остановке вызывает `close_models()`. [Порядок и готовность моделей](../model-gateway/lifecycle.md) Перед приёмом загрузок проверяет оставшиеся файлы в рабочем томе. Владельцы возобновляют прерванные этапы, Queue Relay публикует незавершённый outbox. [Модели Searcher](../retrieval/pipeline.md) · [Проверка временного тома](./upload-spool/index.md#приём-и-восстановление)

В конфигурацию передаём адреса сервисов, секреты, режимы входа и лимиты попыток по этапам. При недоступном Redis идём полным путём. Сбой RabbitMQ или Relay задерживает передачу работы. Приём вопросов продолжается в пределах лимита незавершённых запросов. Приём файлов зависит также от S3, конвертера/OCR/VLM и рабочего тома; accepted означает подтверждение всех материалов. Сбой Qdrant задерживает поиск или индексацию. [Восстановление](../architecture/lifecycle.md#кто-продолжает-работу-после-рестарта)

Для первого запуска проверяем возраст неподтверждённых записей outbox, отставание доставки и возраст незавершённых задач. Конкретные пороги берём из нагрузки и ограничений кейса. [Проверки первого среза](../faq/mvp-checklist.md)

## Готовность ролей

| Роль | Что требуется до приёма работы |
| --- | --- |
| RAG API | Webhook/секрет/токен, PostgreSQL и запас лимита приёма. Redis/RabbitMQ могут временно отставать благодаря outbox. |
| RAG Core | Нужные модели, совместимый профиль, исправные оба индекса для опубликованного корпуса. Пустой новый корпус допустим и даёт no_evidence. |
| Gateway | Проверенный профиль конвертации, OCR/VLM, S3, том и PostgreSQL. |
| Worker | Супервизор, embedding/generation, оба индекса и том; до запуска проверка остатков. |
| Support web | Настроенный доверенный вход. Пока он не выбран, защищённые ручки возвращают auth_not_configured. |

GET /health/ready проверяет **приём RAG API**, а не полный RAG/модели. Готовность фоновых ролей диагностируется отдельно; живой контейнер не доказывает наличие документов или работоспособность моделей.
