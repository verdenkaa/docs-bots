## Порядок запуска

1. Runtime читает конфигурацию разрешённых провайдеров и строит bindings только для ролей данного процесса. В Core нужны injection, embedding, generation, ocr и опционально reranker; индексатору Worker — embedding и generation для примеров, процессу Document Converter — ocr/vision по профилю. HTTP-процессы и Queue Relay, не выполняющие модельные вызовы, не загружают веса.
2. `start_models(bindings)` проверяет конфигурацию. Локальный адаптер получает закреплённые веса в постоянный дисковый кеш, загружает одну копию на обслуживающий процесс и выполняет пробный inference. Удалённый адаптер создаёт переиспользуемый async-клиент и выполняет минимальную проверку доступности/совместимости API; пробные вызовы могут расходовать квоту. Непроверяемую заранее возможность фиксируем как ограничение выбранного адаптера.
3. Runtime сверяет общий embedding-профиль Core и Worker с настройками индекса, а порог/режим Guardrails — с профилем детектора. Только затем открывает приём работы соответствующими потребителями. На частичном сбое запуска адаптер освобождает уже созданные ресурсы.
4. При штатной остановке Runtime прекращает выдачу новой работы, завершает либо отменяет активные вызовы в пределах срока остановки и вызывает `close_models()`. Закрываем HTTP-клиенты и локальные исполнители. Освобождение локального исполнителя должно включать прекращение его работы, а не только отмену ожидающей корутины.

Повторный `start_models` с тем же binding не создаёт вторую копию; изменение binding в работающем процессе отклоняем до его остановки. `close_models` идемпотентен. Каркас этих действий пока не выполняет; его health checks подтверждают лишь запуск процесса, не готовность моделей.

## Async, очередь допуска и сроки

- Сетевые API используют асинхронный клиент. Локальное вычисление не выполняем в event loop: выбираем управляемый процесс-исполнитель или отдельный сервер инференса. Для коротких вызовов допустимость другого исполнения проверяем отдельно.
- Для каждой роли ограничиваем число активных вызовов `max_concurrency` и длину очереди ожидания. `timeout_s` — положительный бюджет всего вызова, включая очередь допуска, вычисление/сеть и сбор stream; используем монотонный отсчёт. Размер очереди и сетевые лимиты задаёт конфигурация адаптера.
- Guardrails, Searcher и Answer Generator получают собственные бюджеты шагов из конфигурации Runtime и передают их как `timeout_s`. Срок всей попытки остаётся у RAG Core: он ограничивает ожидание пайплайна остатком `attempt.deadline_at`. Это не требует новых параметров у их внешних точек входа. Gateway не продлевает попытку и не делает внутренних повторов.
- Ingestion Worker вычисляет остаток общего срока из взятого задания и передаёт меньший из него и лимита текущего шага (генерация примеров или embedding). Его [супервизор](../ingestion/worker.md#срок-попытки-и-остановка-процесса) контролирует также неотменяемые операции. Новая попытка не должна наследовать занятый локальный исполнитель.
- Отмена ожидания не доказывает остановку вычисления. Локальный адаптер удерживает слот до фактического завершения/остановки исполнителя; зависший исполнитель должен быть остановлен и заменён контролирующим процессом. Для удалённого сервера используем его лимиты исполнения и очереди: закрытие соединения не гарантирует отмену inference. Квоту считаем с учётом этого ограничения.

## Размещение и сохранность

| Вариант | Где лежат веса и кто держит RAM | Что нужно менеджеру контейнеров |
| --- | --- | --- |
| Внешний API | На стороне провайдера. В приложении остаётся сетевой клиент. | Передать адреса и секреты; локальный контейнер модели не нужен. |
| Локально в процессе | Кеш весов на постоянном томе приложения, RAM на каждый обслуживающий процесс. Core и Worker могут дублировать модель. | Подключить том и ресурсы после выбора модели. |
| Собственный сервер инференса | Кеш и RAM у отдельного сервиса; для приложения это `execution="remote"`. | Добавить опциональный сервис с томом, ресурсами и проверкой готовности. |

Сейчас Compose не запускает модельные сервисы и не заполняет Qdrant документами. Наличие здорового Qdrant означает готовность БД, а не наличие эмбеддингов или рабочего RAG. Проверку скачивания и реального inference конкретных моделей выполняем после выбора backend, до объявления такого профиля рабочим.

Изменение embedding-профиля требует согласованной переиндексации, при остановленной смене конфигурации. Изменение Guardrails или генератора также требует проверки совместимости/очистки Exact Cache: поколение корпуса само по себе не инвалидирует ответы после смены правил приложения. [Обновление стенда](../faq/production-update.md).

## Логи

В контекст текущей попытки добавляем `model_role`, `profile_id`, `execution`, время ожидания допуска и время исполнения, исход, код ошибки и доступные usage-счётчики. Для запуска/остановки пишем отдельные технические события без `request_id`. Не логируем ключи, заголовки авторизации, тексты документов, промпты и полные ответы по умолчанию. [Общий формат](../faq/logging.md).

Gateway/Converter имеет отдельный общий срок приёма до accepted; он не получает IngestionAttempt, потому что задание ещё не зарегистрировано. Модельные бюджеты укладываются в этот срок. Управляемый CPU-конвертер останавливает Gateway; индексатором управляет супервизор Worker. Извлечение документа не выполняется в процессе Queue Relay.
