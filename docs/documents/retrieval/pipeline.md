Гибридный профиль ищет по смыслу и по словам. Например, dense помогает сопоставить «не могу войти» с разделом «Восстановление доступа», а BM25 ищет по терминам из вопроса вроде кода ошибки `AUTH-17`. То, как код разбивается на токены, проверяем на реальных примерах. [Гибридный поиск Qdrant](https://qdrant.tech/documentation/search/text-search/hybrid-search/)

~~~mermaid
flowchart LR
    IN["Вопрос и выбранные редакции"] --> D["Эмбеддинг вопроса → dense"]
    IN --> T["Текст вопроса → BM25"]
    D --> F["Qdrant объединяет списки через weighted RRF"]
    T --> F
    F --> R["Reranker переоценивает кандидатов<br/>если включён"]
    R --> OUT["Лучшие фрагменты с источниками"]
~~~

1. Для пустого набора редакций сразу возвращаем пустой список. Для остальных запросов применяем `Match Any` по `revision_id` к каждой ветке до выбора кандидатов. В гибридном запросе один фильтр передаём в оба `prefetch`. Так готовящаяся редакция не займёт места в выдаче, а начатый запрос продолжит поиск по своему набору. [Фильтры в гибридном запросе](https://qdrant.tech/course/beginners/module-3/filtering/)
2. **Dense.** Кодируем вопрос той же версией модели, которой Worker кодирует чанки. Стартовый кандидат — `BAAI/bge-m3`, плотный вектор из 1024 чисел и косинусная метрика в Qdrant. [Карточка BGE-M3](https://huggingface.co/BAAI/bge-m3) · [Конфигурация коллекции](../infrastructure/qdrant/index.md#запуск)
3. **BM25.** Qdrant оценивает совпадения по текстовому индексу payload-поля `text`. Для запроса используем `TextQuery`, а weighted RRF объединяет списки по позициям с весами веток из профиля. Итоговый балл RRF отражает место в выдаче и сам по себе не показывает, достаточно ли данных для ответа. [Полнотекстовый поиск](https://qdrant.tech/documentation/search/text-search/full-text-search/) · [RRF](https://qdrant.tech/documentation/search/hybrid-queries/)
4. **Reranker.** Если включён, приложение одним пакетом передаёт модели пары «вопрос — текст чанка» для ограниченного пула кандидатов. В прототипе используется `BAAI/bge-reranker-v2-m3`. Модель меняет порядок внутри пула. При отключённом шаге сохраняем порядок поиска. [Карточка модели](https://huggingface.co/BAAI/bge-reranker-v2-m3)
5. **Выдача.** Если для выбранного профиля подобран порог релевантности, применяем его перед выдачей. Затем возвращаем до `top_k` фрагментов со ссылочными данными. Даже непустая выдача может не подтверждать ответ. Решение о достаточности контекста остаётся за RAG Core и Answer Generator.

Searcher вызывает `embed_texts([query], "query", timeout_s=embedding_timeout_s)` в [Model Gateway](../model-gateway/entrypoints.md#embed-texts), сверяет `profile_id` с профилем индекса и берёт `vectors[0]`. Runtime-адаптер `find_chunks(query, query_vector, revision_ids, candidate_limit, lexical_priority=has_link)` возвращает список `QdrantHit`. Если reranker включён и кандидаты непусты, Searcher передаёт `query` и `[hit.fragment.text for hit in hits]` в `rerank(..., timeout_s=rerank_timeout_s)`, связывает оценки с кандидатами по `candidate_index`, сортирует по убыванию score (равные — в исходном порядке) и применяет отбор. Наружу возвращает только `fragment`. Бюджеты шагов берёт из конфигурации Runtime. [Контракт Qdrant](../infrastructure/qdrant/contracts.md)

В `day6` прототипа каждая ветка берёт до 10 кандидатов, RRF отдаёт до 10, reranker оставляет до 3. Эти числа подходят для первого сравнительного прогона. Основной рабочий профиль — гибрид; dense-only/BM25-only используем для сравнения и изолированных тестов, а не как скрытый fallback. Выбранный профиль задаём при запуске. Сбой обязательного для профиля компонента возвращаем как техническую ошибку.

Runtime запускает нужные роли через Model Gateway: embedding для Guardrails/Searcher в core и индексатора в worker, reranker только для поиска при включённом шаге. Локальные веса загружает соответствующий адаптер, удалённый использует API; контракт Searcher от этого не меняется. Число одновременных вычислений подбираем по памяти и задержке на сервере. [Порядок запуска](../infrastructure/startup.md)

## Приоритет ссылки в вопросе

Наличие URL/внутренней ссылки не запускает скачивание. Оно выбирает профиль с большим относительным весом BM25, чем dense; для обычного вопроса используется базовый профиль. Searcher определяет вариант по нормализованному query, Runtime получает явные веса и технически исполняет запрос. Нельзя умножать итоговый RRF-score после слияния: это не меняет соотношение веток.

[Weighted RRF Qdrant](https://qdrant.tech/documentation/search/hybrid-queries/#weighted-rrf) поддерживает отдельный вес на prefetch. Порядок весов должен совпадать с порядком dense/BM25 веток. Значения выбираем по тестам со ссылками/кодами. Reranker, если включён, переоценивает уже сформированный пул; влияние приоритета проверяем на итоговой выдаче.

Примеры topic_questions не входят в выдачу Searcher и не могут цитироваться как документ. SearchFragment.images передаётся без смены ID; source_url=None, ссылку на HTML-заглушку строит RAG API.
