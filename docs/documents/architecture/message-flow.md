Access и Support находятся внутри RAG API. Ни собственные контейнеры, ни отдельная очередь для этих компонентов в MVP не требуются.

## Маршруты RabbitMQ

| Очередь | Кто создаёт намерение | Кто забирает | Назначение |
| --- | --- | --- | --- |
| `rag.questions` | RAG API | RAG Core | Обработать надёжно зарегистрированный вопрос. |
| `rag.results` | RAG Core; RAG API, включая Support, для самостоятельных уведомлений | RAG API | Доставить сохранённый ответ, статус или уведомление поддержки. Это расширение прежнего маршрута только для итогов. |
| `ingestion.jobs` | Ingestion Gateway | Ingestion Worker | Проиндексировать готовый Markdown, подготовленный Gateway, и опубликовать редакцию. |

RabbitMQ содержит ссылки на работу, а не тексты, изображения или историю. PostgreSQL хранит вход, результат, задания доставки и состояние попыток. Временный том хранит принятый Markdown до окончания индексации. ID изображений разрешаются через Runtime; бинарные данные в outbox не передаются.

Владелец этапа сохраняет переход и уведомление одной транзакцией. Общий **[Queue Relay](../infrastructure/queue-relay.md)** в `core` публикует готовые записи от имени обоих контейнеров. Он не запускает функции напрямую и не принимает решений об эскалации. Каркас использует DeliveryRef для rag.results и RequestRef для rag.questions; обработчики и адаптеры пока остаются заглушками.

~~~mermaid
sequenceDiagram
  participant T as Telegram
  participant A as RAG API
  participant X as RAG API · Access
  participant P as PostgreSQL
  participant L as Queue Relay
  participant Q as RabbitMQ
  participant C as RAG Core
  T->>A: Update с отправителем и входом
  A->>X: Проверить допуск сотрудника
  A->>P: Дедупликация, один активный вопрос, вход + outbox
  P-->>A: Приём подтверждён
  A-->>T: Подтвердить update
  L->>P: Прочитать готовый outbox
  L->>Q: Опубликовать ссылку в rag.questions
  Q->>C: Доставить уведомление
  C->>P: Взять вопрос и закрепить поколение
  C->>C: Выполнить пайплайн
  C->>P: Сохранить итог или намерение поддержки
  C-->>Q: ACK после надёжного перехода
  L->>Q: Опубликовать готовую доставку в rag.results
  Q->>A: Доставить уведомление
  A->>P: Прочитать сохранённый текст и ссылки
  A->>T: Отправить текст и нужные изображения
~~~

Схема показывает допущенный новый вопрос; отказ доступа и занятость сотрудника завершают приём до `rag.questions`. Если результат требует поддержки, ссылка на тикет доставляется после его создания, а не выдумывается в момент решения Core.

## Когда работа считается принятой

1. **Приём Telegram.** После проверки доступа RAG API согласует дедупликацию update и занятие слота сотрудника в PostgreSQL. Повтор уже принятого update получает прежний исход. Другой вопрос занятого сотрудника не регистрируется как RAG-вопрос: обновление подтверждаем, уведомление о занятости проходит через общий лимитер доставки. Это не повод просить Telegram повторять update.
2. **Приём документа.** Gateway проверяет отправителя и вызывает Document Converter. До подтверждения приёма изображения сохраняются в S3, а полученный Markdown с ID/описаниями — во временном томе. Затем редакция и outbox `ingestion.jobs` регистрируются одной транзакцией. Оригинал не сохраняется: до этого коммита повтор загрузки обеспечивает отправитель, после коммита Worker восстанавливается по Markdown.
3. **Публикация уведомления.** Relay ждёт подтверждения брокера и проверяет маршрутизацию, затем отмечает outbox отправленным. Потеря подтверждения допускает повтор; потребитель проверяет сохранённое состояние.
4. **Завершение этапа.** Потребитель подтверждает RabbitMQ после сохранённого результата, плана повтора либо проверки, что уведомление уже не требует действий. Готовый ответ не генерируется заново при повторе доставки.

При недоступности PostgreSQL новый вопрос нельзя считать принятым. При недоступности RabbitMQ приём возможен в пределах настроенной ёмкости: outbox публикуется после восстановления. Глобальные пределы нагрузки отдельно от отказа «сотрудник занят» остаются технической политикой RAG API.

## Порядок и повторы

- Общая очередь вопросов остаётся: разные сотрудники ждут доступных слотов Core. Ограничиваем параллелизм и prefetch. Очереди следующих вопросов одного сотрудника нет.
- На один чат — одна активная отправка; все ответы, изображения, статусы и сообщения Support используют общий лимитер RAG API. Сохранённая последовательность доставок нужна даже при единственном активном вопросе.
- Перед отправкой статуса ожидания проверяем, что итог ещё не готов; устаревшее уведомление пропускаем. Для составного ответа сохраняем прогресс по частям: подтверждённый текст не отправляем повторно только из-за сбоя картинки. Неизвестный исход отдельной отправки всё ещё допускает дубликат; exactly-once для Telegram не обещаем.
- При ограничении Telegram учитываем `retry_after`. Частоту исходящих сообщений не приравниваем к RPS вопросов: один ответ может потребовать текст и несколько изображений.
- Ingestion Worker выполняет задания последовательно. Повтор использует тот же Markdown, результаты подготовки и ID точек, без оригинала и повторной конвертации; неизвестная запись Qdrant ждёт сверки. После публикации повторяется только незавершённая уборка.

## Уведомления и поддержка

Статус после 10 секунд создаёт фоновый контроллер RAG API по сохранённому времени приёма, независимо от занятости Core. Повторы и рестарты не обнуляют это время. Достижение 20 секунд фиксируется как превышение целевой метрики, без отмены пайплайна и создания тикета.

Core сохраняет намерение автоматической эскалации вместе со своим итогом. Support подбирает такие намерения через Runtime, создаёт тикет идемпотентно и сохраняет уведомление для RAG API. Ручную просьбу и ответ на подтверждение RAG API передаёт Support как управляющие действия, без очереди нового RAG-вопроса. Таймер 10 минут хранится в PostgreSQL, не в памяти обработчика; для него отдельная RabbitMQ-очередь в MVP не требуется.
