:::warning Проект запуска
Рабочий вариант для одного сервера с Compose. Образы, ресурсы, доступность HTTPS и настройки хранилищ уточним по условиям кейса.
:::

## Что поднимаем

| Сервис | Что запускает | Постоянные данные |
| --- | --- | --- |
| `core` | RAG API, RAG Core, потребителя `rag.results` и один активный [Queue Relay](./queue-relay.md) для всех маршрутов. | В подключённых хранилищах. |
| `worker` | Ingestion Gateway и одного последовательного Ingestion Worker под отдельным [супервизором](../ingestion/worker.md#срок-попытки-и-остановка-процесса). | `worker_spool` для файлов незавершённых загрузок. |
| `postgres` | Базу состояния и outbox. | `postgres_data` подключаем к каталогу данных выбранного образа PostgreSQL. |
| `rabbitmq` | Три долговечные очереди с сохраняемыми сообщениями. | `rabbitmq_data` для состояния брокера. |
| `qdrant` | Поисковую коллекцию. | `qdrant_data` подключаем к `/qdrant/storage`. |
| `redis` | Exact Cache. | Для первого среза достаточно памяти. |

`core` и `worker` собираем из одной Python-кодовой базы с разными командами запуска. В стартовой схеме без балансировщика выбираем webhook или long polling по условиям сервера. Для HTTP в синке указаны Gunicorn и процессы Uvicorn. Фоновые роли запускаем отдельно от HTTP-процессов внутри контейнера, чтобы масштабирование HTTP не запускало повторно Relay, poller или потребителя доставки. [Варианты приёма Telegram](../telegram/module/index.md#два-способа-приёма) · [Итоги синка, D-07](../faq/drafts/architecture-team-sync.md)

## Что переживает перезапуск

Данные PostgreSQL и Qdrant переживают рестарт контейнера, его пересоздание и перезагрузку сервера, если подключены те же именованные тома и диск сохранился. Для PostgreSQL путь монтирования берём из документации выбранной версии образа. [Тома Docker](https://docs.docker.com/engine/storage/volumes/) · [Образ PostgreSQL](https://hub.docker.com/_/postgres) · [Запуск Qdrant](https://qdrant.tech/documentation/quickstart/)

| Событие | Что происходит |
| --- | --- |
| `docker compose restart` или пересоздание контейнера с тем же томом | Базы снова читают сохранённые данные с тома. |
| Перезагрузка сервера | Тома остаются на диске. Автоматический запуск контейнеров задаётся отдельно, например политикой `restart: unless-stopped`. [Политики перезапуска Docker](https://docs.docker.com/engine/containers/start-containers-automatically/) |
| `docker compose down -v` | Compose удаляет именованные тома, объявленные проектом. [Docker Compose down](https://docs.docker.com/reference/cli/docker/compose/down/) |
| Утрата диска или тома Qdrant | Чанки и векторы восстанавливаем из снимка Qdrant либо повторной загрузкой документов. [Восстановление индекса](./qdrant/index.md#восстановление-индекса) |

## Порядок запуска

1. Поднять хранилища и брокер во внутренней сети. Проверить подключение с учётными данными приложения и доступность нужных томов.
2. Применить миграции PostgreSQL из образа приложения. Одним шагом проверить коллекцию и индексы Qdrant для выбранного профиля. Автоматически создаём пустую коллекцию для нового корпуса. Если коллекция пропала, а в PostgreSQL есть редакции, нужные новым или начатым запросам, требуется восстановление. [Восстановление индекса](./qdrant/index.md#восстановление-индекса)
3. Запустить `core` и `worker`. Runtime объявляет очереди и загружает модели в процессах поиска и индексации до начала их работы. Перед приёмом загрузок проверяет оставшиеся файлы в рабочем томе. Владельцы возобновляют прерванные этапы, Queue Relay публикует незавершённый outbox. [Модели Searcher](../retrieval/pipeline.md) · [Проверка временного тома](./upload-spool/index.md#приём-и-восстановление)

В конфигурацию передаём адреса сервисов, секреты, режимы входа и лимиты попыток по этапам. При недоступном Redis идём полным путём. Сбой RabbitMQ или Relay задерживает передачу работы. Приём вопросов продолжается в пределах лимита незавершённых запросов. Приём файлов зависит от рабочего тома, PostgreSQL и лимитов загрузки. Сбой Qdrant задерживает поиск или индексацию. [Восстановление](../architecture/lifecycle.md#кто-продолжает-работу-после-рестарта)

Для первого запуска проверяем возраст неподтверждённых записей outbox, отставание доставки и возраст незавершённых задач. Конкретные пороги берём из нагрузки и ограничений кейса. [Проверки первого среза](../faq/mvp-checklist.md)
