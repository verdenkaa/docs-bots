:::warning Рабочая спецификация
Внешний способ загрузки, доступ, лимиты и способ сообщать итог индексации определим по кейсу.
:::

Точка входа для любого адаптера — [`accept_upload(upload) -> UploadResult`](./entrypoints.md#accept-upload). Адаптер передаёт поток байтов, имя источника, его URL при наличии и ID документа при обновлении.

## Как подключить источник

| Вариант | Что делает адаптер до вызова `accept_upload` |
| --- | --- |
| Ручной импорт через CLI | Открывает локальный файл как поток. При обновлении оператор передаёт `document_id`. |
| Административная HTTP-загрузка | Проверяет доступ и переводит полученный файл в поток. Способ аутентификации, путь и HTTP-формат определяем, если выберем этот вариант. |
| Импорт из внешней системы | Получает байты и метаданные источника. Если система даёт стабильный ID, адаптер хранит его соответствие с `document_id`. |

Способ запуска адаптера и проверка прав зависят от источника. Смена адаптера сохраняет Python-контракт, очередь и обработку Worker. `source_url` служит ссылкой для ответа. Gateway получает содержимое в `upload.content` и не скачивает файл по этому URL.

## Как принимаем файл

1. Gateway проверяет метаданные и создаёт UUID редакции. При первой загрузке адаптер передаёт `document_id=None`. Для обновления передаёт известный ID, а при неизвестном ID получит `unknown_document`.
2. [`stage_upload`](../infrastructure/upload-spool/contracts.md#stage-upload) читает поток, считает размер по принятым байтам и сохраняет файл с манифестом под внутренним ключом. Имя файла используется как метаданные, путь генерирует адаптер тома. Пустая загрузка, некорректный вход и превышение лимита заканчиваются отказом до регистрации.
3. [`register_revision`](../infrastructure/postgresql/ingestion.md#register-revision) сохраняет редакцию, состояние задания и outbox для `ingestion.jobs` одной транзакцией. Queue Relay доставит уведомление отдельно, поэтому приём завершается сразу после коммита.
4. Результат `accepted` содержит `document_id` для будущего обновления и `job_id` для диагностики. На этом этапе задание принято, публикация ещё впереди. Разбор файла и решение о пригодности текста выполняет Worker.

~~~python
result = await accept_upload({
    "content": file_stream,  # AsyncIterable[bytes] от адаптера
    "source": {"filename": "Руководство.pdf", "source_url": None},
    "document_id": None,
})
~~~

## Что делать при сбое приёма

| Исход | Действие Gateway или адаптера |
| --- | --- |
| Запись файла прервалась | Задание ещё не зарегистрировано. Адаптер тома убирает незавершённую запись, а после падения её подбирает проверка тома при запуске. |
| PostgreSQL подтвердил отказ регистрации | Gateway удаляет временную загрузку и возвращает отказ. Если удаление прервалось, загрузку подберёт проверка тома. |
| Итог коммита неизвестен | Gateway оставляет файл и поднимает `StorageError`. Для диагностики пишет ID редакции. Если коммит состоялся, Queue Relay и Worker продолжают работу по этой редакции. |
| Адаптер потерял ответ о приёме | Перед повторной загрузкой нужно выяснить исход первой. Каждый новый вызов `accept_upload` создаёт новый ID редакции. Если выбранному транспорту нужен автоматический повтор, его ключ идемпотентности согласуем отдельно. |

После приёма состояние задания читается по `job_id` в `document_revisions`. Способ показать это состояние оператору выбираем вместе с внешним адаптером.
