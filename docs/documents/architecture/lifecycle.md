Access и Support далее обозначают компоненты RAG API: допуск и поддержку. Их состояние хранится в PostgreSQL через адаптеры Runtime.

## Вопрос и доставка

| Состояние | Кто и что фиксирует | Откуда продолжаем |
| --- | --- | --- |
| Принят | RAG API после Access атомарно сохраняет вход, сотрудника, время приёма, активный слот и outbox. | Повтор update относится к прежнему исходу; другой вопрос сотрудника не регистрируется. |
| Обрабатывается | Core берёт попытку, закрепляет поколение, получает текст/OCR и выполняет пайплайн. | После технического сбоя повторяет шаги по тому же входу и поколению, если остались попытки. |
| Ответ готов | Core сохраняет Markdown с источниками и ID изображений, снимает закрепление поиска и создаёт доставку. | RAG API читает итог без новой генерации; Guardrails больше не выполняется при повторе этой доставки. |
| Нужна поддержка | Core сохраняет бизнес-причину и устойчивое намерение Support вместе с завершением обработки. | Support создаёт тикет, затем RAG API доставляет ссылку. При задержке допустимо честное уведомление «передача готовится», без фиктивного тикета. |
| Доставка выполняется / ждёт повтора | RAG API сохраняет подтверждённые части, исход отправки и время повтора. | Повторяем только незавершённые части; неизвестный исход Telegram всё ещё допускает дубликат. |
| Вопрос завершён | Доставлен итоговый ответ/уведомление об эскалации либо зафиксирована окончательная ошибка/неизвестный итог доставки. | Слот сотрудника освобождается; новые вопросы можно принимать. Тикет живёт независимо от этого слота. |

Готовность ответа, доставка и закрытие тикета — разные события. Активный слот удерживается до конечного исхода доставки ответа либо уведомления об эскалации, а не до закрытия тикета. Ручное десятиминутное ожидание Support само по себе слот не занимает; если обычный вопрос ещё выполняется, для него по-прежнему действует ограничение одного активного вопроса.

## Ожидание и технические сроки

- С первого приёма вопроса измеряем отдельно время до готовности ответа и до доставки. Время приёма сохраняется один раз; OCR, очередь, повторы и рестарты входят в ожидание пользователя.
- После 10 секунд без готового итога фоновый контроллер RAG API сохраняет одно намерение отправить статус «в работе». Перед отправкой перепроверяет готовность итога; устаревший статус пропускается.
- **20 секунд — целевая метрика.** Более поздний ответ остаётся действительным. Само превышение не отменяет модельный вызов, не освобождает слот и не создаёт тикет.
- Технические сроки попытки, модели и доставки конечны, но задаются отдельно от метрики 20 секунд. Если попытка истекла, её результат не может перезаписать итог новой попытки. Повторы ограничены; при окончательном техническом сбое пользователь получает пояснение, а не сообщение об отсутствии знаний.
- Отмена ожидания не гарантирует остановку вычисления. Model Gateway удерживает занятые ресурсы до фактического завершения/остановки исполнителя; блокирующий код не работает в event loop. [Ограничения моделей](../model-gateway/lifecycle.md)

## Поддержка {#support}

| Событие | Действие Support | Условие продолжения |
| --- | --- | --- |
| Низкое сходство с примерами темы, пустой корпус/выдача или нехватка подтверждений | Подбирает сохранённое намерение автоматической эскалации и создаёт тикет с контекстом. | Без десятиминутной отсрочки. Пустота индекса из-за технического сбоя не выдаётся за низкую релевантность. |
| Ручная просьба пользователя | Сохраняет обращение и время проверки через 10 минут; сообщает об ожидании. | Новые самостоятельные вопросы разрешены, если нет активного RAG-вопроса. |
| Наступило время проверки | Через RAG API спрашивает «Помощь ещё нужна?». | Только ответ «Да» создаёт тикет; «Нет» завершает ожидание. Без ответа автоматического создания нет. |
| Тикет создан | Сохраняет ID/URL и уведомление пользователю. | Пользователь переходит в web-систему, оператор работает там. |
| Повтор команды/подтверждения, рестарт либо совпадение ручной и автоматической эскалации одного обращения | Проверяет сохранённое состояние и ключ идемпотентности. | Не создаёт второй тикет и не возобновляет уже завершённое ожидание. |
| Тикет-система недоступна | Сохраняет намерение, ошибку и план повтора; информирует о задержке. | Не обещает состоявшуюся передачу до подтверждения создания. |

Изначально кнопки оператора нет. После явного недовольства ответом или просьбы о человеке после ответа показываем кнопку ручного вызова. При отсутствии подтверждённого ответа создаём тикет автоматически и даём ссылку вместо кнопки. Просьба до первого ответа не запускает ожидание. Минимальная история — исходный вопрос и фактический ответ; case уникален по request_id, повтор не запускает новый таймер. Срок хранения неподтверждённых ожиданий задаётся отдельной политикой хранения. [Правила Support](../telegram/module/support.md) Управляющие действия поддержки не являются новым вопросом к модели. При отзыве допуска Access проверяется до выполнения пользовательского действия.

Ручная просьба доступна только после подтверждённой текстовой части ответа и не отменяет оставшуюся доставку картинок. Привязку к вопросу, stage и уникальность case проверяем атомарно в PostgreSQL; при гонке callback/фонового перехода второй тикет не создаётся. Это защита от гонки реальных действий, а не таймер на 20-й секунде.

## Кто продолжает работу после рестарта

| Ситуация | Владелец | Что восстанавливает |
| --- | --- | --- |
| Штатный рестарт брокера/потребителя | RabbitMQ | Сохранённые очереди и сообщения; неподтверждённые уведомления доставляются повторно. |
| Публикация outbox не подтверждена | Queue Relay | Допубликовывает записи без отметки успеха. Получатель проверяет повтор по состоянию работы. |
| Прервана попытка Core, доставки или индексации | Владелец этапа через Runtime | Возобновляет готовую работу либо фиксирует конечный сбой; потерявшая право попытка не публикует результат. |
| Статус ожидания или части ответа ещё не доставлены | RAG API | Проверяет актуальность уведомления и сохранённый прогресс, затем продолжает доставку. |
| Ручное ожидание / создание тикета прервано | Support | Сохранённые сроки, подтверждения и намерения. Таймер не начинается заново после рестарта. |
| Утрачено содержимое RabbitMQ | Runtime и владельцы этапов | Восстанавливают маршруты и готовые уведомления из состояния PostgreSQL с учётом сроков и окна доставки. |

Проверку незавершённой работы выполняем при запуске и периодически. Она не зависит от нового сообщения пользователя. Queue Relay публикует, а бизнес-решение о продолжении принимает владелец этапа. [Протокол восстановления](../infrastructure/postgresql/outbox.md#recover-pending-work) подбирает вопросы, самостоятельные доставки и задания; ожидания/creating-case подбирает отдельный цикл Support.

## Загрузка и публикация

| Состояние | Что происходит | Правило восстановления |
| --- | --- | --- |
| Документ конвертируется | Gateway вызывает Document Converter, сохраняет изображения в S3 и связывает их с плейсхолдерами. Оригинал существует только как вход текущего вызова. | При сбое до надёжного приёма отправитель повторяет загрузку; задание ещё не подтверждено. |
| Markdown принят | Gateway сохраняет результат конвертации и метаданные, затем задание с outbox; оригинал не сохраняется. | Уже принятое задание восстанавливается по тому же Markdown и изображениям, без повторной конвертации. |
| Редакция готовится | Worker сохраняет подготовленные чанки/примеры, ожидаемые наборы и начало записи. | Повтор не генерирует заново уже закреплённый набор. При неизвестной записи Qdrant повтор/удаление блокируются до сверки. |
| Редакция опубликована | После проверки обоих индексов Worker переключает видимость и поколение одной транзакцией PostgreSQL. | Новые вопросы используют новый состав; временный Markdown можно удалить. |
| Старая редакция ждёт очистки | Удаляются чанки и примеры, не нужные активному составу и закреплённым вопросам. | Незавершённая уборка повторяется отдельно от публикации; метаданные HTML-заглушки и изображения не удаляются этим переходом. |

Супервизор Worker контролирует общий срок и отдельные блокирующие шаги. Зависший процесс и дочерние исполнители останавливаются до повторного выполнения. Неизвестный исход записи в Qdrant требует отдельной сверки; запрет коммита просроченной попытки сам по себе вычисление не останавливает. [Действующий протокол Worker](../ingestion/worker.md#срок-попытки-и-остановка-процесса) сохраняется и расширяется на индекс примеров.

## Что происходит при сбое

| Сбой | Поведение |
| --- | --- |
| Итог записан, ACK потерян | Повтор читает состояние и подтверждается без новой генерации/создания тикета. |
| Модель ответила, но коммит неизвестен | Проверяем состояние; повторяем вычисление только если надёжного итога нет и попытка разрешена. |
| Картинка не получена | Сохраняем текстовый ответ и описание; фиксируем сбой изображения. Повторы ограничены, текст не теряется из-за недоступного файла. |
| Индекс новой редакции частичен | Сохраняем старую опубликованную редакцию. После сверки восстанавливаем полный набор чанков и примеров. |
| Изображение утрачено в S3 | Фиксируем потерю материала; не подменяем его другим содержимым по тому же ID. Оригинала для повторного извлечения у нас нет. |
| Конвертация / S3 завершились, регистрация задания прервалась | При неизвестном коммите сохраняем Markdown и изображения до проверки PostgreSQL. При подтверждённом отказе удаляем временную загрузку. Уборка непривязанных S3-объектов — отдельная операция по политике ссылок, не удаление по факту ошибки. |

## Отзыв допуска сотрудника

Отключение действует на регистрацию новых вопросов. Вопрос, принятый до коммита отключения, проходит обычный пайплайн и доставляется полностью: текст, оставшиеся изображения либо ссылка автоматически созданного тикета. Core не отменяет такой вопрос и не освобождает слот досрочно. Технические сроки и ограниченные повторы продолжают действовать.

Если приём и отключение пришли одновременно, их сериализует Runtime по user_id: принято до отключения — завершаем; отключено до приёма — denied. Повтор того же принятого update возвращает прежний исход, а не становится новым запрещённым вопросом.
