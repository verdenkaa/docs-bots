:::warning Границы показателей
«Успешный автоответ» ниже — согласованное операционное определение для демонстрации,
не подтверждённое решение проблемы пользователя. Темы определяются словарём,
причины слабых мест проверяет человек. В режиме ДЕМО все цифры синтетические.
:::

## Один экран для кейса

В серверной Grafana, папка **RAG**, откройте **RAG · Бизнес-аналитика**
(`uid=rag-business`, путь `/d/rag-business`). Доступ — через существующий
SSH-туннель и вход администратора Grafana. Дашборд добавляется к четырём
[техническим экранам](./monitoring.md).

На одном экране находятся:

- количество вопросов, автоответов без эскалации, их доля, передачи оператору,
  ожидание результата и медианное время до ответа;
- динамика нагрузки, доли автоответов и тем;
- сравнение тем с предыдущим смежным периодом такой же длительности;
- частые вопросы без подтверждений, зарегистрированное недовольство,
  кандидаты для FAQ и причины передачи оператору.

Фильтры: **Данные** (рабочие / ДЕМО), **Канал** (Telegram / web), **Тема**,
диапазон Grafana. По умолчанию — рабочие данные за семь дней, обновление раз в минуту.
Ссылки вверху переключают рабочие данные и демонстрацию.

## Как показать на защите

1. Нажмите **Демо · 7 дней**. В верхней плашке останется явная пометка
   **ДЕМО (синтетические данные)**.
2. Покажите базовые KPI и распределение тем: это базовая аналитика администратора.
3. В таблице трендов сравните **Сейчас**, **Ранее**, абсолютное изменение и процент роста.
   В демо растут вопросы про маршрут согласования и списание мебели.
4. Откройте таблицу приоритетов: частота вместе с отсутствием подтверждений
   показывает, какие инструкции и настройки поиска проверить в первую очередь.
   Недовольство ответами — отдельный повод проверить ответ и сценарий продукта.
5. Переключитесь на рабочие данные. Демо не заполняет историю бота или тикеты.

Демонстрационные строки вычисляются представлением PostgreSQL за 28 полных
UTC-дней относительно текущей даты. Они воспроизводимы внутри суток, включают
автоответы, автоматические и ручные эскалации, технические исходы. Они не являются
оценкой реального качества или доказательством сокращения времени решения.

## Формулы и источники

Все панели выбирают когорту **принятых** вопросов по сохранённому `received_at`:
начало диапазона включается, конец исключается. Одна строка соответствует одному
`request_id`; повторы очередей, доставки и HTTP не добавляют вопросов. Приём,
готовый результат и состояние Support читаются из PostgreSQL, а не восстанавливаются
по разности логов.

| Показатель | Определение |
| --- | --- |
| Принято вопросов | Все сохранённые вопросы когорты, включая ещё обрабатываемые. Отказы до регистрации не входят. |
| Автоответ без эскалации | `result.kind=answered`; Telegram полностью доставил ответ с нормальными квитанциями без `length_fallback`, либо web-результат доступен после коммита. Нет эскалации и зарегистрированного недовольства. |
| Доля успешных автоответов | Автоответы без эскалации / все вопросы когорты с сохранённым результатом × 100%. В знаменателе также Support, уведомления и технические ошибки. Вопросы без результата исключены и показаны отдельно. |
| Передано оператору | Сохранённый результат `support` либо case в `creating/open/closed`, в том числе после автоответа. Ожидание, неподтверждённая помощь и отмена не считаются передачей. |
| Недовольство | Принятая Telegram-реакция `offer/dissatisfied` либо Support case с причиной `dissatisfied`, включая web. Отсутствие этой реакции не доказывает удовлетворённость. |
| Ожидают результата | У вопроса ещё нет сохранённого результата Core. |
| Медиана до ответа | Для `answered`: от приёма до первой нормальной текстовой квитанции Telegram; для web — до `web_requests.completed_at`. Отрицательные и отсутствующие замеры исключаются. Это не время решения проблемы. |
| Рост темы | `(вопросы сейчас − вопросы ранее) / вопросы ранее × 100%`. Предыдущий диапазон смежный и равен выбранному по длительности. Нулевая база → «Нет базы сравнения», процент остаётся пустым. |
| Частый вопрос | Точное совпадение после перевода в нижний регистр, удаления крайних и сжатия внутренних пробелов; минимум два вопроса. Смысловые перефразирования не объединяются. |

На пустом диапазоне счётчики равны нулю, доли и медианы показывают **Нет данных**.
Графики не добавляют искусственные нули. Группировка графиков — UTC-сутки;
отображение времени — Europe/Moscow. Крайние сутки могут быть неполными.

Состояние когорты **текущее**: поздняя передача оператору или реакция меняет
показатель за прошлый период. Это не журнал неизменяемых исторических снимков.
История ограничена фактически сохранёнными строками и политикой очистки PostgreSQL,
а не семидневным retention Loki.

## Темы и сигналы слабых мест

Словарь находится в `deploy/monitoring/topics.json`: командировки, мебель,
согласование, доступ и документы БАРС Офиса. Используются сохранённый OCR-текст,
текст вопроса или подпись изображения. Первая совпавшая группа ключевых подстрок
побеждает. Если совпадений нет, вопрос попадает в **Другое / не определено**.
Словарь можно заменить под документы кейса без вызова моделей и изменения DTO.
После изменения повторно запустите `analytics-init`: темы прошлых вопросов также
будут пересчитаны. Демо имеет собственную фиксированную разметку сценариев.

Таблица приоритетов сортируется по числу передач с `no_evidence`, затем по
недовольству и частоте. `no_evidence` может означать пробел инструкции,
неудачный поиск, пустой корпус или недостаточное подтверждение при генерации.
Растущая тема может отражать изменение продукта, сезонность или непонятный процесс.
`out_of_scope` показывается отдельно и автоматически не считается дефектом.
Следующий шаг в таблице — рекомендация для разбора, не установленный диагноз.

Тексты вопросов доступны администратору Grafana в таблицах; в Loki они не
добавляются. Тексты для отображения обрезаются после группировки. Имена сотрудников,
Telegram ID, ответы и секреты в аналитическое представление не включаются.

## Подключение на сервере

Корневой `compose.yaml` использует прежние конфиги Loki/Alloy и технические
дашборды из `container-manager/monitoring/`. Бизнес-аналитика принадлежит серверной
сборке: код, JSON и provisioning находятся отдельно в `deploy/monitoring/`.
Локальный профиль менеджера продолжает подключать только четыре технических экрана.

После применения миграций одноразовый `analytics-init` создаёт схему
`rag_analytics`, представления и роль `rag_analytics_reader`. Существующие таблицы
приложения и DTO не меняются. Читатель получает только `USAGE` на аналитическую
схему и `SELECT` на итоговое представление; подключение также имеет read-only по
умолчанию и таймаут запроса 10 секунд. Grafana ждёт успешного завершения setup.
Доступ к хранилищам и моделям для setup не нужен, кроме PostgreSQL.

Пароль читателя — `GRAFANA_ANALYTICS_PASSWORD`; при пустом значении используется
`GRAFANA_PASSWORD`. Пароль владельца PostgreSQL в Grafana не передаётся.
Повтор setup обновляет пароль читателя и определения представлений. Произвольный
`RAG_PG_SCHEMA` поддерживается; аналитическая схема имеет фиксированное имя.
Для создания роли первоначальный setup требует владельца стенда с `CREATEROLE`
или superuser; штатный PostgreSQL из Compose создаёт такого владельца.

Из корня на сервере после обновления исходников:

```bash
python container-manager/monitoring/generate_dashboards.py
docker compose up -d --build analytics-init grafana
```

Полный `docker compose up -d --build` также подключит аналитику. Никакие тома
удалять не нужно. JSON перечитывается раз в 30 секунд; после изменения схемы,
словаря или пароля отдельно повторите setup и пересоздайте Grafana:

```bash
docker compose run --rm analytics-init
docker compose up -d --force-recreate grafana
```

Provisioning и доступ читателя соответствуют официальным описаниям
[PostgreSQL datasource](https://grafana.com/docs/grafana/latest/datasources/postgres/configure/)
и [SQL-макросов Grafana](https://grafana.com/docs/grafana/latest/datasources/postgres/query-editor/).

## Проверка

```bash
python -m deploy.monitoring.generate_dashboard
python -m deploy.monitoring.verify --engine docker
```

Нужны зависимости приложения и Docker; поддерживается `--engine podman`.
Проверка создаёт временные PostgreSQL 17 и Grafana 12.1.1, реальную схему моделей
приложения с искусственными вопросами и отдельного читателя. Проверяются
нормальная/частичная/fallback-доставка, web, поздняя эскалация, недовольство,
формулы KPI, фактические запросы Grafana для live/demo, фильтры, пустые диапазоны,
повтор setup и сохранение ID дашборда после рестарта. `.env` не читается,
постоянные тома и рабочие сервисы не используются. `--hold` оставляет тестовую
Grafana до Ctrl+C для визуальной проверки, затем удаляет только созданные контейнеры.
