## Запуск

Поднимаем один экземпляр Qdrant с именованным томом `qdrant_data`, подключённым к `/qdrant/storage`. Runtime создаёт коллекцию `document_chunks` для нового корпуса и при повторном запуске сверяет её параметры. Если у PostgreSQL есть редакции, нужные новым или начатым запросам, отсутствие коллекции означает необходимость восстановления. [Запуск Qdrant](https://qdrant.tech/documentation/quickstart/) · [Коллекции Qdrant](https://qdrant.tech/documentation/manage-data/collections/)

| Что настраиваем | Для чего |
| --- | --- |
| Именованный вектор `dense` | Семантический поиск. Для кандидата BGE-M3 используем 1024 измерения и косинусную метрику. |
| Payload-индекс `keyword` по `revision_id` | Фильтр набора редакций для обеих веток поиска. ID храним как строки UUID. |
| Текстовый payload-индекс по `text` с `scoring: true` | BM25 в гибридном профиле. Токенизацию и русский стемминг выбираем по корпусу. |
| `optimizers_config.prevent_unoptimized: false` | Для выбранной версии Qdrant локальный шард применяет журнал записи WAL при загрузке, прежде чем станет доступен. Это условие [процедуры сверки](#сверка-незавершённых-записей). |

Для BM25 по payload через `TextQuery` фиксируем совместимую пару Qdrant и `qdrant-client` с поддержкой API, появившейся в обеих версиях 1.20.0. Настройка индекса из прототипа `TextScoringParams` заменяется на `scoring=True` в Python-клиенте. [Релиз сервера](https://github.com/qdrant/qdrant/releases/tag/v1.20.0) · [Релиз клиента](https://github.com/qdrant/qdrant-client/releases/tag/v1.20.0) · [Настройка BM25](https://qdrant.tech/documentation/search/text-search/full-text-search/#create-a-full-text-index-with-scoring)

Core и Worker используют одну конфигурацию эмбеддингов с закреплённой версией модели. При переходе на несовместимую модель пересчитываем векторы из сохранённых текстов чанков. Совпадения размерности недостаточно для совместимости. [Конвейер Searcher](../../retrieval/pipeline.md)

## Структура точки

Одна точка представляет один чанк и содержит один вектор `dense`. Для BM25 Qdrant индексирует уже сохранённый текст чанка. ID точки вычисляем как `uuid5(revision_id, str(chunk_no))`, нумерация с нуля. При повторе ID сохраняются, у новой редакции свой набор точек. Массив вектора в примере укорочен. [Пример замены редакции](../../ingestion/index.md#пример-замены-редакции) · [Точки Qdrant](https://qdrant.tech/documentation/manage-data/points/)

```json
{
  "id": "545f64ff-7692-579a-842a-31f87e6522df",
  "vector": { "dense": [0.15, -0.23, 0.41] },
  "payload": {
    "document_id": "43f95f66-7343-4cbc-beb5-19fd36a8ca77",
    "revision_id": "bb32ecbf-082b-4497-a41f-4b61aa56a139",
    "chunk_no": 3,
    "text": "Фрагмент инструкции по установке.",
    "source_name": "Руководство по установке.pdf",
    "locator": { "page": 4, "section": "Установка" }
  }
}
```

Локатор зависит от формата документа. Если есть доступный адрес источника, добавляем `source_url` в payload. Searcher возвращает эти сведения с идентификаторами документа, редакции и точки. [Формат фрагмента](../../retrieval/entrypoints.md#search)

## Публикация, поиск и очистка

- **Запись.** Ingestion Worker добавляет фрагменты новой редакции рядом со старыми. После подтверждения `write_revision_points` публикует редакцию в PostgreSQL.
- **Чтение.** RAG Core восстанавливает набор редакций закреплённого поколения из PostgreSQL и передаёт его Searcher. Обе ветки поиска в Qdrant получают один фильтр `Match Any` по `revision_id`. [Match Any в Qdrant](https://qdrant.tech/documentation/search/filtering/#match-any)
- **Очистка.** Ingestion Worker удаляет точки по `revision_id`, когда PostgreSQL разрешил очистить неактивную редакцию. Повтор очистки затрагивает ту же редакцию. [Правила закрепления и очистки](../postgresql/index.md#повтор-и-восстановление)

Способ передать фильтр и его стоимость проверим на реальном размере корпуса. Подготовленный индекс становится видимым для новых запросов после публикации в PostgreSQL. [Данные и версии](../../architecture/data-and-versions.md)

## Сверка незавершённых записей

Процедура для одного экземпляра Qdrant в MVP. Оператор выполняет её в окно обслуживания. Пока идёт сверка, обычные записи, включая удаление, приостановлены.

1. Приостановить обработку вопросов и остановить `worker` вместе с его дочерними процессами. Отключить остальных писателей в коллекцию, если они есть. Убедиться, что старые процессы и их соединения завершены.
2. Перезапустить Qdrant с тем же томом и дождаться успешной загрузки коллекции и всех локальных шардов. При `prevent_unoptimized=false` Qdrant 1.20.0 применяет незавершённые операции из журнала WAL при загрузке шарда. Рестарт закрывает запросы старого процесса сервера. Если коллекция не загрузилась штатно, признак в PostgreSQL сохраняем и разбираем сбой. [Загрузка локального шарда в Qdrant 1.20.0](https://github.com/qdrant/qdrant/blob/v1.20.0/lib/collection/src/shards/local_shard/mod.rs#L520-L540) · [Воспроизведение WAL](https://github.com/qdrant/qdrant/blob/v1.20.0/lib/collection/src/shards/local_shard/mod.rs#L709-L744)
3. Прочитать [истёкшие незавершённые записи](../postgresql/ingestion.md#list-pending-revision-writes). Для каждой удалить точки через `delete_revision_points`, которая подтверждает удаление и проверяет пустой набор. Если удаление завершилось с неизвестным исходом, перед повтором сверки этой записи снова пройти шаг 2: запоздалое удаление иначе может затронуть точки новой попытки.
4. Вызвать [`clear_revision_write_pending(revision_id, attempt_no)`](../postgresql/ingestion.md#clear-revision-write-pending) только для успешно сверенной записи. После окна обслуживания запустить обычных потребителей. Runtime возобновит задания без блокировки через outbox. Остальные отмеченные редакции останутся на сверке.

## Восстановление индекса

При штатном рестарте используем сохранённый том. При известной утрате индекса приостанавливаем обычную обработку вопросов, включая обращения к Exact Cache. Пустая выдача поиска сама по себе не показывает, потеряны ли данные.

- Восстанавливаем точки с прежними ID. Пока обычная обработка и изменения индекса остановлены, берём [манифесты текущих и закреплённых редакций](../postgresql/ingestion.md#list-required-revision-manifests) из PostgreSQL. Для каждой редакции [сверяем точный набор ID](./contracts.md#verify-revision-points). Например, 40 точек при ожидаемых 100 означают неполный индекс. Неверные или лишние ID также означают сбой даже при совпадении числа точек.
- Если число ожидаемых чанков неизвестно, восстанавливаем его в PostgreSQL из доверенного манифеста или повторно загружаем документ. Количество точек в восстанавливаемом снимке не используем как ожидаемое. При повторной загрузке оператор при необходимости создаёт коллекцию и использует прежние `document_id`. Worker публикует новые редакции и поколение. Редакции с признаком незавершённой записи сначала проходят сверку. Если для уже начатого запроса нужные редакции восстановить не удалось, Core в режиме обслуживания сохраняет технический итог обычным переходом и освобождает закрепление. После ремонтных операций снова приостанавливаем изменения и проверяем все оставшиеся нужные редакции. Затем возобновляем обычную обработку, включая Exact Cache.

При восстановлении PostgreSQL на более ранний момент также очищаем Exact Cache до запуска, поскольку номера поколений могут использоваться снова. [Снимки Qdrant](https://qdrant.tech/documentation/operations/snapshots/) · [Тома и перезапуск](../startup.md#что-переживает-перезапуск)
