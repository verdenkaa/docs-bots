**Support — внутренний компонент RAG API.** Он хранит историю обращения, ожидания и тикеты, предоставляет простой web-интерфейс оператора и админ-панель. ORM и атомарные переходы находятся в Runtime. Core сохраняет причину передачи, не ведёт разговор с оператором.

## Когда передаём человеку

| Ситуация | Что видит сотрудник | Создание тикета |
| --- | --- | --- |
| Начало работы, ещё не было ответа бота | Просьба задать вопрос; кнопки оператора нет. | Не создаётся. |
| Бот не нашёл подтверждённого ответа, включая вне темы/пустую выдачу | После создания — ссылка на тикет вместо кнопки вызова. При задержке сообщаем, что передача готовится. | Автоматически, без нажатия и десятиминутной отсрочки. |
| Ответ получен, пользователь явно сообщил, что он не помог | Кнопка «Позвать оператора». | Нажатие запускает ручной сценарий. |
| Пользователь явно просит человека после ответа бота | Кнопка «Позвать оператора». | Нажатие запускает ручной сценарий. |
| Обычный ответ без признака недовольства | Ответ и источники. Кнопку вызова не добавляем автоматически. | Не создаётся. |
| Отказ безопасности, бессмыслица, нет текста OCR или техническая ошибка | Пояснение соответствующего исхода. | Не создаётся только из-за самого отказа/ошибки. |

Недовольство — явная реакция пользователя на конкретный ответ, а не предположение модели по тону. Формат callback и явных команд закреплён в [DTO](./contracts.md); пользовательская реакция связана с исходным request_id. Просьба о человеке до первого ответа не запускает ожидание: сначала предлагаем задать вопрос либо дождаться уже выполняющегося.

## Ручной сценарий

1. Допущенный сотрудник нажимает кнопку, связанную с конкретным ответом. Проверяем принадлежность и актуальность действия.
2. Сохраняем ожидание и момент проверки через 10 минут. Повтор нажатия по тому же обращению не начинает срок заново.
3. Сотрудник может продолжать задавать самостоятельные вопросы. Ожидание помощи и открытый тикет не считаются активным RAG-вопросом.
4. По истечении срока спрашиваем «Помощь ещё нужна?». Только подтверждение «Да» создаёт тикет; «Нет» завершает ожидание. Без ответа автоматического создания нет.
5. После подтверждённого создания доставляем ссылку. Если обращение уже создано автоматическим путём, повторное подтверждение не создаёт дубликат.

Таймер и подтверждения хранятся в PostgreSQL, переживают рестарт и обрабатываются фоновым процессом RAG API. 20 секунд ожидания ответа модели не запускают этот сценарий.

## Контекст, оператор и аналитика

Support получает сохранённый вопрос, доступные ответы и причину передачи. В MVP сохраняется один исходный вопрос и фактический ответ, если был; этот снимок нужен оператору и не становится контекстом диалога LLM. Пользователь переходит по ссылке и общается с оператором в web-системе. В Telegram остаётся бот; Mini App и пересылка операторских реплик в тот же Telegram-чат не входят в срез.

Администратору нужны число запросов, темы, автоматические ответы, эскалации и время решения. Генерация без ошибки, молчание пользователя и лайк — разные наблюдения; формула успешного решения пока не утверждена. Данные дополняют технические логи, а не заменяются ими.

## Повторы

Core сохраняет намерение Support вместе с завершением обработки. Support подбирает его через Runtime и создаёт обращение идемпотентно. При неизвестном коммите сначала проверяет сохранённое состояние. После создания тикета сохраняет уведомление для общей доставки RAG API; сбой Telegram не создаёт второй тикет.
