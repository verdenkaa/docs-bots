## Что запускают сценарии

В репозитории две рабочие папки. В `docs/` находится сайт документации, а в `container-manager/` — единый Compose-файл, менеджер и настройки диагностики. Проект Compose называется `rag-hackathon`.

| Группа | Сервисы Compose |
| --- | --- |
| Infrastructure | `postgres` (PostgreSQL), `redis` (Exact Cache), `rabbitmq` (очереди), `qdrant` ([чанки, векторы и BM25](../infrastructure/qdrant/index.md)) |
| Application | `core` (RAG API и RAG Core), `worker` (Ingestion Gateway и Ingestion Worker) |
| Observability | `alloy` (сбор логов), `loki` (хранение), `grafana` (поиск и просмотр) |
| Load Testing | `locust` (веб-интерфейс запуска нагрузки) |

| Команда менеджера | Контейнеры | Когда использовать |
| --- | --- | --- |
| `up infra` | Infrastructure · 4 | Python запускается из IDE на хосте. Для доступа к базам добавьте `--local` перед командой. |
| `up app` | Infrastructure + Application · 6 | Запускает указанные образы приложения или собирает недостающие образы каркаса. |
| `up full` | Все группы · 10 | Диагностика с Grafana и Locust. Нагрузку запускают вручную в веб-интерфейсе. |

Повтор команды сохраняет работающие контейнеры. Например, `up full` после `up app` добавит четыре контейнера. Обратный переход остановит их. `monitor on/off` переключает только Grafana, Loki и Alloy, `load on/off` — только Locust. Для `load on` нужен готовый `core`.

## Как запустить

Нужны Python 3.10+ и современный Compose-провайдер. Подойдут Docker Desktop, Docker Engine с Compose, Docker CLI с контекстом Colima или Podman с внешним Compose-провайдером. Для Podman предпочтителен Docker Compose V2-совместимый провайдер. На Windows и macOS сначала запустите Desktop или соответствующую виртуальную машину. Менеджер проверяет доступ к движку и Compose, показывает варианты подключения и не меняет глобальный контекст. [Compose для Docker](https://docs.docker.com/compose/install/) · [Podman Compose](https://docs.podman.io/en/latest/markdown/podman-compose.1.html)

В Windows откройте папку `container-manager` и дважды щёлкните `manage.bat`. Из PowerShell в той же папке команда выглядит так.

```powershell
.\manage.bat
```

На Linux/macOS:

```bash
cd container-manager
sh manage.sh
```

Введите `1` и нажмите Enter для запуска инфраструктуры. Менеджер показывает этап операции и обновляет цветную таблицу на одном экране. Подробности ошибок открываются клавишей `D`.

Для подключения из IDE запустите `.\manage.bat --local up infra` в PowerShell или `sh manage.sh --local up infra` на Linux/macOS. При нескольких окружениях укажите движок перед действием, например `manage.bat --engine podman --local up infra`. Для Podman менеджер использует подключение, выбранное в его CLI.

### Где задаются пароли

Для каждого стенда используется свой `container-manager/.env`. В нём задаются `POSTGRES_PASSWORD`, `RABBITMQ_PASSWORD` и `GRAFANA_PASSWORD`. Compose берёт из этого файла учётные данные для инфраструктуры и передаёт соответствующие пароли `core` и `worker`.

- **Локально.** Если `.env` уже есть, менеджер использует его как есть. Если файла и томов ещё нет, менеджер создаёт `.env` один раз. На новом локальном стенде можно заранее задать свои значения по `.env.example`.
- **На сервере.** До первого запуска положите на сервер его собственный `container-manager/.env` с отдельными секретами. Сохраните файл в защищённом хранилище вместе с настройками стенда. `.env` исключён из Git.

Пароли сохраняются между запусками. Если файл потерян, а тома уже есть, восстановите исходный `.env`. Для смены пароля в работающем PostgreSQL сначала обновите его у роли в самой базе, затем синхронизируйте `.env` и настройки подключений.

Пункт **13** показывает в отдельном экране пароли PostgreSQL, RabbitMQ и Grafana, которые Compose читает из конфигурации. Переменные оболочки могут переопределить `.env`. После правки файла значения на экране могут отличаться от действующих паролей уже созданных учётных записей. `M` закрывает экран. Redis и Qdrant в текущем стенде доступны без паролей.

### Куда подключаться

В Compose используйте `postgres:5432`, `redis:6379`, `rabbitmq:5672`, `qdrant:6333` и `core:8000`. В интерактивном меню порты инфраструктуры публикуются на `127.0.0.1` по умолчанию. Для прямой команды используйте `--local up infra`. Менеджер пересоздаст только те контейнеры инфраструктуры, у которых отличаются настройки проброса. Именованные тома сохраняются. Для подключения Python с хоста задайте `PGHOST=127.0.0.1`, `PGPORT=5432`, `PGUSER=rag`, `PGDATABASE=rag` и пароль из `.env`. Занятый порт можно поменять, например через `POSTGRES_PORT=15432`.

В таблице мониторинга `In Compose` показывает адрес для кода внутри сети Compose, а `Host / browser` — фактически опубликованный адрес на хосте движка. С портами по умолчанию Qdrant открывается на [6333/dashboard](http://localhost:6333/dashboard), Grafana — на [3300](http://localhost:3300/), Locust — на [8089](http://localhost:8089/). Для PostgreSQL, Redis и RabbitMQ в таблице указаны адреса для клиентов. Прочерк означает, что адрес недоступен в этом режиме. При подключении к удалённому движку его `127.0.0.1` относится к серверу.

RabbitMQ считается готовым, когда принимает TCP-соединение на AMQP-порту `5672`. При следующем `up` менеджер применит новую проверку к уже созданному контейнеру RabbitMQ, если проверка отличается. Именованный том данных сохранится. [Проверки готовности RabbitMQ](https://www.rabbitmq.com/docs/4.1/monitoring)

### Как посмотреть память в Podman

Если Podman не отдаёт метрику памяти контейнера, менеджер показывает сумму RSS процессов с пометкой `MiB RSS` и обновляет её раз в 20 секунд. Если и этот замер недоступен, показывает `N/A`. Резидентную память отдельных процессов можно посмотреть вручную:

```powershell
podman top rag-hackathon-rabbitmq-1 -eo pid,rss,comm
```

Столбец `RSS` показывает память в КиБ. Имя другого контейнера можно взять из `podman ps`. Строка `ps` относится к самому замеру. Сумма RSS может повторно учитывать общие страницы и не включает весь учёт памяти cgroup. [Podman top](https://docs.podman.io/en/latest/markdown/podman-top.1.html)

На сервере используйте прямые команды без `--local` или запускайте меню с `--no-local`. Чтобы убрать уже опубликованные порты, пересоздайте затронутые сервисы с базовой конфигурацией и теми же томами. Для внешнего Telegram webhook понадобится отдельно настроенный HTTPS-вход. [Режимы приёма Telegram](../telegram/module/index.md) · [Порядок старта Runtime](../infrastructure/startup.md)

### Как подключить или обновить приложение

С пустыми `CORE_IMAGE` и `WORKER_IMAGE` менеджер при `up app` или `up full` автоматически собирает недостающие образы из `app/Dockerfile` через `compose.scaffold.yaml`. Чтобы подключить готовый образ, укажите его тег или digest для соответствующей роли в `.env`. На продовом стенде укажите оба тега или digest образов релиза.

Core слушает `0.0.0.0:8000` и отвечает на `/health/ready`. Worker пишет временные загрузки в `WORKER_SPOOL_DIR`. Его образ должен давать процессу право записи в этот каталог и включать healthcheck. Общие настройки приложения можно передать через `app.env`. У каркаса в Grafana Explore стартовые события можно найти запросом `{service=~"core|worker"} | json | operation="bootstrap" | mode="scaffold"`.

Для Telegram впишите выданный `@BotFather` токен в `TELEGRAM_BOT_TOKEN` в файле `container-manager/.env`. Compose передаёт эту переменную контейнеру `core`, где её читает RAG API. Менеджер генерирует пароли инфраструктуры, а токен добавляется вручную. Для запуска `up infra` токен не нужен. Если `core` уже создан, после правки токена выполните `update local`, чтобы Compose применил новые настройки. [Инструкция Telegram](https://core.telegram.org/bots/tutorial#obtain-your-bot-token)

После изменения кода каркаса выполните `update local`, чтобы пересобрать его. Для своих образов `update local` применяет уже собранные локальные теги, а `update registry` загружает указанные образы из реестра. Менеджер обновляет `core` и `worker` и проверяет их состояние. Для продового стенда сначала сверяйтесь с [порядком обновления и миграций](./production-update.md). Не запускайте CI/CD и менеджер одновременно для одного Compose-проекта.

## Как добавить контейнер или группу

1. Опишите сервис в `container-manager/compose.yaml` под `services`. Укажите образ и, если другим сервисам нужно дождаться готовности, добавьте `healthcheck`. Подключение внутри Compose идёт по имени сервиса. Порт для работы с хоста можно добавить в `compose.local.yaml` с привязкой к `127.0.0.1`.
2. Добавьте имя сервиса ровно в одну группу `GROUPS` в `manager.py`. Например, для новой базы добавьте её в `infra`, чтобы она входила во все три сценария. Для отдельной группы укажите её место в `GROUPS` и включите её в нужные сценарии `SCENARIOS`. `full` включает все группы автоматически. Группы запускаются по порядку и останавливаются в обратном. Если один сервис должен дождаться готовности другого, разместите зависимость в более ранней группе. Сервисы внутри группы запускаются вместе.
3. Обновите таблицу сценариев выше. На тестовом стенде запустите нужный `up`, проверьте новый сервис через `status` и `logs ИМЯ`, затем переключитесь на сценарий без него или выполните `stop`.

Меню, таблица, `logs` и `restart` используют список из `GROUPS`. Команды `monitor` и `load` переключают группы `monitoring` и `load`, а `update` обновляет образы группы `app`.

Перед удалением или переименованием сервиса остановите его по старому имени. Проверьте, нужны ли его данные и тома для переноса.

## Диагностика

### Команды меню

| № | Команда в терминале | Что делает |
| --- | --- | --- |
| 1 | `up infra` | Запускает PostgreSQL, Redis, RabbitMQ и Qdrant. Останавливает приложение и диагностику, если они запущены. |
| 2 | `up app` | Запускает инфраструктуру, `core` и `worker`. Останавливает диагностику. |
| 3 | `up full` | Запускает все группы и проверяет доставку логов в Loki. |
| 4 | `monitor on` | Запускает Loki, Alloy и Grafana. |
| 5 | `monitor off` | Останавливает группу мониторинга. |
| 6 | `load on` | Запускает Locust при готовом `core`. Нагрузку включают вручную. |
| 7 | `load off` | Останавливает Locust. |
| 8 | `status` | Обновляет таблицу состояния и ресурсов. В терминале `watch` показывает её непрерывно. |
| 9 | `logs ИМЯ` | Показывает последние строки журнала выбранного сервиса. |
| 10 | `restart ИМЯ` | Перезапускает выбранный контейнер. |
| 11 | `Update app images` | Пересобирает каркас и загружает из реестра образы, явно заданные в `.env`. В CLI доступны отдельные команды `update local` и `update registry`. |
| 12 | `stop` | Останавливает контейнеры проекта после подтверждения в меню. Тома сохраняются. |
| 13 | `passwords show` | Показывает настроенные пароли PostgreSQL, RabbitMQ и Grafana в интерактивном терминале. |
| 0 | | Закрывает меню. Контейнеры продолжают работать. |

### Типовые задачи

| Задача | Команда или действие |
| --- | --- |
| Посмотреть состояние и ресурсы | Таблица в меню обновляется автоматически. `R` обновляет её по запросу. Из обычной командной строки используйте `status` для снимка или `watch` для наблюдения. `N/A` означает, что метрика недоступна. |
| Узнать причину сбоя | В меню введите `9` и номер сервиса. В журнале `J` и `K` прокручивают строки, `M` возвращает в меню. Из обычной командной строки доступны `logs core` и `logs worker --follow`. При `unhealthy` проверьте логи и доступ к зависимостям. |
| Смотреть логи в Grafana | `monitor on`. Откройте [Grafana](http://127.0.0.1:3300/), войдите как `admin` с паролем из `.env`, затем Explore → Loki. Пример фильтра `{service="core"}`. |
| Проверить сбор логов | `monitor check` проверяет готовность Loki и показывает, наблюдалась ли доставка. Если записей ещё нет, сгенерируйте событие в стенде и повторите проверку. |
| Запустить или остановить нагрузку | `load on`, затем откройте [Locust](http://127.0.0.1:8089/) и вручную запустите тест. Остановить тест можно в интерфейсе. `load off` остановит весь сервис Locust, приложение продолжит работу. |
| Остановить весь проект | `stop`. Закрытие менеджера, выход из логов и `Ctrl+C` оставляют контейнеры работать. |

У Loki и Alloy в колонке Health может стоять `N/A`, поскольку для них нет Compose health check. Менеджер отдельно проверяет доступность Loki из Grafana и читает метрики Alloy. Если мониторинг доступен, но Alloy ещё ничего не доставил, менеджер показывает предупреждение. Если Alloy сообщает об отклонённых строках, меню показывает их число с момента его запуска. Причину смотрите в `logs alloy`. Например, Loki может отклонить старые записи при повторном чтении журнала. [Счётчики Alloy](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.write/) · [Порядок записей в Loki](https://grafana.com/docs/loki/latest/configure/#accept-out-of-order-writes)

Alloy получает логи через сокет движка на стороне Linux-хоста или VM. По умолчанию используется `/var/run/docker.sock`. Для rootless Podman путь уточните через `podman info --format '{{.Host.RemoteSocket.Path}}'` и задайте `ALLOY_SOCKET` в `.env` без префикса `unix://`. Сокет даёт Alloy доступ к API движка, поэтому используйте эту конфигурацию только на доверенном стенде. Для проверки из менеджера запускайте его на машине стенда, где доступен опубликованный loopback-порт Alloy. [Источник Docker в Alloy](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.docker/)

Grafana, Alloy и Locust публикуются только на loopback. Для удалённого просмотра откройте SSH-туннель со своего компьютера. Если локальный порт занят, поменяйте левый порт в аргументе `-L`.

```bash
ssh -N -L 3300:127.0.0.1:3300 -L 8089:127.0.0.1:8089 user@SERVER
```

Приложение пишет в stdout/stderr. Когда мониторинг выключен, эти записи по-прежнему видны через `logs` в пределах ротации движка (настройка Docker — по 10 МБ, до трёх файлов на контейнер). Loki удаляет записи по сроку хранения в семь дней. Оба ограничения действуют отдельно. После включения Alloy полнота старой истории зависит от сохранившихся локальных логов. [Ротация Docker](https://docs.docker.com/engine/logging/drivers/json-file/) · [Срок хранения Loki](https://grafana.com/docs/loki/latest/operations/storage/retention/)

Именованные тома сохраняют PostgreSQL, RabbitMQ, Qdrant, временные файлы worker, историю Loki, позиции Alloy и настройки Grafana. Redis хранит восстанавливаемый кеш в памяти. `stop` оставляет тома и контейнеры на месте. Если менеджер сообщает, что движок недоступен, сначала проверьте `docker info` или `podman info`, затем `docker compose version` или `podman compose version`.

## Как выполнить команды напрямую

Из `container-manager/` используйте то же имя проекта и те же профили. Для локального режима добавьте `-f compose.local.yaml` сразу после базового файла. Для Podman замените `docker compose` на `podman compose`.

```bash
c() { docker compose -p rag-hackathon -f compose.yaml --profile '*' "$@"; }
c config -q
c up -d --no-recreate postgres redis rabbitmq qdrant
c up -d --no-recreate core worker
c up -d --no-recreate loki alloy grafana
c up -d --no-recreate locust
c ps -a
c logs --tail 100 -f core
c stop locust grafana alloy loki
c stop
```

В PowerShell подставьте полную команду вместо `c`. Указывайте сервисы явно. Для перехода к инфраструктуре остановите диагностику, `core` и `worker`. При запуске вручную дождитесь готовности `core` перед использованием Locust. [Команды Compose](https://docs.docker.com/reference/cli/docker/compose/)
