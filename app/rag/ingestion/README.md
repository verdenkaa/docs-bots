# Индексация готового документа

`handle_ingestion_job(JobRef) -> ConsumeDecision` реализует часть Ingestion после разбиения на чанки. Worker читает сохранённую `DocumentBatch`, определяет опубликованную версию по имени, резервирует версию 0 либо следующую, получает embedding и примеры вопросов через Model Gateway, сохраняет `PreparedRevision`, записывает и проверяет оба индекса и публикует редакцию.

Входные и выходные DTO, сигнатуры операций и JSON-форматы сохранены. `contracts.py` этой реализацией не изменён. Конвертер, Gateway и вызываемая им `prepare_chunks` остаются отдельной частью подготовки; индексатор их не вызывает.

## Компоненты

| Файл | Ответственность |
| --- | --- |
| `worker.py` | Существующая публичная точка входа, валидация события и сборка одной обработки. |
| `_indexing.py` | Порядок переходов, резервация версии, подтверждение снимка, публикация и исходы сбоев. |
| `_batch.py` | Проверка целого документа и соответствия восстановленного снимка заданию. |
| `_preparation.py` | Пакетный embedding и детерминированная сборка ChunkPoint/TopicPoint. |
| `_topics.py` | Упаковка всех чанков в порции, системный промпт, строгий JSON и удаление точных повторов вопросов. |
| `_execution.py` | Проверка DTO на границах, монотонный бюджет попытки; трассировка используется из Runtime. |
| `_maintenance.py` | Ограниченная очистка после разрешения PostgreSQL. |
| `_dependencies.py` | Существующие операции Runtime/Model Gateway и часы; без создания клиентов. |
| `_settings.py` | Неизменяемые настройки текущей обработки из окружения. |

Модельные вызовы выполняются через Model Gateway. Его запуск, клиенты хранилищ, брокер, периодическое восстановление и супервизор процессов принадлежат Runtime. Импорт Ingestion не запускает эти компоненты.

## Обязательные настройки

Все переменные начинаются с `INGESTION_`. Worker читает только окружение процесса и не загружает `.env` самостоятельно. Без обязательных значений возникает `StepError("ingestion_configuration_error", False)` до claim задания.

| Переменная | Значение |
| --- | --- |
| `INGESTION_EMBEDDING_PROFILE` | Точный profile_id уже настроенного embedding Model Gateway и индекса. |
| `INGESTION_GENERATION_PROFILE` | Точный profile_id генератора примеров вопросов. |
| `INGESTION_PREPARATION_PROFILE` | Неизменяемая версия всего профиля подготовки: разбиения, генератора/промпта, упаковки и правил вопросов. |
| `INGESTION_EMBEDDING_DIMENSIONS` | Положительная размерность векторов, совместимая с Qdrant. |
| `INGESTION_EMBEDDING_INPUT_CHARACTERS` | Проверенный для модели максимальный размер одного текста embedding в символах Python. |
| `INGESTION_TOPIC_INPUT_CHARACTERS` | Проверенный предел суммы символов содержимого system/user сообщений, включая JSON и название документа. |
| `INGESTION_GENERATION_MAX_OUTPUT_TOKENS` | Положительный бюджет вывода для генерации примеров вопросов. |

Пределы символов не являются числом токенов. Их выбирают испытанием конкретной модели с учётом её токенизатора, служебного шаблона сообщений и выходного бюджета. Слишком большой чанк завершается явной ошибкой; текст не обрезается. Вопросы, извлечённые из всех порций документа, кодируются с purpose=query, исходные чанки — с purpose=document.

При смене генератора, промпта, упаковки или правил вопросов требуется новый preparation_profile. Профили нельзя незаметно менять между попытками старого задания. При восстановлении Worker сравнивает сохранённые профили, содержимое каждого чанка, изображения, имя, доступ, версию документа и размерность векторов.

## Дополнительные настройки

Названия полей `_Settings` переводятся в верхний регистр с префиксом `INGESTION_`, например `step_timeout_s` → `INGESTION_STEP_TIMEOUT_S`.

| Поля | Значения по умолчанию |
| --- | --- |
| `max_attempts` | 3; должно совпадать с политикой выдачи попыток Runtime. |
| `step_timeout_s`, `embedding_timeout_s`, `generation_timeout_s`, `index_timeout_s` | 10, 30, 60, 30 секунд. Каждый вызов дополнительно ограничен остатком срока попытки. |
| `retry_initial_s`, `retry_max_s` | 1 и 60 секунд, ограниченная экспоненциальная задержка. |
| `embedding_batch_size` | 32 текста. |
| `topic_questions_per_portion`, `max_topic_questions` | 8 и 10000. Превышение даёт ошибку без скрытого обрезания. |
| `max_question_characters`, `max_response_characters` | 1000 и 262144. |
| `max_document_characters`, `max_chunks` | 2000000 и 10000. |
| `cleanup_limit`, `cleanup_timeout_s` | 20 элементов на проход и общий бюджет 10 секунд. |

До begin_revision_write временный сбой получает сохранённый ограниченный повтор. После подтверждённого begin ошибка индекса оставляет qdrant_write_pending для сверки. Неизвестный коммит PostgreSQL возвращает retry_broker; потеря права — ack без дальнейших записей. Отмена корутины пробрасывается. Истёкшая попытка не пытается записать новый итог, а передаётся на проверку через повтор брокера/восстановление Runtime.

После подтверждённой публикации, окончательного сбоя или пустого claim выполняется ограниченная очистка. Удаление точек разрешает только claim_revision_cleanup; подтверждение удаления предшествует finish_revision_cleanup. Сбой очистки фиксируется отдельно и не меняет состоявшуюся публикацию. Стартовое и периодическое восстановление с очисткой подключены в Runtime runner; pending-записи по контракту MVP требуют операторской сверки. Фоновый цикл при импорте не создаётся.

Логи содержат ID, номера попыток/версий, профили, исходы и длительности. Тексты документов, названия источников, вопросы модели и полный ValidationError в них не выводятся.

## Проверка

Из каталога `app/`:

```text
python -m unittest discover -s tests -v
python -m unittest discover -s rag/ingestion/_tests -v
```

Тесты внутри модуля исполняют реальный обработчик с подстановками портов; общие тесты проверяют разбиение, настоящие файлы spool, Gateway и конвертер. Операции store_document_batch/load_document_batch и read_document_version/reserve_document_version реализованы в Runtime; их копий в Ingestion нет. Интеграционная группа проверяет исходный DOCX с изображением, сохранение S3/партии, подготовку двух индексов, публикацию версий 0/1 и дубль задания. Модели в этой проверке тестовые.

Конвертер возвращает ConversionResult с байтами; только Gateway пишет S3 и создаёт ConvertedDocument. Конфигурация конвертера: RAG_CONVERTER_*. Разбиение: INGESTION_CHUNK_CHARACTERS и INGESTION_CHUNK_OVERLAP. Для чтения Markdown используется RAG_MAX_MARKDOWN_BYTES.


## Как читать сценарий и логи

Начните с `_Indexer._run` в `_indexing.py`: комментарии `├──` / `└──` показывают
путь от claim до публикации. Подготовка описана в `_preparation.py`, генерация
примеров — в `_topics.py`. `_handle` выбирает повтор/отказ/сверку и отдельно
запускает уборку после подтверждённого результата.

Общий Runtime `_operation_trace` открывает контекст попытки и пишет started/finished;
`_span` размечает шаги и включает проверку их результата. Ingestion определяет
бизнес-исходы, Model Gateway добавляет вложенные модельные метрики. Самостоятельного
`_Trace` и ручного переноса profile_id из модельных результатов в шаги нет.
