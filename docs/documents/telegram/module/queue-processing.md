## Приём и постановка вопроса

1. Проверяем подлинность webhook и валидность update. Корректные обновления групп/каналов пропускаем: MVP работает только в личном чате.
2. По сохранённому update распознаём повтор; он сохраняет прежний исход, включая при последующем отключении сотрудника, и не запускает новую работу. Только для нового вопроса через Access/атомарную регистрацию проверяем текущий допуск по Telegram User ID.
3. Разделяем самостоятельный вопрос и управляющее действие. Просьба о человеке, недовольство ответом и подтверждение помощи идут в Support, не занимая новый слот Core.
4. Для вопроса атомарно проверяем активный слот сотрудника, сохраняем вход, время приёма и outbox `rag.questions`. Текст сохраняется непосредственно; изображение — как устойчивая ссылка/метаданные с подписью. После рестарта Core должен получить тот же файл, а не потерянный объект из памяти.
5. Подтверждаем webhook после надёжного решения. Отсутствие допуска, занятость и неподдерживаемый тип — завершённые бизнес-исходы: они не заставляют Telegram повторять update. Если решение/коммит проверить нельзя, приём требует технического повтора.

На сотрудника один активный вопрос, но общая очередь разных сотрудников сохраняется. Отказ занятому сотруднику не создаёт строку нового RAG-вопроса. Данные для распознавания обработанного update и необходимого уведомления сохраняются отдельно от постановки вопроса; конкретная схема — задача Runtime.

RabbitMQ может быть временно недоступен: приём допустим, пока PostgreSQL сохраняет outbox и есть глобальная ёмкость. Технический предел ёмкости отличается от занятости одного сотрудника. [Маршруты](../../architecture/message-flow.md)

## От Core до доставки

Core читает ссылку из `rag.questions`, выполняет пайплайн вне webhook и сохраняет бизнес-итог. Relay публикует уведомление о готовой работе. RAG API получает данные доставки из PostgreSQL, не запускает повторный поиск ради отправки.

- **Готовый ответ:** Markdown, источники и ID изображений идут в общий обработчик доставки.
- **Нет подтверждённого ответа:** Support сразу создаёт тикет; затем доставляем ссылку на созданный тикет. Кнопка вызова и десятиминутное ожидание здесь не нужны.
- **Отказ Guardrails / бессмыслица / нет текста OCR:** доставляем соответствующее пояснение, без автоматического создания тикета только из-за отказа.
- **Технический сбой:** сохраняем отдельный исход и политику повтора; не выдаём его за отсутствие знаний.

## Отправка результата

1. Через Runtime берём готовую доставку с номером и сроком попытки. На чат допускается одна активная отправка; разные чаты обслуживаются с общим ограничением для бота.
2. Готовим текст и список изображений. ID должны принадлежать сохранённому ответу; Runtime получает S3-файлы. Новый и кешированный ответ используют один путь.
3. Отправляем части в сохранённом порядке и фиксируем подтверждения. При сбое картинки не генерируем ответ заново и не повторяем уже подтверждённый текст.
4. Временный сбой планирует ограниченный повтор; окончательный или неизвестный исход фиксируется явно. Подтверждаем RabbitMQ после надёжного перехода либо проверки, что действие уже не требуется.

Неизвестный исход Telegram может привести к дубликату конкретной части; подтверждение локального состояния не доказывает, что внешнее сообщение не пришло. Если изображение окончательно недоступно, текст и описание сохраняются; это не молчаливый отказ от всего ответа. Лимиты текста и резервный текст остаются в [текущих правилах оформления](./entrypoints.md#send-answer); контракт составной доставки описан через DeliveryPart, сохранённый план и квитанции.

## Статусы и ограничения

- Фоновый контроллер RAG API использует исходное время приёма. Через 10 секунд без готового итога сохраняет одно уведомление «в работе»; перед отправкой проверяет актуальность.
- 20 секунд — целевая метрика: работа может продолжиться и дать более поздний ответ. Этот срок не создаёт тикет, не завершает попытку и не освобождает слот.
- Все исходящие сообщения — текст, картинки, статусы, занятость и Support — проходят общий лимитер. Скорость вопросов не равна числу отправок.
- Ограничение Telegram учитывается по фактическому ответу, включая `retry_after`; временные ошибки не запускают бесконечный цикл.
- Слот вопроса освобождается после конечного исхода доставки ответа/уведомления об эскалации либо окончательной ошибки доставки. Десятиминутное ожидание и открытый тикет сами по себе этот слот не занимают.

## Сбои и восстановление {#сбои-и-повторы}

| Сбой | Действие |
| --- | --- |
| Повтор update / уведомления / управляющего действия | Читаем прежний исход и состояние, не создаём новую работу. |
| PostgreSQL или итог коммита неизвестен | Не подтверждаем надёжный результат, повтор проверяет состояние. |
| Итог Core сохранён, уведомление потеряно | Relay и восстановление Runtime возобновляют доставку без новой генерации. |
| Сбой между частями ответа | Продолжаем по сохранённому прогрессу; неизвестную отправку отмечаем отдельно. |
| Рестарт во время статуса или ожидания помощи | Восстанавливаем сроки из PostgreSQL, не отсчитываем заново. |
| Сбой создания тикета | Сохраняем намерение и повтор; не выдаём пользователю выдуманную ссылку. |

## Отключение сотрудника во время вопроса

После коммита приёма вопрос завершается даже при последующем enabled=False. Досылаем текст, оставшиеся изображения либо ссылку автоматической эскалации; новые вопросы получают denied. Повтор уже принятого update не создаёт новый вопрос и сохраняет прежний исход. Прогресс и сроки доставки не обнуляются.
