## Запуск

Поднимаем один Redis во внутренней сети. Exact Cache хранит копии готовых ответов. После перезапуска Redis кеш можно начать с пустого состояния. При недоступности Redis Core идёт через поиск и генерацию.

## Ключ и значение

Ключ `rag:exact:v1:<sha256>` строим из SHA-256 нормализованного вопроса в UTF-8. Для общего корпуса один вопрос имеет один ключ в пределах совместимого профиля ответа. При несовместимой смене профиля или формата меняем префикс либо очищаем кеш при переключении. Значение содержит `RagResult` и `corpus_generation` для сравнения с поколением запроса. [Точки входа Exact Cache](../../rag-core/exact-cache-entrypoints.md)

```json
{
  "corpus_generation": 42,
  "answer_text": "Инструкция находится в разделе «Установка».",
  "sources": [
    {
      "document_id": "43f95f66-7343-4cbc-beb5-19fd36a8ca77",
      "revision_id": "bb32ecbf-082b-4497-a41f-4b61aa56a139",
      "chunk_id": "545f64ff-7692-579a-842a-31f87e6522df",
      "source_name": "Руководство по установке.pdf",
      "locator": { "page": 4, "section": "Установка" },
      "source_url": null
    }
  ]
}
```

Записываем новые готовые ответы с источниками после коммита в PostgreSQL. Подтверждение вопроса и доставка опираются на PostgreSQL. Срок жизни записи освобождает память, актуальность определяет поколение.

## Чтение и конкурентное обновление

1. После Guardrails Core передаёт Exact Cache нормализованный вопрос и закреплённое поколение. Exact Cache читает ключ и сравнивает поколения.
2. Совпадение даёт готовый ответ. Более старая запись даёт промах и удаляется условно. Если другой запрос уже заменил прочитанное значение, удаление пропускается. Более новая запись тоже даёт промах для старого запроса.
3. При записи сравниваем поколение с уже сохранённым значением. Старый запрос может записать ответ в пустой ключ, а более новое значение сохраняет приоритет. Сравнение и изменение делаем атомарно, например условной транзакцией Redis.
