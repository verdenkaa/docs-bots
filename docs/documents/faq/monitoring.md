Мониторинг использует существующий datasource `rag-loki` и JSON-события приложения
из stdout. [Формат событий](./logging.md) и архитектура определяют смысл показателей;
наличие панели не означает наличие трафика или готовность всех бизнес-сценариев.

Серверная сборка дополнительно подключает единый
[бизнес-дашборд](./business-analytics.md) с PostgreSQL: вопросы, темы,
автоответы без эскалации, тренды и приоритеты улучшения документации.
Рабочие и демонстрационные данные в нём разделены. Локальный профиль мониторинга
сохраняет четыре технических экрана, описанных ниже.

## Развёртывание и воспроизводимость

В `container-manager/monitoring/` находятся `dashboards.yaml`, четыре JSON в
`dashboards/`, генератор `generate_dashboards.py` и изолированная проверка `verify.py`.
Compose монтирует provider и JSON только для чтения. При обычном запуске профиля
`monitoring` Grafana создаёт папку **RAG** и четыре дашборда. Стабильные UID:
`rag-overview`, `rag-pipeline`, `rag-ingestion`, `rag-messaging`.
Изменения файлов перечитываются каждые 30 секунд. Повторный запуск обновляет те же
дашборды; правки через UI не сохраняются. Для существующего контейнера после
добавления mounts нужно выполнить обычный `up` профиля monitoring с пересозданием
Grafana. Тома и данные сбрасывать не нужно.

Из корня репозитория:

```text
python container-manager/monitoring/generate_dashboards.py
python container-manager/monitoring/verify.py
```

Генерация требует только стандартную библиотеку Python. Проверка требует Docker
и образы Loki 3.5.8/Grafana 12.1.1; создаёт отдельную сеть и временные контейнеры
без постоянных томов, не читает `.env`, не обращается к рабочим сервисам.
Контрольные события в её Loki явно тестовые и не попадают в рабочие дашборды.
Проверяются provisioning, сохранение ID при рестарте, запросы LogQL, отсутствие
данных, контрольные расчёты и ссылки Explore. Для изменений приложения дополнительно
выполните из `app/` `python -m unittest discover -s tests -v`.

Поведение provisioning и агрегаций сверено с официальными описаниями
[Grafana provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/)
и [LogQL metric queries](https://grafana.com/docs/loki/latest/query/metric_queries/).

## Что показывают экраны

| Дашборд | Содержание |
| --- | --- |
| **RAG Overview** | Принятые уникальные вопросы, результаты Core, answered/support/notice, технический итог, p50/p95/p99 приём→коммит Core, доля до 20 секунд, динамика и распределение исходов. Support означает сохранённое автоматическое намерение; создание тикета диагностируется в событиях Support. |
| **RAG Pipeline Performance** | Guardrails и его исходы; cache hits/misses/unavailable и hit rate; Searcher и пустая выдача; генератор и insufficient_evidence; модели по role/profile с ожиданием, inference и reuse; длительности и доли верхних шагов Core. |
| **Ingestion & Document Lifecycle** | Принятие загрузки отдельно от Worker и публикации; конвертация, чанкинг, embeddings, подготовка примеров, запись/проверка Qdrant, транзакция публикации, ретраи, reconciliation, редакции и поколения. |
| **Messaging & Reliability** | Попытки Relay по трём маршрутам, обработанные уведомления, ожидание готовой outbox, отдельные подтверждения брокера/БД, redelivery/retry_broker, Telegram HTTP-задержки и 429, доставка и восстановление уведомлений. |

Верхние KPI используют весь выбранный диапазон, графики — интервал Grafana
с минимальным шагом 1 минута. По умолчанию открыт последний час, обновление 30 секунд.
Все длительности в миллисекундах. Порог 20000 мс относится к времени **приём→коммит
Core**. Доставка Telegram наблюдается отдельно; из текущих DTO нельзя получить
достоверный единый числовой замер приём→успешная доставка. Цветовой порог доли 95%
служит настройкой отображения и не объявляет новый SLA проекта.

## Методика подсчёта

Принятые вопросы: только `rag_api/handle_telegram_update`, `event=finished`,
`outcome=accepted`, непустой `request_id`. Повтор update возвращает `duplicate`.
Завершённые вопросы: только `rag_core/handle_rag_question`, `event=finished`,
непустой `result_status`, появляющийся после подтверждённого `complete_question`.
`started`, `retry_scheduled`, `stale_attempt`, `not_claimed` сюда не входят.
Количество считается как число групп `request_id`, а не число строк логов.
Идемпотентный коммит создаёт единственный терминальный результат; перцентили
используют его `processing_elapsed_ms`, не длительности предшествующих попыток.

«Обработаны без технического итога» включает все зафиксированные бизнес-исходы,
кроме `notice` с `result_code=technical_error`. `notice` без известного
`result_code` в этот успешный счётчик не включается. «Ответы по документации» —
только `result_status=answered`. Их доля имеет знаменателем **все результаты Core**,
включая технические; это когорта завершений. Входящие за тот же период могут ещё
обрабатываться, а завершения могут принадлежать вопросам, принятым ранее.

Доля до 20 секунд: число терминальных вопросов с известным
`processing_elapsed_ms ≤ 20000` / число терминальных вопросов с известным замером.
Отрицательная разность UTC не публикуется. Для сравнения между процессами нужна
синхронизация часов. Замер включает возврат операции коммита и её сетевое время.
Глобальные перцентили вычисляются `quantile_over_time(... ) by ()` по сырым
замерам; перцентили по ролям/профилям/шагам группируются внутри этой функции.
Перцентили отдельных потоков не усредняются и не складываются.

На Pipeline и Messaging единица учёта — **вызов или попытка**, включая ретраи.
Hit rate = cache_hit / (cache_hit + cache_miss); unavailable показан отдельно.
Диагностические ошибки по компонентам не являются числом независимых первопричин:
одна ошибка зависимости может наблюдаться в нескольких компонентах.
Для распределения времени суммируются только верхние шаги Core с `step_depth=0`;
вложенные модели и handler не прибавляются повторно. Промежутки вне шагов не входят.

Нет наблюдений — **Нет данных** или разрыв графика. Никаких искусственных нулей
для отсутствующего трафика. В отношении пустой числитель превращается в ноль
только при наблюдаемом знаменателе, например 0 hits при известных misses.
Период до внедрения инструментирования не имеет новых полей и замеров.

Логирование не транзакционно с PostgreSQL: сбой после коммита и до записи stdout
может потерять терминальное событие. Дедупликация счётчиков защищает от повторных
строк в диапазоне; произвольное повторное копирование терминальных логов с новыми
timestamp может исказить выборку перцентилей. Для аудиторских счётчиков нужны
показатели из устойчивого состояния БД.

## От KPI к конкретному запросу

Фильтры `service`, `component`, `operation`, `route` применяются после JSON-разбора;
для проекции шага `operation` сопоставляется с `parent_operation`.
`request_id`, `delivery_id`, `job_id` — поля ввода только для диагностической панели,
а не глобальные фильтры статистики. Пустые значения не выбирают все сообщения.

1. Выберите нужный диапазон и введите `request_id` внизу любого дашборда.
2. Сбросьте component/operation/route на All для полного пути. В логах будут API,
   Core, Relay для `rag.questions` и доставка API.
3. Скопируйте `delivery_id` из доставки в одноимённый фильтр. Панель использует
   объединение request_id **или** delivery_id **или** job_id. Так добавляется Relay
   для `rag.results`: его `ResultNotice` по контракту не содержит request_id.
4. `message_id` связывает RabbitMQ и Relay, `run_id` — started/finished и шаги одной
   попытки. Сравнивайте attempt_no вместе с операцией: доставка и Core нумеруются отдельно.
5. Клик по значению KPI/графика или полю таблицы открывает соответствующий запрос
   в Grafana Explore с текущим диапазоном. Исходный JSON доступен в деталях логов.

Alloy сохраняет прежний pipeline и постоянный label `service`. `request_id`,
`job_id`, `run_id`, `delivery_id`, `message_id`, а также диагностические JSON-поля
не добавляются как постоянные Loki labels. Группировка ID в LogQL временная и
может упереться в лимит series на больших диапазонах: сузьте диапазон/сервис,
не увеличивайте retention и лимиты автоматически. Retention стенда — 7 дней.

## Что пока нельзя измерить корректно

| Показатель | Причина и минимальное расширение |
| --- | --- |
| Текущее число активных обработок | started−finished не переживает crash, рестарт и начало диапазона. Нужен периодический снимок действующих lease из PostgreSQL по компоненту, а не счётчик разности логов. |
| Ready/unacked backlog RabbitMQ | Публикации/consume — события, не gauge очереди. Без нового сервиса можно включить `rabbitmq_management` и собирать `messages_ready/messages_unacknowledged` через Management HTTP API периодическими JSON-снимками. Плагин и poller сейчас не включены. |
| Полное время принятие документа→публикация | В сохранённых данных, доступных Worker, нет времени регистрации. Нужен accepted_at в служебных метаданных задания и publication_elapsed_ms после подтверждённого publish_revision. Это отдельное изменение хранения/внутреннего контракта. В текущем решении видны время Gateway, попытка Worker и транзакция публикации отдельно. |
| Текущее число незакрытых reconciliation | Лог показывает факт перехода, а не актуальное состояние. Нужен периодический снимок соответствующего состояния БД. |
| Полное время вопрос→доставка Telegram | У ClaimedDelivery нет времени первоначального приёма. Нужен служебный замер из сохранённого состояния вопроса при complete_delivery; публичный DTO в этой задаче не расширяется. |

Эти ограничения показаны и на самих дашбордах. Реализация не добавляет сервисы,
не меняет публичные DTO, не запускает модели при импорте и не записывает тексты
вопросов, ответов, документов или секреты.
